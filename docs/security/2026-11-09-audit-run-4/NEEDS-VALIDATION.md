## SHA-pinned shared release workflow runs its own compute-version and announce-release actions from mutable @main inside Pulsix's privileged release job

Fingerprint `github-workflows/create_docker_changelog_version_release:floating-self-reference-in-pinned-release-workflow`

release.yml pins NoiXdev/github-workflows' create_docker_changelog_version_release.yaml to commit f7196176 (release.yml:86). The comment at release.yml:83-85 gives the reason: `secrets: inherit` (release.yml:101) hands the registry credentials and the Discord webhook to whatever the reference resolves to (backlog 7.16, which also recorded on 2026-11-01 that github-workflows' main had no branch protection). The pinned file still calls two of its own actions by branch. Line 234 calls `NoiXdev/github-workflows/actions/compute-version@main`, with the comment 'Deliberately unpinned ... the README records why the self-references float' (github-workflows@f7196176:README.md:39-42). Line 577 calls `NoiXdev/github-workflows/actions/announce-release@main`. Every other `uses:` in that file is pinned to a 40-character SHA. GitHub resolves a nested `uses: owner/repo/path@ref` exactly as written, so the caller's SHA pin does not cover these two calls. They run whatever github-workflows' main holds when the job is set up.

The release job runs its steps in this order: (1) the Docker Hub configuration check, whose env holds DOCKERHUB_USERNAME and DOCKERHUB_TOKEN for that step only (github-workflows@f7196176:.github/workflows/create_docker_changelog_version_release.yaml:194-214). (2) actions/checkout with `token: secrets.GITHUB_TOKEN` and the default persist-credentials (216-223). (3) setup-node. (4) compute-version@main (230-238). (5) QEMU and Buildx. (6) docker/login-action with the Docker Hub secrets, skipped on a dry run (332-338). (7) Builds and pushes of the manager and worker images from the checked-out tree (370-433). (8) A commit pushed to Pulsix main, then a tag (486-513). (9) The GitHub release (515-).

The job's token has contents: write: release.yml:82 grants it, and the shared workflow asks for it at the workflow level (171-172). The step at position 4 is a composite action. It can read that token through `github.token` or the credential checkout persisted in .git/config. It can also change the working tree, which steps 7 and 8 then build into noixdev/pulsix-manager and pulsix-worker and commit. The Docker Hub token cannot be read through the `secrets` context inside a composite action. The action can, however, write GITHUB_PATH or GITHUB_ENV so that the `docker` binary later called by login-action and build-push-action is a wrapper of its choosing. Step 4 also runs on a dry run (the default input), and there it still has the contents: write token.

The announce job (565-583) has no job-level permissions, so it inherits contents: write. It runs announce-release@main with DISCORD_WEBHOOK_RELEASE_NOTIFICATION. Pulsix's own announce.yml:49 pins the same action to f7196176, which shows the intended policy.

Backlog 7.16 accepted the floating self-references when the only floating one received just the webhook ('it receives only the webhook'). The Docker workflow adopted on 2026-11-09 (backlog 7.5) puts a floating action inside the credentialed build job, which that rationale did not cover. As a result, anyone who can update github-workflows' main controls code that runs in Pulsix's release job. That covers the image content, a hijack of the Docker Hub login, and the contents: write token on NoiXdev/pulsix (main, tags, releases). It needs no Pulsix review and no change to the pinned SHA. Whether this is broader trust than Pulsix's own release maintainers depends on who can write to that repository and whether its main is protected. Neither is visible in source.

**Claimed root cause:** The integrity control is a SHA pin on the reusable workflow alone. The pinned workflow refers to its own composite actions by the mutable branch `@main` (github-workflows@f7196176 create_docker_changelog_version_release.yaml:234 and :577). The code that runs with the release job's contents: write token, before the registry login and the image builds, is therefore chosen by github-workflows' current main, not by the pinned commit.

## Release guard and Docker Hub credentials sit only in workflow code the dispatched ref supplies (no environment since 38098bdb)

Fingerprint `github-workflows/release.yml:registry-secrets-reachable-outside-release-guard`

release.yml is workflow_dispatch only (line 18). Its publishing job `release` (line 79) gets contents: write (line 82) and calls the shared NoiXdev/github-workflows Docker release workflow, pinned by SHA (line 86), with `secrets: inherit` (line 101). That hands every organization secret available to the repository to the called workflow, including DOCKERHUB_USERNAME/DOCKERHUB_TOKEN and the Discord webhook. The release has two authorization checks, both in the guard job of the same file: github.ref must be refs/heads/main (lines 50-57), and the newest ci.yml push run on main for the SHA must be green (lines 59-77). More directly, any workflow on any branch, for example ci.yml's `on: [push, pull_request]` (ci.yml:2) edited on a pushed branch, can name secrets.DOCKERHUB_TOKEN itself. Even with an environment in place, the secrets would stay reachable, because docs/BACKLOG.md:587 records them as organization secrets readable by any run of the repository, not environment secrets, and the owner decided on 2026-11-09 to keep them that way ('won't do'). ## One host agent identity can drive back-to-back maximum check-result batches against the instance-wide Postgres pool and check_samples hypertable

Fingerprint `internal/agentapi/stream.go:receiveMessages:no-per-agent-check-results-ingest-budget`

An enrolled host agent sends CheckResults messages on AgentStream. The manager processes each message as soon as it is received. The server applies no rate, interval, row or byte budget to them. Each batch may hold 1000 observations (MaxObservationsPerBatch). The repository's own measurement (samples.go:150) puts 10 000 observations at 11.98 s of serial statements on one pool connection, so a full batch holds a connection for about 1.2 s, inside one transaction. One identity may keep two streams open (maxStreamsPerSerial = 2), so a looping agent can keep about two connections of the shared pool busy continuously. In code the pool is opened with pgxpool.NewWithConfig and no MaxConns. The shipped compose DSN sets neither pool_max_conns nor statement_timeout, so the default is max(4, NumCPU) connections. A few such agents could therefore occupy the pool that every tenant's HTTP, worker and rule-engine work shares. Possible sources are a compromised monitored host, which is root on a host with no REST access, or several agents enrolled by an operator of one organization. Each stream would also insert about 800 sample rows per second into the instance-wide check_samples hypertable, kept for 90 days. The label field is not length-bounded at ingest (withinContract bounds only check_key, item and metric), so a message may carry up to the 16 MiB gRPC receive cap of label data. Heartbeat resolves received a per-serial bound in backlog 7.25, but ingest did not. A legitimate agent sends at most 200 results per collect, about every 30 s, but only the client enforces this. Recovery: the load stops when the agent's certificate is revoked or the host is deleted. Rows already written stay until the 90-day retention or the host-delete cascade removes them. Source and the hunter's local harness establish that the input-to-cost path is unpaced. How much the real pool and database actually degrade has not been measured.

**Claimed root cause:** receiveMessages/process/recordCheckResults forward every CheckResults batch to checks.Service.RecordObservations. They apply no per-serial or per-organization pacing, row or byte budget, or concurrency limit on the shared pool (the only per-serial throttle, allowResolve, gates heartbeat resolves). MaxObservationsPerBatch bounds one transaction, not how many transactions an identity drives back to back. MaxTuplesPerHost bounds distinct tuples, not sample rows. The label value is unbounded except by the 16 MiB message cap. The legitimate cadence (200 results per message, 30 s collect) is enforced only in the agent.

### Trace

1. **entrypoint** `internal/agentapi/stream.go:95` (Service.receiveMessages): Each AgentMessage from the mTLS-authenticated agent stream (lower-trust host agent identity) is received and processed serially, with no pacing between messages
2. **propagation** `internal/agentapi/stream.go:150` (Service.process): A CheckResults body goes straight to recordCheckResults. Only the heartbeat branch is throttled, by allowResolve (line 200)
3. **propagation** `internal/agentapi/stream.go:298` (Service.recordCheckResults): The whole batch is converted and handed to Checks.RecordObservations for the agent's organization
4. **propagation** `internal/checks/samples.go:336` (Service.RecordObservations): After the count, contract (check_key/item/metric only), shape and plausibility checks, every valid observation goes to the store
5. **propagation** `internal/checks/store_sql.go:271` (SQLStore.RecordObservations): One WithOrg transaction on the instance-wide pool for the whole batch
6. **sink** `internal/checks/store_sql.go:390` (writeHostObservations): An UpdateCheckCurrent plus an InsertCheckSample per observation, issued serially inside that transaction, writing to the shared check_samples hypertable, which has no uniqueness on (tuple, at)

### Evidence

- `internal/checks/samples.go:150`: The repository's own measurement: 10 000 observations took 11.98 s on one pool connection, about 1.2 s per 1000-observation batch. The comment itself calls an unbounded batch a denial of service against other tenants
- `internal/checks/samples.go:165`: MaxObservationsPerBatch = 1000 bounds a single batch, not the batch rate
- `internal/agentapi/registry.go:46`: maxStreamsPerSerial = 2: one identity can run two ingest loops concurrently

- `deploy/compose/docker-compose.yml:29`: The shipped DSN sets neither pool_max_conns nor statement_timeout
- `internal/db/migrations/00044_check_samples.sql:50`: Hypertable rows are kept for 90 days for the whole instance. label (line 45) is unbounded text

## A host agent can store multi-MiB check labels and error texts that never expire and are reloaded on every evaluation

Fingerprint `internal/checks/samples.go:withinContract:unbounded-label-and-error-bytes-per-tuple`

Backlog 7.57 caps a host at 4096 check_current tuples. That limits how many rows a host has, not how large they are. The check-results contract bounds check_key (64 bytes), item (512) and metric (64). The label and the collection-error text an agent sends have no length bound on the ingest path: not in the agentapi mapping, not in the service's contract or shape checks, not in the SQL store, and not as a column CHECK. The only ceiling is the shared gRPC receive limit of 16 MiB per message. A host agent under an attacker's control (root on an enrolled host, using its own mTLS identity) can fill its tuple quota and then keep resending existing tuples with labels or error strings close to 16 MiB each. An existing tuple is always updated in place, even at the cap. Up to 4096 such values then stay in check_current, which nothing prunes. The labels are also copied into check_samples (90-day retention) on every batch, the label into check_states.last_label on every evaluation, and into check_state_changes on state changes. Every accepted batch marks the host dirty. Each evaluation then reads the whole set into the manager process with ListCheckCurrent (SELECT *) inside a transaction with a 10 s statement timeout. The host page API (CurrentForHost) loads and encodes the same set. The manager process and the Postgres instance serve every tenant, so the memory, I/O and disk growth is shared. The principal is one host agent, and recovery needs manual row deletion. Verifier reproduction (sandboxed, against checks.Service with the package's fake store): a metric of 65 bytes is refused with ErrInvalidInput before reaching the store, while a 15 MiB label and a 15 MiB error string are each accepted (accepted=1, err=nil) and reach the store. A CheckResults protobuf carrying that 15 MiB label is 15,728,678 bytes, which fits under the 16 MiB receive limit. The persistence and reload half is source-only, because the Postgres-backed path cannot run here.

**Claimed root cause:** withinContract (internal/checks/samples.go:192-213) bounds only the three identifying strings (check_key, item, metric). Observation.Label and Observation.Err pass unchanged through agentapi.Service.recordCheckResults (stream.go:289-295), Service.RecordObservations (wellShaped and plausible look at shape and time only) and SQLStore.writeHostObservations into unconstrained text columns (migration 00044 check_current/check_samples label and error, migration 00046 check_states.last_label). So MaxTuplesPerHost bounds rows per host but not bytes per host. The rule evaluator's Load and the host page then read every stored byte.

### Trace

1. **entrypoint** `internal/agentapi/stream.go:292` (Service.recordCheckResults): The agent-supplied CheckResult label, and at line 294 the error string, from an mTLS-authenticated host agent stream are copied verbatim into checks.Observation. ## Passkey registration finished with a session principal resolved before an admin ResetSecondFactor can add a passkey after the reset

Fingerprint `pulsix/auth/enrolment-writes-not-revalidated-against-ResetSecondFactor`

An instance admin uses ResetSecondFactor (internal/accounts/actions.go) to lock someone out of an account. In one transaction, under the users row lock, it deletes every TOTP secret, recovery code and passkey, revokes every session and voids reset links. It does not delete pending webauthn_ceremonies, and it cannot affect requests already in flight. CookieMiddleware resolves the session cookie into a Principal once, when the request headers arrive (middleware.go:31), before huma reads the body. huma v2.40.0 then reads the JSON body under a default 5 s per-operation BodyReadTimeout, before it calls the handler, and http.Server sets only ReadHeaderTimeout. A client can therefore send the headers of POST /api/v1/auth/passkeys/register/finish while its session is still live and send the body later, for example once a parallel GET /auth/me returns 401. When the handler runs, requireEnrolmentSession accepts the snapshot (MFAComplete=true, MustChangePassword=false). requireFreshFactor reads Enrolled live; the reset has just removed every factor, so Enrolled is false and the freshness check is skipped. FinishRegistration takes the ceremony, which is checked only for kind and user id and survived the reset, verifies the attestation and inserts the passkey with an unconditional INSERT. completeEnrolment does nothing for an MFA-complete principal, so the request returns 200. Passkey login then gives the attacker an MFA-complete session. Without a temporary password the attacker has full access again. With one, the attacker's sessions are held at password_change_required until the owner changes the password. Preconditions for the passkey path: register/begin takes no request body (passkey_handlers.go:89, *struct{}), so it runs as soon as the headers arrive and cannot be parked. The ceremony must therefore be begun before the reset, while the account still has a factor, so the attacker must pass requireFreshFactor at begin: a factor proven within StepUpWindow (5 min), and a ceremony used within CeremonyTTL (5 min). For this path the attacker is someone who holds an account factor (or a session that proved one in the last 5 minutes), which is the person a second-factor reset is meant to lock out; a cookie alone, without a fresh factor, is not enough for the passkey path. A parked finish request that times out never reaches the handler and does not consume the ceremony, so the attacker can open a new parked request every few seconds for the life of the ceremony and renew the ceremony with a step-up. Variants with the same root cause: (a) TOTP enrol and confirm (both take a codeInput body, so both can be parked) under stale principals. This variant needs only an MFA-complete session cookie, not a fresh factor: after the reset requireFreshFactor is exempt because Enrolled is false, and TOTP.BeginEnrol asks for no code when no secret exists, so the attacker parks an enrol and a confirm request before the reset, sends the enrol body after it, computes a code from the returned secret and sends the confirm body. MarkSessionMFAComplete selects the session by id only, with no revoked_at or expires_at predicate, so ConfirmTOTP commits a confirmed secret chosen by the attacker for a revoked session. Signing in with that secret also needs the password; without the password the planted factor still blocks the owner's re-enrolment (the owner's next pending session must verify a factor the owner does not have) until an admin resets again. (b) A passkey login whose assertion was validated just before the reset creates a live MFA-complete session after it. Sessions.Create is not re-validated against the reset. The bundled compose proxy (Traefik, deploy/compose/docker-compose.yml) configures no request-buffering middleware on the manager router, so the parked-body window is not removed there.

**Claimed root cause:** Credential-adding writes (Passkeys.FinishRegistration -> AddCredential/InsertPasskey, TOTP BeginEnrol/ConfirmEnrol, and Sessions.Create in FinishLogin) are authorised against a session Principal resolved before the request body is read. They are neither serialised on the users row lock that ResetSecondFactor takes (they do not re-check under it) nor conditioned on the authorising session still being live (Sessions.StillValid exists but is not used). requireFreshFactor exempts an account with no enrolled factor, and the reset produces exactly that state. Registration ceremonies are bound to the user only and survive the reset. MarkSessionMFAComplete does not filter revoked or expired sessions.

### Trace

1. **entrypoint** `internal/api/passkey_handlers.go:109` (POST /api/v1/auth/passkeys/register/finish): Route for an attacker-held interactive cookie session. huma reads its JSON body (ceremony_id, name, attestation response) under a 5 s default BodyReadTimeout before the handler runs, so the body can arrive after an admin's reset has committed.
2. **propagation** `internal/auth/middleware.go:31` (CookieMiddleware): The Principal (MFAComplete, MFAAt, MustChangePassword) is resolved once via Sessions.Lookup when the headers arrive (mounted at api.go:407) and is never re-validated for this request.
3. **propagation** `internal/api/session_gates.go:226` (requireEnrolmentSession): Accepts the snapshot: MFAComplete=true and MustChangePassword=false admit the request without a live session check.
4. **propagation** `internal/api/session_gates.go:191` (requireFreshFactor): Enrolled is read live. After ResetSecondFactor it is false, so the function returns nil and the step-up check (passkey_handlers.go:116) is skipped because the lock-out removed every factor.
5. **propagation** `internal/accounts/actions.go:93` (Service.ResetSecondFactor): Concurrent admin action under withAccount (LockAccount FOR UPDATE): DeleteSecondFactors, RevokeAllSessions and VoidResetTokens, then commit. Pending webauthn_ceremonies and in-flight requests are untouched.
6. **propagation** `internal/auth/passkey.go:221` (Passkeys.FinishRegistration): The ceremony taken by TakeCeremony (passkeys.sql:20) is checked only for kind and owning user id. There is no binding to a session or reset generation, so a ceremony begun before the reset is still accepted.
7. **sink** `internal/auth/passkey.go:238` (Passkeys.FinishRegistration -> SQLPasskeyStore.AddCredential): InsertPasskey commits a new passkey for the account after the reset. Its FK lock on users waits for the reset transaction if that is still open, then succeeds because the users row still exists. The handler then returns 200 (completeEnrolment is a no-op at session_gates.go:248).

### Evidence

- `internal/api/passkey_handlers.go:89`: register/begin takes *struct{} (no body), so it cannot be parked. It runs requireFreshFactor while the account still has factors, so the attacker needs a factor proven within StepUpWindow before the reset to obtain a ceremony.
- `internal/db/queries/accounts.sql:95`: LockAccount takes users FOR UPDATE. ResetSecondFactor's deletes and revocations run under it, but no enrolment write takes or re-checks under this lock, so they serialise after the reset instead of being refused.
- `internal/db/queries/accounts.sql:106`: DeleteSecondFactors deletes totp_secrets, recovery_codes and passkeys only. webauthn_ceremonies rows for the user survive (the only other deletes are TakeCeremony and the expiry reaper in passkeys.sql).
- `internal/db/queries/passkeys.sql:4`: InsertPasskey is an unconditional INSERT with no predicate on a live session or a reset generation.
- `internal/api/session_gates.go:248`: completeEnrolment returns without touching the session when the snapshot was MFA-complete, so no step of the request notices that the session was revoked.
- `internal/db/queries/auth.sql:49`: MarkSessionMFAComplete's CTE selects the session by id only (no revoked_at/expires_at predicate, unlike GetSession at auth.sql:27), so it updates 1 row for a revoked session (variant a).
- `internal/auth/enrolment.go:57`: ConfirmTOTP relies on MarkMFAComplete returning ErrNotFound for an ended session to roll back the confirmation. Its doc comment promises 'an already-ended session returns ErrNotFound and changes nothing', but the SQL does not enforce this for a revoked session.
- `internal/auth/passkey.go:349`: FinishLogin creates an MFA-complete session after validating against a credential read earlier in the request. A reset that commits in between does not prevent the session (variant b).
- `internal/auth/session.go:139`: Sessions.StillValid already re-checks a session mid-request (used by the job log stream, backlog 7.22). The enrolment routes do not use it or any equivalent.
- `cmd/manager/main.go:227`: Only ReadHeaderTimeout is set on http.Server. Reading the body after the middleware is bounded only by huma v2.40.0's default per-operation BodyReadTimeout (5 s, huma.go:1567-1569, applied before the handler at huma.go:1041-1043).
- `internal/api/mfa_handlers.go:105`: POST /api/v1/auth/totp/enrol and /totp/confirm (line 132) take a codeInput body, so both can be parked. Enrol runs requireEnrolmentSession and requireFreshFactor (exempt once the reset removed every factor); TOTP.BeginEnrol (totp.go:154) asks for a code only when a confirmed secret exists. Variant (a) therefore needs only a pre-reset MFA-complete cookie.
- `deploy/compose/docker-compose.yml:115`: The bundled Traefik router for the manager (labels at lines 115-119) declares no middleware, in particular no buffering middleware, so request bodies are streamed to the manager and the parked-body window applies behind the bundled proxy.

### Blockers

- The end-to-end result needs the real Postgres-backed stores: a ceremony surviving DeleteSecondFactors, InsertPasskey committing after the reset, and MarkSessionMFAComplete reporting 1 row for a revoked session. internal/db/testdb and internal/api/apitest start Postgres through testcontainers and the host Docker socket, which the approved sandbox forbids (--network none, no Docker socket). The API Deps use the concrete *auth.Sessions over gen.Queries, so there is no DB-free fake path through the handlers. No reproduction was run, and no artifact supports the claim.
- Whether a custom (non-bundled) reverse proxy in front of the manager buffers request bodies is a deployment fact not visible in source. The bundled compose Traefik router declares no buffering middleware, so this blocker concerns only other proxies. Buffering removes the parked-body widening of the window, but not the base race between handler entry and the reset commit.
