## 2. Security posture

Within this run's scope, Pulsix holds its main trust boundaries. Every run-3 record was revalidated: the fixes for backlog 7.49-7.62 hold on every traced path (bearer-minted machine enrollments, authenticated backup headers driving retention and `restore --list`, the restore re-checking for managers before the wipe and ending sessions, agent fact and check-tuple cardinality, the shared rule-evaluation budget, the compose enrollment snippet, IPv6 metadata ranges, and the both-quotes redaction case). The new features get the hard parts right: password-reset tokens are random, hashed, single-use and short-lived and revoke every session; instance-admin account actions require a fresh factor; the setup token is derived from the master key and checked in constant time after the already-completed check; worker-side repository reads go through `os.Root` and refuse links that leave the clone or enter `.git`; ansible-galaxy runs under the play uid and the worker takes over only a verified, bounded copy of what it wrote; worker-reported variable sources are bound to the job row's organization and repository; and certificate adoption after a restore is limited to the backup-to-restore window, with key continuity for agents.

Six records are confirmed, one medium and five low. The medium one is in the worker's git handling: a clone that already exists keeps fetching from its old origin after a repository URL changes, offering the current credential to the old remote and running content the organization moved away from. The low ones are a reset link that a mailbox holder can obtain right after an admin's second-factor reset, repository URLs whose embedded credentials are stored and shown to every reader, redaction gaps for YAML-quoted and URL-encoded secrets, a YAML number/string differential in the requirements source check, and a variable-sources report built in full before its size cap. Eight leads need a deployment fact, a database or an owner decision to settle; the most consequential are the release path (no `release` environment since the switch to the shared workflow, and that shared workflow calling its own actions from a mutable `@main`) and several per-agent and per-repository resource bounds on shared manager and worker capacity.

## 4. Confirmed findings in brief

### 4.1 Existing worker clones ignore a changed repository URL and keep fetching (with the current credential) from the old origin (medium)

- **Location:** `internal/repos/service.go:357` → `internal/worker/runner/gitrepo.go:231`
- **Lower-trust principal and conditions:** The worker already holds a clone of the repository from before the URL change (any earlier sync or run of that repository on that worker's data dir).; The repository URL has to be changed by an org admin (or by an instance admin for a shared definition). The party who benefits needs no Pulsix role: it is whoever controls, or later gains control of, the content or host at the old URL, for example an abandoned, compromised, mistyped or squatted source that the admin replaced.; Standard git semantics: 'git fetch origin' resolves the remote URL stored by 'git clone'. The verifier observed this with the git 2.47.3 shipped in noixdev/pulsix-worker:dev.; The credential-disclosure half applies only when the repository has a git_token and the old https host requests HTTP authentication, or when a git_key is used against an old ssh host while no pin for a different new ssh host is set (a pin seeds known_hosts for the new URL's host and StrictHostKeyChecking=yes then refuses the old host before authentication; a stale-clone worker never captures a new pin itself because ObservedGitHostKey looks up the new URL's host name). That half follows from the environment construction in source and was not observed against a live authenticating server.
- **Reproduction:** Controller of a repository source that an organization used to configure and has since replaced. The effect was observed through the worker's own git invocations in sandboxed harnesses. Source: confirm in internal/worker/runner/gitrepo.go:228-237 that the update path passes 'origin' rather than spec.URL to git, and that spec.URL reaches git only in the clone at line 250. Hunter harness: in the approved golang:1.27.1-alpine sandbox, run the runner-package tests TestAuditChangedRepoURLKeepsOldOrigin and TestH10FetchExistingCloneIgnoresClaimURL (fake git that logs argv and the GIT_ASKPASS answer). Check that the second fetch issues 'fetch --quiet -- origin main' with the new token answered by askpass, and that the new URL never reaches git. Real-git check: in the worker image, create two local bare repositories with different site.yml files. Clone A with fetchGit's clone argv, commit new content to A, then run fetchGit's update argv in the clone. Compare site.yml, remote.origin.url and HEAD with the tips of A and B.
- **Result:** Fake-git harnesses: the second FetchRepoDir ran 'fetch --quiet -- origin main' and 'reset --hard FETCH_HEAD' with GIT_ASKPASS answering the new token, and the claim URL never reached git (PASS; agents/h04-req-cache/artifacts/evidence.txt, agents/h10-runner/artifacts/evidence.txt). Real git 2.47.3 in the worker image: after the update with claim URL file:///tmp/bareB.git, site.yml contained 'NEW content pushed to OLD source A', remote.origin.url was still file:///tmp/bareA.git, and clone HEAD 54641d94 equalled A's tip, not B's 388ca8ad (agents/v07-req-cache/artifacts/evidence.txt).
- **Impact:** Playbooks from a source the organization removed run against its managed hosts with the org's machine credentials, and the repository's current git token or key can be offered to the old host. The UI shows the new URL, so the operator believes the change took effect.
- **Priority:** likelihood low (Requires a URL change on a repository that a worker already cloned, while the old source stays reachable and someone other than the organization controls it, or asks for credentials. URL changes are rare and the old source is often still the organization's own.); impact high.
- **Smallest fix:** On the update path, fetch from the claim's URL instead of the stored remote (or compare remote.origin.url with spec.URL and re-clone on a mismatch), so the credential, the pin check and the fetched content all go with the URL the manager currently has configured. Add a regression test where a second FetchRepoDir with a different URL hands that URL to git and never contacts the old one.
- **Fingerprint:** `internal/worker/runner/gitrepo.go:fetchGit:update-fetches-stale-origin`

### 4.2 Forgot-password issues a fresh reset link right after an admin's second-factor reset, so mailbox access alone takes over the account (low)

- **Location:** `internal/api/password_reset_handlers.go:87` → `internal/api/session_gates.go:239`
- **Lower-trust principal and conditions:** An instance admin reset the target's second factor without also setting a temporary password. This is the documented case of a person who lost their factor but whose password is considered certain.; The attacker can read the target's mailbox (the threat the code's lock-out comments name). No password or factor is needed.; Outbound mail is configured, so self-service forgot is available.; The attack must happen before the rightful owner signs in and enrols a new factor. The window has no expiry, and the 'second factor reset' notice mailed to the same mailbox announces it.
- **Reproduction:** Someone who holds the target's mailbox but is not signed in to Pulsix, acting after an instance admin reset the target's second factor. Copy the repository to scratch and add internal/accounts/audit_v02_factor_reset_test.go, which uses the package's existing newResetFixture and fakeStore. In the approved sandbox (network none, read-only root and source, uid 65532, 2 CPU, 2 GiB, 300 s), run: go test -count=1 -v -run 'TestAuditV02|TestLoginWithoutAFactorRequiresEnrolment' ./internal/accounts/ ./internal/auth/ Observe three things. After ResetSecondFactor, the forgot flow mails a new link and ResetPassword accepts it. With must-change pending, no link is mailed. A login on an account with no factor yields an enrolment-only session.
- **Result:** TestAuditV02ForgotAfterFactorReset/factor_reset_only PASS: 'factor reset: notice=sent actions=[delete second factors revoke sessions void reset tokens] mails=1', 'forgot after factor reset: link mailed, token length 43', 'RESULT: password set via fresh link after factor reset; setCalls=1 clearMustChange=true'. Contrast subtest PASS: 'CONTRAST: forgot with must-change pending mailed 0 link(s)'. TestLoginWithoutAFactorRequiresEnrolment PASS (MFARequired=false, EnrolmentRequired=true). The enrolment gate (session_gates.go:221-239) and ConfirmTOTP completing the session (mfa_handlers.go:141) are established from source only, because the API layer needs Postgres. Evidence: agents/v02-accounts/artifacts/evidence.txt.
- **Impact:** The attacker fully takes over the target account (its org memberships and roles, or instance-admin rights if the target is an instance admin), the owner is locked out, and the second-factor guarantee of the reset flow does not hold for that account. Only one account per admin action is affected, and the attack depends on a prior mailbox compromise.
- **Priority:** likelihood low (The attack needs three things at once: the mailbox is compromised, an admin reset the factor without a temporary password, and the attacker acts before the owner re-enrols. The spec tells admins to add a temporary password when the password is uncertain, which narrows this further.); impact medium.
- **Smallest fix:** Make the self-service forgot path issue no link while the account has no confirmed second factor, mirroring the must-change refusal. The admin's SendResetLink and temporary password stay as recovery paths. Read the factor state under the same row lock LockAccount already takes, using the has_second_factor expression ListAccounts already uses (accounts.sql:47-48). Regenerate sqlc, add HasSecondFactor to LockedAccount, map row.HasSecondFactor in SQLStore.LockAccount (internal/accounts/store_sql.go:140; without that mapping the field stays false and forgot would stop working for every account), and add it to the fake store. Add regression tests: after ResetSecondFactor, RequestReset issues no token and sends no mail; SendResetLink still works. This also closes the same gap for accounts that never enrolled a factor.
- **Fingerprint:** `internal/accounts/reset.go:requestReset:forgot-link-after-admin-second-factor-reset`

Regression tests: refusal of https://u:p@h/x, https://tok@h/x, ssh://u:p@h/x and u:p@h:x, acceptance of ssh://git@h/x and git@h:x; shared CreateRepo/UpdateRepo refuse the same; a viewer GET of a pre-existing userinfo row shows no secret.

### 4.4 Worker JSON-encodes the whole variable-sources report before applying the 8 MiB cap, so a ~66 KB repository drives a sync to gigabytes of memory (low)

- **Location:** `internal/worker/sync.go:158` → `internal/varsource/report.go:30`
- **Lower-trust principal and conditions:** The attacker can push to the synced branch of a git repository that an org admin configured in Pulsix. Repository content is lower trust than the org admin, and no Pulsix account is needed.; A sync of that repository runs: a webhook repo_sync trigger, a schedule, or an operator's manual sync.; The process dies only when the worker host or container has less memory than the encode needs. Measured: about 1.8 GB of process memory for 64 playbooks, linear in the playbook count, so several GB at a few hundred playbooks and tens of GB at the 1000 cap. Hosts with less memory than that lose the worker. Hosts with more see only a large memory and CPU spike.
- **Reproduction:** Repository writer who adds one role and a few dozen one-line playbooks to a repository that Pulsix syncs. Copy the source to scratch. Add internal/worker/zz_verify_encode_test.go, which writes the payload tree for N playbooks into t.TempDir() and drives SyncExecutor.Run with the package's fakeFetcher through the existing syncSources helper. It logs TotalAlloc and MemStats.Sys around the sync. Add internal/varsource/zz_verify_encode_test.go, which calls ParseRepo on the same tree (64 playbooks, testing/fstest.MapFS), logs the live heap after GC, then calls Encode(report, MaxReportBytes) and logs TotalAlloc and Sys. Run each in the approved sandbox (golang:1.27.1-alpine, --network none, --read-only, --cap-drop ALL, --user 65532, --memory 2g --memory-swap 2g, --cpus 2, 300 s): go test -count=1 -v -run '^TestAuditVerifyGrowth$' ./internal/worker/; then ^TestAuditVerifyFresh48$ and ^TestAuditVerifyFresh64$ each in a fresh container; then ^TestAuditVerifySplit$ ./internal/varsource/.
- **Result:** Through the real sync executor: 1 playbook (65 311-byte repository) allocated 45.9 MB. 16 playbooks allocated 0.80 GB, and 32 playbooks 1.58 GB (process memory 1.19 GB), all sending 1 playbook with incomplete=true. In a fresh process, 48 playbooks (66 627-byte repository) allocated 2.45 GB (process memory 1.46 GB). 64 playbooks ended with 'signal: killed' under the 2 GiB limit; the tmpfs build cache also counts toward that limit. Isolated: 64 playbooks parsed to 6 400 fields with a live heap of 7.7 MB. Encode then allocated 3.05 GB and raised process memory from 26 MB to 1.82 GB, while the sent report was 6.16 MB. Growth is linear in the playbook count. The 1000-playbook endpoint is extrapolated, not executed.
- **Impact:** The org's zone worker process dies from memory exhaustion (shown at 64 playbooks under a 2 GiB limit). Each sync of that commit repeats it until the repository is fixed or the sync is stopped, which blocks that zone's playbook runs. The worker has no memory limit in the shipped compose stack, so the spike also pressures the shared host. With the non-default embedded worker, the manager process is hit. No data exposure or integrity effect.
- **Priority:** likelihood medium (Needs only push access to a repository Pulsix already syncs (lower trust than the org admin) and a ~66 KB commit. Syncs run automatically on webhooks or schedules, and no Pulsix credentials are needed.); impact low.
- **Smallest fix:** Bound the encode. Size each playbook with its own json.Marshal (each is bounded by its walk caps), find the longest prefix whose summed size fits MaxReportBytes, and only marshal or binary-search reports built from that prefix. Optionally also track the running encoded size in ParseRepoInstalled and stop walking once it passes the cap, moving the rest to LeftOut with report_too_large, which also saves parse time. Regression test: the alias fixture with 1000 playbooks must keep Encode's TotalAlloc under a small multiple of MaxReportBytes plus one playbook, and must still return 1 playbook with incomplete=true.
- **Fingerprint:** `internal/varsource/report.go:Encode:full-marshal-before-size-cap`

### 4.5 Run-output redaction misses a secret printed through to_yaml/to_nice_yaml (single-quoted) or urlencode (low)

- **Lower-trust principal and conditions:** The claim secret is at least 4 characters long. For the YAML case it must contain a ' and need quoting under PyYAML: a leading indicator character, ': ' or ' #' inside, or leading/trailing space. A secret without a ' is still caught, because its quoted body equals the value. For the URL case it must contain any character that urlencode escapes, meaning anything other than ASCII letters, digits, _.-~ and /.; A play (written by an operator or taken from the repository) prints the secret through to_yaml, to_nice_yaml or urlencode, for example in a debug of a rendered config or in a module result holding a DSN, and an operator starts the run.; The reader is any org member with jobs.read (the viewer role) who is not otherwise entitled to read the secret.

Record the displayed msg strings. Copy the repository to scratch and add internal/worker/runner/zz_v08_audit_test.go (TestV08RedactorRealProducerSpellings). It builds newRedactor(&workerpb.Job{Redact: []string{"@Pa'ss!w0rd"}}) and calls eventPayload on a runner_on_ok Event whose event_data.res.msg and display stdout carry each recorded msg verbatim. Run in the approved offline sandbox: go test -count=1 -v -run TestV08 ./internal/worker/runner/ (golang:1.27.1-alpine, --network none, read-only source and module cache, cap-drop ALL, uid 65532, timeout 300 s).
- **Result:** The worker image's ansible-core 2.21.4 (PyYAML 6.0.3, Jinja2 3.1.6) printed '@Pa''ss!w0rd' for to_nice_yaml and to_yaml, and %40Pa%27ss%21w0rd for urlencode (evidence2.txt). With those exact strings, eventPayload redacted the control ('control [redacted]' in res.msg and stdout). For to_nice_yaml, to_yaml and urlencode, res.msg and stdout were forwarded with redacted=false and still held the secret's reversible spelling (evidence.txt). The scope check passed: a secret without a ' ('@Pass!w0rd') became '[redacted]' in its YAML-quoted form.
- **Impact:** Every viewer of the org's run logs sees the full credential or secret var. Both quoted forms are trivially reversible. The leak stays inside one org's lowest role; it does not cross tenants.
- **Priority:** likelihood low (The secret needs specific characters (a ' plus a YAML quoting trigger, or any URL-escaped character), and a play has to print it through to_yaml, to_nice_yaml or urlencode. Both are ordinary, but neither is the default output path.); impact medium.
- **Smallest fix:** In newRedactor, add the two reversible spellings to the base set, each with its JSON and nested-JSON forms. (1) The YAML single-quoted body strings.ReplaceAll(v, "'", "''"), added when v contains a '. (2) The percent-encoded bodies that the producers emit: Python urllib.parse.quote with safe='/' (Jinja2 urlencode on a string), which percent-encodes every byte except ASCII letters, digits, _.-~ and / with uppercase hex; and url.QueryEscape (urlencode on a dict or for_qs: safe='', space written as '+'). Add only the spellings that differ from v. Add regression tests that mirror TestRedactsPythonReprSpellings for '@Pa'ss!w0rd' in the to_nice_yaml, to_yaml and urlencode display forms above. Optionally record the remaining YAML gaps (double-quoted escapes for non-printable characters, folded long scalars) in the backlog.
- **Fingerprint:** `internal/worker/runner/redact.go:newRedactor:yaml-single-quote-and-urlencode-spellings`

### 4.6 Requirements source check skips plain scalars that yaml.v3 types as numbers but ansible-galaxy reads as path strings (low)

- **Location:** `internal/worker/sync_requirements.go:91` → `internal/worker/runner/galaxy.go:168`
- **Lower-trust principal and conditions:** The attacker can commit to a repository that an org admin configured in Pulsix (repository-content author). ## 6. Hardening notes and positive patterns

Hardening notes are not findings: each describes a missing defence-in-depth layer or a risk with no demonstrated boundary violation. They are grouped by the coverage unit whose hunter raised them.

**CI and release workflows of a public repository — Secrets and write tokens reachable from fork pull requests and dispatch inputs**
- announce.yml:40-43 uses the derived heredoc delimiter BODY_EOF_${GITHUB_RUN_ID} for multi-line GITHUB_OUTPUT. Generate a random delimiter (for example from /dev/urandom) so a release body can never close the block and set extra step outputs such as url.
- announce.yml:53 and the shared release workflow forward the release body (a changelog built from merged commit subjects, which public-repo contributors can author) to Discord. Whether the shared announce-release action suppresses @everyone/@here and role mentions (allowed_mentions) is not visible in source.
- dependabot.yml:5-12 groups every github-actions update under the pattern '*', which includes the NoiXdev/github-workflows pins that receive secrets: inherit (release.yml:86) and the Discord webhook (announce.yml:49). Exclude those pins from the group, or review them separately, so a routine weekly bump cannot move secret-receiving code unnoticed.
- release.yml:101 still uses secrets: inherit. The 7.16 follow-up (declare the needed secrets under workflow_call.secrets and pass only those) remains open.
- docs/BACKLOG.md:587 says 'The `release` environment and the guard stay as they are', but release.yml has not declared the environment since 38098bdb, so the environment protects nothing now. Correct the record.
- The release.yml guard query (release.yml:71) filters on branch=main, which is the run's head_branch, and that also matches a push of a tag named 'main' for the same SHA. The commit is the same, so no untested code passes. Adding a check that the run's head_branch came from a branch push, or a ruleset forbidding a 'main' tag, would remove the ambiguity.
- release.yml has no concurrency group, so two dispatches can race on version computation and the version commit to main. This affects integrity of the release metadata only.
- deploy/worker/Dockerfile:62-69 installs apt packages unpinned and pip packages by version without --require-hashes. Both come from signed or registry sources with no lower-trust writer, so this is a reproducibility gap, not a finding.

**Restore and worker re-enrolment commands — Restore refusal while managers run and replaced worker identity**
- internal/backup/storage_dir.go:42-43 dirStorage.Put opens <name>.pxbak.partial with O_CREATE|O_TRUNC|O_WRONLY but without O_NOFOLLOW or O_EXCL, while CleanPartials (storage_dir.go:180-207) deliberately skips symlinks. A backup-folder writer can pre-plant a symlink at the predictable next name (ObjectName of the second the attempt starts, run.go:31-32) so the manager truncates and writes the encrypted backup into the symlink target, and os.Rename then publishes the symlink itself, which List ignores (backup silently missing while the attempt is recorded succeeded). In the shipped distroless image the manager uid can write little of value outside the volume, so no boundary result; fix by opening with O_CREATE|O_EXCL|O_NOFOLLOW (removing a stale regular partial first, as CleanPartials already does) and fstat-checking the result.
- internal/backup/storage_dir.go:118-170 and internal/backup/storage_s3.go:183-209 have no cap on how many entries a listing describes, and ReadHeader (format.go:160-176) reads the up-to-4 KiB header one byte per read syscall on an unbuffered *os.File. prune runs this under advisory lock 8313 on the ticker goroutine (ticker.go:128-170), so a storage writer flooding the destination slows every scheduled tick and the admin backup routes. Bound the listing (entry cap or deadline in prune) and wrap the file in a bufio.Reader limited to maxHeaderLen+len(magic).
- internal/app/restorecmd.go:309-334 restore --list shows no Verified/authentic marker and backup.Restore (restore.go:76-109) does not compare the object name the operator selected with the authenticated manifest header. A storage writer can present an older authentic backup under a newer-looking name; the CREATED column and the post-restore summary still show the true date, and deleting newer backups already gives that writer a similar rollback, so this is operator-facing hardening: print Verified in --list and warn when name != ObjectName(m.Header.CreatedAt, m.Header.Kind).
- internal/backup/restore.go:92-96 rechecks for managers only before the wipe; nothing re-runs noManagerConnected inside the load transaction. A manager started after that check (against the documented procedure) can, under READ COMMITTED, have a setup completion whose AdminExists check ran before the load commit block on the SHARE lock and insert an extra instance admin right after the load commits (setup token required). Re-running BeforeWipe inside load() after the LOCK, or locking out manager connections (e.g. REVOKE CONNECT / pg_terminate_backend of pulsix-manager sessions) for the duration, would close it.
- internal/app/managers.go:21-34 recognises only application_name pulsix-manager; RunWorkerAdd (internal/app/workeradd.go:102-113) opens the database with db.Open without an application_name and runs Migrate and CA Ensure, so a concurrently running worker add (e.g. compose worker-enroll left up while only the manager was stopped) is not detected and can make the load fail with a misleading 'database is now empty' message. Stamp worker add sessions with a recognised name.
- internal/backup/restore.go:317-326 ends sessions only; password_reset_tokens used after the snapshot become unused again (bounded by their 60-minute expiry) and are not named in restoreNextStep. Deleting password_reset_tokens and webauthn_ceremonies in endSessions would make the restore's sign-out complete at no cost.

**NoiXdev/github-workflows create_docker_changelog_version_release.yaml and actions/announce-release at the pinned commit f7196176 — Reusable workflow receiving secrets: inherit and contents: write from Pulsix releases and the Discord announce**
- The shared docker workflow declares no `workflow_call.secrets`, so release.yml must pass `secrets: inherit`, exposing every organization secret available to NoiXdev/pulsix to the called workflow; declaring DOCKERHUB_USERNAME, DOCKERHUB_TOKEN and DISCORD_WEBHOOK_RELEASE_NOTIFICATION explicitly would let the caller pass only those.
- github-workflows@f7196176 create_docker_changelog_version_release.yaml:216-223 checks out with the default persist-credentials, leaving the contents: write GITHUB_TOKEN in the workspace git config for every later step (TriPSs/conventional-changelog-action, docker build steps). Those are SHA-pinned, so this is least-privilege hardening; set persist-credentials: false and authenticate only the final git push.
- Released images are not signed (no cosign/attestation signing) and Pulsix's compose/install path consumes them by tag; buildkit provenance (mode=max) and SBOM are attached but unsigned and not verified by any consumer. A registry-credential compromise therefore has no second integrity check on the consumer side.
- announce.yml:40-43 uses a predictable GITHUB_OUTPUT heredoc delimiter (BODY_EOF_<run id>) around release-body text derived from commit messages; a body line equal to the delimiter could only append further outputs of this read-only (contents: read) job that feed the Discord message. A random delimiter (e.g. from /dev/urandom) removes the ambiguity.
- Release notes built from commit subjects (including squash-merged external PR titles in the now-public repository) are posted to Discord verbatim; if the Discord action does not restrict allowed_mentions, text like @everyone in a merged commit subject would ping the channel. Low impact, notification only.
- Release authorization remains entirely in workflow code of the dispatching ref and the registry credentials are unscoped organization secrets (backlog 7.37, owner decision 2026-11-09 'won't do'); not re-reported, noted because it means any workflow run of the repository by a write-collaborator can reach DOCKERHUB_TOKEN regardless of release.yml's guard.

**Agent disk plugin mount points reported as check items — Whole-batch refusal of check results on one over-limit item**
- Service check unit names are reported verbatim as items (internal/agent/checks/service.go:90) without the agent's reportableItem filter, and internal/checks/definitions.go:171 only refuses blank names. A unit name with a control character or over 512 bytes, written by an org member with checks.write, makes every service batch of the bound hosts fail withinContract and ends their agent streams on every run. Validate unit names (and explicit mount names) against the item contract at definition write time, and filter them on the agent as disk.go does.
- Fact values are clipped to 512 bytes but never checked for valid UTF-8 or NUL, either by the collector (internal/agent/facts/facts.go:316-380) or by agents.RecordFacts. A host whose hostname, os-release or CPU model is not valid UTF-8 makes the agent's facts message impossible to marshal. A NUL would fail the jsonb UPDATE (Postgres refuses \u0000) and end the stream with Internal. Either way, every session dies at its first facts push. Only root or the infrastructure controls these sources, so this is a robustness gap, not a cross-boundary one. Apply strings.ToValidUTF8 and strip NUL or control characters in normalize.
- There is no per-agent rate limit on CheckResults messages. Each stream processes batches serially (up to 1000 observations, about 1.2 s of single-connection work each), and maxStreamsPerSerial = 2, so one agent can keep about two shared pool connections busy continuously. The cost scales with the number of compromised hosts.

**Agent enrollment and certificate renewal — Agent enroll token host binding and renew key binding**
- internal/api/trigger_handlers.go:166 and :224 (trigger create and rotate-secret) still accept a pxt_ bearer token; the secret fires only one pre-configured template run or repo sync that an operator token could already make persistent, so this is not a finding, but adding requireInteractiveSession (or documenting triggers as the intended automation exception next to backlog 7.49) would make 'credentials do not mint credentials' uniform.
- internal/agentapi/service.go:252 (agent Renew) signs whatever key the CSR carries, while internal/agents/adopt.go relies on 'an agent keeps its key across renewals' for post-restore adoption and the worker path enforces key continuity (internal/workers/enroll.go:193 sameKey). Because an agent renewal revokes the previous serial there is no extra persistence today, but checking that the CSR key equals the authenticating certificate's key would make the adoption assumption a server-enforced invariant and match the worker rule.
- internal/agents/store_adopt.go:29 resolves adoption by (org, agent_name), and for a bound-host enrollment the agent name is whatever the enrolling agent presents (internal/agentapi/service.go Enroll), so two hosts can share an agent name; after a restore both then fail adoption and must re-enroll. Using the host name for bound enrollments, or carrying the host id in the agent certificate, would remove the ambiguity (availability only; the key fingerprint check prevents cross-host adoption).
- internal/agentapi/registry.go and internal/grpcsrv/streams.go cut streams on revocation only in the manager process that handled the revocation, and TouchAgentBySerial (internal/db/queries/agents.sql:72) ignores zero affected rows. Single-manager today; before multi-manager HA (v0.6) a heartbeat that touches no row should end the stream so a revoked agent's stream on another manager does not continue.
- internal/grpcsrv/server.go:253 compares the RunEvents binding token with != rather than subtle.ConstantTimeCompare; the token is random, single use, 30 s TTL and needs an authenticated worker certificate, so this is hygiene only.
- internal/api/worker_snippets.go:47 and :71 put the enrollment token on the operator's command line as an environment prefix, so it lands in that operator's shell history; the token is single use with a 1 h TTL and history is readable only by the same account, so it is not a boundary issue, but a dialog hint (leading space / HISTCONTROL, or read -s) would keep unredeemed tokens out of history.

**AgentStream CheckResults messages from one authenticated host agent — Sustained check-result ingest from one organization's agents versus the instance-wide Postgres pool and check_samples hypertable shared by every tenant**
- ParseInline on a 512 KiB merge-key and alias document allocates about 234 MB in total (117-133 ms) before giving up with file_too_complex. Each POST/PUT of an editor playbook also re-parses the text in ValidateYAML and firstPlayName. Per-request work is bounded, but concurrent saves by an operator multiply the allocation. A cheaper pre-check (anchor/alias count) would cut it.
- Heartbeat-driven ResolveHost is bounded per serial (allowResolve, 10 s) and per serial stream count (2), and the bound survives reconnects (throttle_test.go). No gap remains there.
- check_samples has no uniqueness on (org_id, host_id, check_key, item, metric, at), so replaying the same sample many times is stored many times. A unique index or ON CONFLICT DO NOTHING would also make replays after reconnect idempotent.

**Monitoring and alerting REST CRUD handlers — Per-object scope and body-referenced child ids**
- internal/outbound/policy.go blockedRanges still protects IPv6 instance-metadata space with a hand-enumerated list of provider /64s inside fc00::/7, which is otherwise allowed. Every provider known from source is listed, and webhook responses are discarded. Consider an operator-extensible deny list (for example PULSIX_NOTIFY_DENY_CIDRS), or refusing fd00::/8 sub-ranges known to carry instance services, so a new provider does not need a code change.
- Webhook triggers with the GitHub or Gitea presets cannot use the timestamp window, because those senders do not sign '<ts>.<body>'. A captured signed delivery can then be replayed indefinitely, bounded only by the per-trigger rate limit. Optional deduplication on X-GitHub-Delivery or X-Gitea-Delivery would close it. This matches spec §3 and is not a contract breach.
- Notification delivery last_error (channels.read, operator) and the test-send response (channels.write, admin) carry the raw SMTP transport and reply text from internal/mail/smtp.go (for example 'dial <instance smtp host:port>', 'authenticate: <server reply>'). The invitation path (internal/api/authz.go mapTenancyErr, ErrInviteDelivery) deliberately keeps that text from org admins, because it names instance-owned SMTP hosts. Applying the same generic message to e-mail channel errors would make the two paths consistent.
- Webhook notification channels let an org admin send POST/PUT requests with chosen headers and body to any private-range host:port reachable from the manager, by design. Status-code and connection-error text in the delivery log act as a blind port and service oracle for the manager's network. Operators of multi-tenant instances should be told that PULSIX_NOTIFY_ALLOW_CIDRS cannot narrow private space.

**Organization creation and instance organization list — Who may create and list organizations**
- PUT /api/v1/admin/settings/smtp keeps the sealed SMTP password when the body omits it even if host or port change (internal/api/setup_handlers.go:129-144 keepStoredPassword); a second instance admin can point the host at a server with a valid certificate for its name and receive the password through AUTH PLAIN on POST /admin/settings/smtp/test. - The setup token is a fixed HKDF derivation of the master key and never rotates (internal/setup/token.go:29-37). It is printed in the manager log, the access log line for /setup?token= (internal/api/request_log.go only redacts /invite/ paths) and, outside source, any reverse-proxy access log, and the SPA leaves ?token= in the address bar and history (web/src/features/setup/SetupWizardPage.tsx:71-74). If AdminExists ever becomes false again (for example the empty database after an incomplete restore, see the run-3 note), any copy of that old token claims the instance. Consider moving the link to a fragment as for invites, stripping it with replaceState, redacting /setup?token= in the request log, and mixing a per-database nonce (or the restore marker) into the derivation, or refusing setup while a restore marker or incomplete-restore state exists.
- AcceptInvite's password-less-account branch (internal/tenancy/invites.go:159-164) sets the first password and display name without checking users.disabled_at. No current code path creates a password-less user row, so it is unreachable except through a direct DB edit or a restored dump; adding `AND disabled_at IS NULL` (or refusing a disabled account) would make the branch match the deactivation contract.
- The anonymous invite-accept form (web/src/features/members/InviteAcceptPage.tsx:153-207) does not show which address or organization the new account is created for, so a person handed someone else's unmailed link can set a password for an address they do not own; AcceptInvite on the server cannot prove mailbox ownership in the no-mail mode (design decision of backlog 7.10). Showing the invited address and org (via a peek endpoint keyed by the token) would make the binding visible to the person accepting.
- tenancy.Service.CreateOrg writes the org, the owner membership and the default-zone hook in separate statements (internal/tenancy/service.go:253-270); a failure between them leaves an organization without owner or zone that an instance admin must repair. Not a security boundary, but a transaction would remove the state.

**Instance-admin account management — Instance-admin authority over every account**
- API tokens (pxt_) survive SetTemporaryPassword, ResetSecondFactor, EndSessions, ChangePassword and ResetPassword (only deactivation revokes them; owner decision in docs/superpowers/specs/2026-11-04-settings-and-accounts-design.md). SetTemporaryPassword's comment calls it a lock-out of 'someone who may have the account', yet a token that intruder minted keeps org access at min(token role, membership). Consider revoking the account's tokens on the lock-out actions, or at least showing them on the admin account page.
- In-flight request window: CookieMiddleware resolves the principal before huma reads the body (BodyReadTimeout 5 s default, server has only ReadHeaderTimeout), and passkey register/finish (auth/passkey.go:216-238 AddCredential), TOTP enrol/confirm and recovery-code regeneration do not re-check the session inside their write. A request opened just before ResetSecondFactor/EndSessions can still add a credential after it; with a passkey that gives passwordless sign-in unless a temporary password was also set. Re-validate the session (revoked_at/expires_at) in the same transaction as the credential insert.
- ChangePassword (accounts/password.go) does not void outstanding reset links; ResetPassword, SetTemporaryPassword, ResetSecondFactor and Reactivate do. Low value against a mailbox holder (who can request a new one) but cheap consistency.
- MarkSessionMFAComplete's CTE (db/queries/auth.sql:48-55) selects the session without revoked_at/expires_at filters, so it returns a new cookie for a revoked session; harmless today because GetSession refuses it, but returning ErrNotFound would match its :execrows intent.
- Session cookie has no __Host- prefix; SameSite=Lax plus net/http CrossOriginProtection already block cross-origin and same-site sibling mutations, so this is defence in depth only.
- Instance admins can take over any account, including peer instance admins and accounts in organizations they are not members of, via temporary password plus second-factor reset (documented 'no peer protection'); only the best-effort notice mail and the audit entry reveal it.
