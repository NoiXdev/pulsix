# Needs validation

Prioritized leads without severity. Each names the exact fact that source and the local sandbox could not settle, and a bounded plan to settle it. Do not treat them as confirmed vulnerabilities, and do not test them against a live deployment.

## Release guard and registry credentials still sit only in workflow code that the triggering tag or branch supplies

Fingerprint `github-workflows/release.yml:registry-secrets-reachable-outside-release-guard`

Unchanged since run 2: `git log 4f9c7103..7ae1808 -- .github/workflows/release.yml .github/workflows/tag.yml` lists no commit. release.yml runs on any pushed tag matching v* (lines 9-12). On a push event GitHub runs the workflow file stored at the pushed commit, so both the guard job (lines 24-58: tagged commit must be an ancestor of origin/main, newest ci.yml run for the SHA must be green) and the release job come from a file the tag author chooses. The release job's only link to the guard is `needs: guard` (line 61). It binds no `environment:`, and no workflow under .github/workflows declares one. DOCKERHUB_USERNAME/DOCKERHUB_TOKEN (lines 118-119) and HARBOR_USERNAME/HARBOR_PASSWORD (lines 125-126) are therefore repository or organization secrets. GitHub hands those to any non-fork workflow run on any ref. A principal who can push a v* tag can point it at a commit whose release.yml drops the guard, then build and push noixdev/pulsix-manager and noixdev/pulsix-worker under the version tag and `latest` to Docker Hub and harbor.cloud.noidee.dev. The compose stack defaults every Pulsix image to `latest`: the x-manager-base anchor shared by manager and cli (deploy/compose/docker-compose.yml:15), worker-enroll (line 158) and worker (line 191). An installation that keeps the default would pull such an image into the manager, which holds the master key and DB URL, and into the worker. tag.yml (workflow_dispatch only at line 37, `contents: write` at line 46, `secrets: inherit` at line 61) can be dispatched from any branch carrying an edited copy, and the commit pin at line 60 binds only the copy that runs. Neither route adds a principal beyond 'can push a ref': any pushed branch workflow can name repository secrets directly. The guard is therefore not a security boundary against write users, only against mistakes. A secondary weakness applies even when a genuine main release.yml runs. Its CI query (lines 52-54) takes the newest ci.yml run for head_sha with no event or branch filter, and ci.yml also runs on pull_request (ci.yml:2). A pull_request run whose workflow definition comes from a writer-controlled base branch can therefore satisfy the guard for a main commit whose CI failed. Exploitability depends entirely on hosted facts. Local history has one author, noidee (all 1013 commits). Backlog 1.38 records five automatic tag.yml runs (Actions has run in this repository at some point), while backlog 7.17 says CI is disabled. Backlog 7.16 still lists 'registry secrets belong in a protected release environment' as open.

**Claimed root cause:** Release authorization is enforced only in workflow code that the triggering ref supplies: the guard job in release.yml, and tag.yml when it is dispatched from a branch. The registry push credentials are repository or organization secrets, not environment secrets behind a tag-only deployment rule or required reviewers. Any principal who can push a ref (a v* tag, or any branch carrying a workflow) can therefore reach them, and nothing outside attacker-editable YAML separates that principal from a release-authorized one. The guard's CI query also accepts a ci.yml run of any event type for the SHA.

### Trace

1. **entrypoint** `.github/workflows/release.yml:10` (on.push.tags "v*" (lines 9-12)): Any pushed tag matching v* starts the workflow. For push events GitHub runs the workflow definition stored at the tagged commit (GITHUB_SHA), so the tag author chooses which release.yml runs, including one without the guard job.
2. **propagation** `.github/workflows/release.yml:39` (jobs.guard (lines 24-58)): The on-main check (merge-base --is-ancestor, lines 34-42) and the CI-green check (lines 44-58) live in that same tag-supplied file. The CI query at line 53 filters only on workflow file and head_sha, with no event=push or branch=main filter.
3. **propagation** `.github/workflows/release.yml:61` (jobs.release.needs): The publish job's only gate is `needs: guard` in the same file. No `environment:` key is bound, so GitHub evaluates no deployment protection rule (tag pattern, reviewers) before giving the job secrets.
4. **propagation** `.github/workflows/tag.yml:37` (on.workflow_dispatch; permissions contents: write (line 46); jobs.tag secrets: inherit (line 61)): workflow_dispatch runs the tag.yml copy on whichever branch the dispatcher selects, with contents: write and every repository secret. The commit pin at line 60 protects only the copy that is dispatched. This is the same principal class as a tag pusher, not a new one.
5. **sink** `.github/workflows/release.yml:119` (jobs.release: Docker Hub/Harbor login (lines 115-126) and build-push (lines 128-156)): secrets.DOCKERHUB_TOKEN (line 119) and secrets.HARBOR_PASSWORD (line 126) are handed to a job with no environment. build-push-action then pushes the version tag and `latest` of pulsix-manager and pulsix-worker to Docker Hub and harbor.cloud.noidee.dev.

### Evidence

- `.github/workflows/release.yml:15`: The comment states the intended invariant: a tag is not evidence, a hand-pushed tag must not be trusted, and the thing that publishes does the checking. The check lives in the tag-supplied file, so it cannot hold against the tag pusher.

- `.github/workflows/tag.yml:61`: `secrets: inherit` remains, together with workflow_dispatch (line 37) and contents: write (line 46).
- `deploy/compose/docker-compose.yml:15`: The x-manager-base anchor (manager and cli) uses noixdev/pulsix-manager:${PULSIX_VERSION:-latest}. worker-enroll (line 158) and worker (line 191) default to latest too, so a pushed `latest` reaches installations that keep the default.
- `docs/BACKLOG.md:559`: Backlog 7.16 lists 'the registry secrets belong in a protected release environment (1.38)' as still open outside this repo, which confirms they are not environment-bound today.
- `docs/BACKLOG.md:96`: Backlog 1.38 records five failed automatic tag.yml runs, so Actions has executed in this repository at some point. Backlog 7.17 (line 560) says CI is disabled, so whether Actions is enabled now is an open hosted fact.

### Blockers

Each is a repository secret or an organization secret, and for an organization secret the repository access list matters. Source shows only that they are not environment secrets: no `environment:` key exists in any workflow.
- Hosted fact: whether any principal can push a branch or a v* tag, or dispatch workflows, without being authorized to cut releases. That means collaborators, teams, and GitHub Apps or bots with write or maintain access, plus any ruleset restricting refs/tags/v* creation. Local history has a single author (1013 commits by noidee). If every writer is a release manager, the bypass is same-principal and not a vulnerability.

- No safe local check: demonstrating secret release to a guardless tag-supplied workflow needs a real GitHub Actions run, and this audit may not contact GitHub or publish anything.

**Local plan:** No in-audit local reproduction exists, because GitHub Actions secret delivery cannot be emulated offline. Source checks already done: release.yml and tag.yml are unchanged since 4f9c7103; no workflow declares `environment:`; the guard query has no event or branch filter. ## One host agent can grow hosts.facts without bound, and every org-wide host read pays for it

Fingerprint `internal/agents/facts.go:RecordFacts:unbounded-fact-key-length-and-merged-key-cardinality`

The manager limits a facts push to 64 keys and each value to 512 bytes. It does not limit key length or key characters. Only the 16 MiB gRPC receive limit bounds key length. It also does not limit the number of distinct keys across pushes. The store merges with jsonb ||, which never removes a key. So one host agent identity (root on one compromised host) can loop on its own AgentStream. Each Facts message carries 64 new keys of about 256 KiB, roughly 16 MiB per message. This grows the agent's own hosts.facts until Postgres's jsonb size limit (about 255 MB) refuses the UPDATE. There is no per-stream message rate bound, and each push rewrites the whole growing jsonb value. The inflated document persists. No code path trims facts, so recovery needs operator action outside the product's facts path. ListAllHosts (SELECT * FROM hosts) reads the facts column and json-decodes every host's facts into map[string]any. It runs through checks.Service.ResolveHost/ResolveHosts/ResolveOrg → checksHostRoster.MonitoredHosts: on every heartbeat-driven resolve of every agent in the organization (at most once per 10 s per agent), on every rule evaluation's ContextForHost, on every inventory render, preview and job snapshot, and on several API and template paths. The paginated host list (ListHosts, also SELECT *) returns the document whenever that host is on the page. Inventory render also embeds the document as pulsix_facts when the host is in scope. One host's inflated document is therefore transferred and decoded many times per minute by the shared manager process and database. That load also lands on other tenants on the same instance. Locally observed so far: only the service layer and wire limits accept the input. Database growth and the cost of the reads are not observed.

**Claimed root cause:** Service.RecordFacts (internal/agents/facts.go:67-83) mirrors only part of the collector's normalization: the per-push key count and the value byte length. It omits key length, key charset and any aggregate bound on stored keys or document size. UpsertHostFacts (internal/db/queries/agents.sql:119-122) merges with jsonb || and keeps every key ever reported. There is no column CHECK on hosts.facts (internal/db/migrations/00010_hosts.sql:31). Hot org-wide paths read the full row (ListAllHosts SELECT *, internal/db/queries/hosts.sql:102) and decode it (internal/hosts/store_sql.go:246-252).

### Trace

1. **entrypoint** `internal/agentapi/stream.go:148` (Service.process): On the mTLS-authenticated AgentStream of one host agent, every Facts message goes to FactsSink.RecordFacts for that agent's own org and host. receiveMessages (stream.go:89-127) has no rate or count bound. The shared gRPC server allows messages up to 16 MiB (internal/grpcsrv/server.go:181, internal/pb/workerpb/limits.go:20).
2. **propagation** `internal/agents/facts.go:68` (Service.RecordFacts): Checks only len(facts)<=64, non-empty keys and len(value)<=512. Key length and the total across pushes are not checked.
3. **propagation** `internal/agents/store_sql.go:290` (SQLStore.RecordFacts): The map is json.Marshal'ed and passed whole to UpsertHostFacts in an org-scoped write transaction.
4. **propagation** `internal/db/queries/agents.sql:120` (UpsertHostFacts): facts = COALESCE(facts,'{}') || $facts merges the new keys, and keys missing from the push are kept forever. The only ceiling is Postgres's own jsonb size limit.
5. **propagation** `internal/app/checks_ports.go:87` (checksHostRoster.MonitoredHosts): Every checks ResolveHost/ResolveHosts/ResolveOrg (internal/checks/resolver.go:324,365,409) loads ListAllHosts for the organization, facts column included, only to collect monitored host IDs.
6. **sink** `internal/hosts/store_sql.go:249` (fromHostRow): Each host row's facts are json.Unmarshal'ed into map[string]any on every such read: heartbeat resolve, rule-evaluation context, inventory render and job snapshot, and the ListAllHosts API and template paths.

### Evidence

- `internal/agents/facts.go:75`: Values are the only thing whose size is checked. Keys have no length limit (constants at facts.go:28-37 define only MaxFactsKeys and MaxFactsValueLen).
- `internal/db/queries/agents.sql:120`: The jsonb || merge. The query comment (agents.sql:110-118) says every key the agent did not report survives untouched.
- `internal/db/migrations/00010_hosts.sql:31`: facts jsonb NOT NULL DEFAULT '{}' with no size CHECK.
- `internal/db/queries/hosts.sql:102`: ListAllHosts is SELECT * FROM hosts WHERE org_id = $1, so it includes facts and has no pagination.
- `internal/agentapi/stream.go:185`: Heartbeat-driven ResolveHost runs for every agent in the org, at most once per heartbeatResolveInterval = 10 s (internal/agentapi/registry.go:53). It goes through MonitoredHosts to ListAllHosts.
- `internal/inventory/renderer.go:135`: Every inventory render, including job snapshots, loads ListAllHosts. renderer.go:182 copies Facts into render.Host, and render.go:390-391 emits it as pulsix_facts for in-scope hosts.
- `internal/grpcsrv/server.go:181`: MaxRecvMsgSize = MaxWorkerToManagerBytes (16 MiB) also applies to AgentService, which is registered on the same server (server.go:196). It is the only bound on key length. Independent sandboxed check (agents/v03-agent-data/artifacts/evidence.txt): 3 Facts messages of 64 distinct 261,120-byte keys each marshal to 16,712,389 bytes, under the 16,777,216-byte limit. Service.RecordFacts accepted all of them, and 50,135,040 key bytes were forwarded to the store.

### Blockers

- PostgreSQL cannot run in the approved sandbox: testcontainers and internal/db/testdb are forbidden. So nothing below was observed. The growth of hosts.facts across pushes. The per-push rewrite, TOAST and WAL cost. The exact jsonb ceiling at which UPDATE fails. The bytes and decode time ListAllHosts spends per call with one inflated row. Locally observed: only that the wire limit and the service layer accept and forward 64 distinct keys of about 256 KiB per push (agents/v03-agent-data/artifacts/evidence.txt; also agents/h05-agent-data/artifacts/evidence2.txt).
- Whether the repeated read and decode measurably degrades the shared manager or database depends on deployment facts outside the repository: the manager container's memory limit, the database's I/O capacity and statement_timeout, and the number of agents and rules per organization.

**Local plan:** Use internal/db/testdb in a Postgres-capable environment. Create one org with two monitored hosts A and B. Call agents.SQLStore.RecordFacts on host A 4 times, each with 64 distinct keys of 200 KiB and value "v". After each call, query SELECT pg_column_size(facts), octet_length(facts::text) FROM hosts WHERE id = A. Assert that the size grows monotonically to about 50 MB and that hosts.SQLStore.ListAllHosts returns all 256 keys for host A. Then measure one checks.Service.ResolveHost for host B with runtime.MemStats TotalAlloc and wall time, before and after the inflation, and record the difference. Optionally keep pushing until the UPDATE fails, and record the Postgres error and size at that point to establish the ceiling. Dummy data only, no stress loop.

**Owner-observed check:** On an owner-controlled staging instance, give one test host an inflated facts document of about 50 MB, either through the store or with an UPDATE as the schema owner. Leave the org's other agents heartbeating and the rule ticker running for 10 minutes. Record manager RSS and GC CPU, database read and WAL bytes, and heartbeat-resolve latency. Compare them with the same window before the inflation and with the manager container's memory limit. Then remove the test keys with UPDATE hosts SET facts = '{}' and confirm recovery. No production instance, no saturation test.

## Compose worker snippet writes the live enrollment token into a compose file with default permissions

Fingerprint `internal/api/worker_snippets.go:workerSnippets:enroll-token-inline-in-compose-file`

When an org member with workers.write creates a worker enrollment (POST /api/v1/orgs/{org}/worker-enrollments), the API returns the token plus a docker run snippet and a compose snippet (worker_handlers.go:232). Fix b6a8c56 (backlog 7.39) moved the docker run snippet's token out of the docker client's argv and into its environment. The compose snippet was left as it was: it still inlines the live, single-use worker enrollment token (pxw1 format) as a quoted YAML scalar (`PULSIX_ENROLL_TOKEN: "pxw1...."`, worker_snippets.go:53). The backlog row for 7.39 itself says 'The compose snippet still writes the token into the compose file, whose permissions are the operator's', so this residual is known but has not been fixed. The Add worker dialog offers the compose snippet with a copy button (AddWorkerDialog.tsx:86). Its only note is 'Token valid for one hour, single use ... shown only now' (workers.ts:55-56), with nothing about the file's permissions. To use the snippet, the admin saves it to a file on the worker host. That file's mode comes from the admin's umask (commonly 0644) and from where it is saved. The token stays redeemable until the worker first calls Enroll or the one-hour TTL runs out (EnrollmentTTL, enroll.go:23). Enroll is the one worker RPC that needs no client certificate, and it is rate limited only per client address (grpcsrv/enroll.go:21-33). Redemption checks only the secret hash, that the token is unused and that it has not expired (enroll.go:153). It then signs any CSR for the enrollment's org, zone and name (enroll.go:156) and marks the token used in the same transaction. A local account on the worker host can do this if it can read the file, cannot otherwise control docker (not root, not in the docker group) and can reach the manager's worker endpoint. That account can redeem the token first and receive an authenticated org+zone worker certificate. The genuine worker is then refused. The rogue identity can claim that zone's jobs, and the decrypted credentials they carry, until an admin notices the failed worker and revokes it. After redemption, the copy left in the file is inert: the worker ignores the token once a bundle exists (internal/worker/enroll.go:46-47), and the token is single use. Source establishes the code path completely. Whether a lower-trust reader can reach the file depends on where the admin saves it, the file and directory modes, and whether the host has such accounts. None of these is visible in source.

**Claimed root cause:** workerSnippets (internal/api/worker_snippets.go:53) renders the pre-redemption secret into the compose YAML as `PULSIX_ENROLL_TOKEN: %q`. Persisting the snippet as a compose file therefore persists the secret in a file whose access control the product neither sets nor advises. The docker run variant was moved to an owner-only channel (worker_snippets.go:31-39, backlog 7.39), but this one was not. The token is also not bound to anything only the intended host holds, so whoever reads it first wins. Possible fixes: render `PULSIX_ENROLL_TOKEN: ${PULSIX_ENROLL_TOKEN}` (compose interpolation from the invoking shell's environment, matching the docker variant), or reference an env_file the dialog tells the admin to create with mode 0600, and add a dialog or doc note on file permissions.

### Trace

1. **entrypoint** `internal/api/worker_handlers.go:212` (POST /api/v1/orgs/{org}/worker-enrollments): An org member with PermWorkersWrite creates a one-time worker enrollment token. The handler gets the token from CreateEnrollment (line 225) and passes it to workerSnippets (line 232), which returns it in compose_snippet.
2. **propagation** `internal/api/worker_snippets.go:53` (workerSnippets): The compose snippet embeds the full token as a quoted YAML scalar (`PULSIX_ENROLL_TOKEN: %q`). The docker snippet instead takes the value from the client's environment (lines 36 and 39).
3. **propagation** `web/src/features/workers/AddWorkerDialog.tsx:86` (AddWorkerDialog compose tab copy button): The dialog renders the compose snippet with the token inline (lines 53 and 83) and offers a copy button. Its note (workers.ts:55-56) gives no guidance on the permissions of the file the admin saves on the worker host before running docker compose up.
4. **sink** `internal/workers/enroll.go:153` (Service.Enroll): Redemption checks only the secret hash, that the token is unused and that it has not expired. Whoever presents the token first gets a CSR signed for the enrollment's org, zone and worker name (line 156), and the token is marked used in the same transaction. The anonymous gRPC Enroll (grpcsrv/enroll.go:29) reaches this with only a per-address rate limit.

### Evidence

- `internal/api/worker_snippets.go:53`: fmt.Sprintf("      PULSIX_ENROLL_TOKEN: %q", token): the literal secret goes into the compose file content.
- `internal/api/worker_snippets.go:31`: The backlog 7.39 fix comment covers only docker run ('The token reaches docker run as its environment ... the environment only for the client's own user and root'). The compose variant is unchanged.
- `docs/BACKLOG.md:589`: Backlog 7.39 is marked done but states 'The compose snippet still writes the token into the compose file, whose permissions are the operator's': the residual is acknowledged and was not fixed.
- `internal/workers/enroll.go:23`: EnrollmentTTL = time.Hour: a token saved in the file stays redeemable for up to an hour if the worker does not redeem it first.
- `internal/grpcsrv/enroll.go:29`: Enroll is the one worker RPC callable without a client certificate. It is rate limited only per client address (lines 21-33).
- `web/src/i18n/en/workers.ts:55`: The dialog's tokenNote says only 'Token valid for one hour, single use ... shown only now'. It gives no instruction to keep the compose file owner-only.
- `internal/worker/enroll.go:46`: Once a usable bundle exists, PULSIX_ENROLL_TOKEN is ignored, so the exposure window is from saving the file until the first successful Enroll or the TTL. After that the copy left in the file is inert.

### Blockers

- Where admins save the compose snippet on a worker host, and that file's mode and its parent directories' traversal permissions, are deployment facts. Source does not set them.
- Whether supported worker hosts have local accounts that are not root, not in the docker group and not the admin, can read the file and can reach the manager's worker gRPC endpoint is a deployment fact. Without such an account, no trust boundary is crossed.
- The real window between saving the file and the container's first Enroll depends on image pull time and on the admin's workflow, and source cannot show it. The approved sandbox cannot create OS accounts or simulate a multi-user host.

**Local plan:** On a disposable Linux VM with no network beyond a local dummy registry, create an admin account in the docker group with default umask 022, and an unprivileged account 'probe' that is not in the docker group. As the admin, save a compose file with the exact shape workerSnippets renders, using the dummy token value pxw1.DUMMY. Save it to typical locations: /opt/pulsix-worker/compose.yml (created with sudo mkdir, default 0755) and ~/pulsix-worker/compose.yml, leaving the distro's default home-directory mode. As 'probe', run only `grep -c pxw1.DUMMY <file>` against each path. Record `stat -c '%a %U' <file>` for each file and its parent directories, together with the grep result. Redeem nothing, contact no manager, and destroy the VM afterwards.

**Owner-observed check:** Have the owner confirm whether supported worker hosts are single-admin machines or shared hosts with other local accounts, and in which directory and with which umask admins normally save the compose snippet. If shared hosts are supported, inspect one compose file created from the dialog with `stat -c '%a %U' <file>` and check its parent directories' modes, without reading or using any live token.

## Restore checks for a running manager only once, before the confirmation and verification, and nothing holds that state through the wipe and load

Fingerprint `internal/app/restorecmd.go:RunRestore:manager-check-not-held-through-wipe-and-load`

RunRestore refuses while a session named pulsix-manager is connected, but it checks only once (restorecmd.go:97). The check runs before the interactive confirmation (which can wait indefinitely), the stdin spool and the full Verify pass over the backup. Nothing is held afterwards. Managers take no lock that restore could take exclusively. wipe does not re-check. The load transaction does not assert that the freshly migrated tables are empty before COPY. For a backup at the binary's schema version, the version re-checks (restore.go:113 and :239) cannot see a manager either.

Source narrows the two claimed outcomes.

A manager started after the wipe runs Migrate and then caInst.Ensure (app.go:203, :449). Ensure inserts the singleton instance_ca row (id=1 CHECK, 00016_ca.sql:5). COPY of the backup's CA row then fails on the primary key and the load rolls back. Restore reports ErrRestoreIncomplete, and a later run is refused by the manager check. In the meantime the manager serves an empty instance whose public first-run setup is open. That is the documented fresh-install posture, during an operator-caused window. It is not a merge.

A merge of foreign rows into the restored database is possible only for a manager started after the check but before the wipe (for example during the confirmation prompt or a long Verify). Such a manager does not run Ensure again. Between MigrateTo's commit and the moment the load transaction locks org_memberships (ALTER ... NO FORCE, forced RLS per 00002_rls.sql:17) and users (FK drop on the referenced table), it serves empty tables. An anonymous caller's setup Complete can create an instance admin, an org and a membership with fresh UUIDv7 ids and a distinct email and slug. If that setup transaction commits inside the window, COPY appends the backup's rows beside it and the restore commits with the attacker's instance admin.

The whole setup request has to fit inside that window: the pre-check, the argon2id hash, then the in-transaction AdminExists re-check under pg_advisory_xact_lock and the inserts. A setup whose re-check runs after the load has locked users blocks, then sees the restored admin and is refused (service.go:289). A setup that interleaves with the load's locks deadlocks with it.

worker-enroll opens the owner URL without an application_name and runs Migrate (workeradd.go:103,108), so it is never counted. In the compose stack, though, it depends_on the manager (docker-compose.yml:162), its Migrate is serialized by advisory lock 7256 and gives the same schema, and it writes nothing until a zone exists. That makes it a detection gap with no separate impact. The cli service does not depend on the manager (docker-compose.yml:132), so the restore command itself starts no manager.

All of this requires an operator (or an orchestrator) to start a manager while a restore is running, against the restore's own instruction. An anonymous caller cannot cause that. Likelihood is therefore low, and the high-impact outcome (an extra instance admin in the restored database) also depends on a narrow timing window.

**Claimed root cause:** The manager-detection control is a single point-in-time pg_stat_activity count (internal/app/managers.go:24) evaluated once at internal/app/restorecmd.go:97. It is not repeated immediately before the wipe, and it is not backed by a lock every manager holds for its lifetime (the alternative the spec names). load() (internal/backup/restore.go:169) never asserts that the target tables are empty before COPY. So rows written by a manager that started between the check and the wipe can pass every later check when the backup's schema version equals the binary's.

### Trace

1. **entrypoint** `internal/app/restorecmd.go:97` (RunRestore): ManagersConnected is evaluated once, on the operator-run CLI restore; a manager that starts after this point is never detected.
2. **propagation** `internal/app/restorecmd.go:106` (RunRestore): confirmReplace can block indefinitely on a terminal prompt, and openSource (line 111) spools stdin. Both run after the only manager check.
3. **propagation** `internal/backup/restore.go:64` (Restore): verifyFrom reads and decrypts the whole backup before the wipe, still with no manager re-check.
4. **propagation** `internal/backup/restore.go:80` (Restore): wipe commits an empty public schema in its own transaction without re-checking for managers. A manager that started after the check keeps running against it.
5. **propagation** `internal/backup/restore.go:113` (migrateAndLoad): The only later concurrency check compares the schema version with the backup's. It passes when the backup's version equals the binary's, even if a manager is serving.

## Restore silently reactivates sessions, API tokens and worker or agent certificates revoked after the backup was taken

Fingerprint `internal/backup/restore.go:load:post-snapshot-revocations-reactivated`

A backup is a full snapshot of every public table except, optionally, check_samples (dump.go:79). That covers sessions, api_tokens, worker_certificates, agent_certificates, workers, org memberships and users, with their revoked_at, status and disabled_at columns. Restore wipes the live database without reading it and COPYs the snapshot rows back as they were. The only reconciliation after the load marks running backup attempts abandoned. The authentication lookups decide only from those restored columns: GetAPITokenByHash (tokens.sql:18), GetSession (auth.sql:10-18) and the gRPC serial lookups (grpcsrv/auth.go:203). So any credential revoked between the snapshot and the restore works again after the restore. That covers an API token (expires_at may be NULL, so it never expires), a revoked worker certificate, an agent certificate superseded and revoked by a renewal (valid up to 90 days), a disabled user, a removed membership and an old password. A revoked session also works again, but only until its original absolute expiry (SessionTTL 12 h, auth/session.go:21), so it matters only for a restore soon after the snapshot. The holder of the revoked credential cannot trigger this. It needs the instance operator, who holds the master key and the owner database URL, to choose a backup older than the revocation. The likely trigger is incident response: credentials are revoked, then a pre-incident backup is restored to undo the damage. Nothing warns about this. The README promises a revoked worker certificate 'stops working at once' (deploy/compose/README.md:88,191). The CLI restore output, the README restore section, the design spec and the end-user backups page (noix-docs branch origin/pulsix, src/content/docs/pulsix/admin/backups.md) mention only certificates renewed after the backup. Yet the same feature's `worker add --replace` and worker-enroll refuse to re-enroll a revoked worker because that 'would undo the revocation'. Backlog 7.47 also says that accepting a stolen but superseded certificate after a restore needs a security decision. Calibration: every full-snapshot database restore in comparable products rolls back credential state in the same way. Whether Pulsix accepts that rollback as part of its restore contract is not stated anywhere in source or docs.

**Claimed root cause:** load() (internal/backup/restore.go:169-247) treats the snapshot as the whole truth for credential and authorization state. Before the wipe it never reads which credentials the replaced database had revoked. After the load it has no step that carries those revocations forward (by token hash, serial or session id), invalidates the restored sessions, or lists the reactivated credentials for the operator. The CLI does not surface the gap either: restoreNextStep (internal/app/restorecmd.go:66) and the docs cover only certificates renewed after the backup.

### Trace

1. **entrypoint** `internal/app/restorecmd.go:120` (RunRestore): The instance operator (compose cli service: master key and owner database URL) restores a backup older than a later revocation, replacing the database with --replace and confirmation.
2. **propagation** `internal/backup/dump.go:79` (Dump): Dump skips only check_samples (when metrics are excluded), so the snapshot holds sessions, api_tokens, worker_certificates, agent_certificates, workers, memberships and users with their revocation columns as of the snapshot.
3. **propagation** `internal/backup/restore.go:80` (Restore): wipe() drops the live database, which holds the post-snapshot revocations, without reading or recording them.
4. **propagation** `internal/backup/restore.go:274` (copyTables): Rows are COPYed back verbatim, so revoked_at, status and disabled_at return to their snapshot values (NULL or active).
5. **propagation** `internal/backup/restore.go:232` (load): The only reconciliation after the load is abandonRunningAttempts on backup_runs. Nothing touches credentials, sessions or memberships before Commit.
6. **sink** `internal/db/queries/tokens.sql:18` (GetAPITokenByHash): API token authentication accepts any token whose revoked_at IS NULL and whose expires_at is NULL or in the future, so a token revoked after the snapshot authenticates again. GetSession (auth.sql:18) and the worker and agent serial lookups (workers.sql:12, agents.sql:101, used by grpcsrv/auth.go:203) decide the same way from the restored columns.

### Evidence

- `deploy/compose/README.md:88`: Stated revocation contract: 'A revoked worker's certificate stops working at once' (also line 191: 'cuts it off at once'). Nothing qualifies it for a restore.
- `internal/app/workerreplace.go:28`: The same feature's stated policy: 'A revoked worker is left alone: replacing it would undo the revocation.'

### Blockers

## One host agent can persist unbounded check tuples that every evaluation of that host re-reads

Fingerprint `internal/checks/samples.go:RecordObservations:unbounded-per-host-tuple-cardinality`

Check results are bounded per message: 1000 observations, each check_key at most 64 bytes, item at most 512 and metric at most 64, with no control characters. Nothing bounds the total number of distinct (check_key, item, metric) tuples one host can accumulate. check_key is never checked against a check definition, so arbitrary keys are stored. Each accepted observation upserts one check_current row for the agent's own host and marks that host dirty. check_current rows are never deleted while the host exists. At every rule evaluation, the host's distinct non-empty (check_key, item) pairs are inserted into check_items, which is also never pruned. The principal is the host agent identity (mTLS, bound to one host), which any org operator can create by enrolling an agent (PermAgentsWrite = RoleOperator). It can grow its host's tuple set by 1000 per message, with no per-stream rate bound and no aggregate quota. The rule ticker is shared across orgs: it runs every 15 s, takes up to 200 dirty or due hosts ordered by next_due_at, and evaluates them one after another under one batch deadline of max(4x interval, 10 s) = 60 s. Each evaluation of the inflated host reads all of its check_current rows (ListCheckCurrent, no LIMIT) and passes all distinct items to Discover in one unnest INSERT. The org-wide GET /api/v1/orgs/{org}/items endpoint returns every check_items row of the org, with no pagination, plus two correlated check_current subqueries per row. Rows stay inside the attacker's own org under RLS, so no data crosses tenants. The open question is availability. A host whose evaluation keeps overrunning the batch deadline is rolled back and keeps its old next_due_at. It may then sort first in every tick and use up each batch's deadline, delaying evaluation of other orgs' hosts on a single-manager instance. Whether that happens depends on database cost at large tuple counts, which was not observed. Recovery: deleting the host cascades its check_current and check_items rows. Revoking the agent stops further growth.

**Claimed root cause:** Service.RecordObservations (internal/checks/samples.go:274-289) enforces only the 1000-observation batch bound and the per-string bounds in withinContract (samples.go:176-193). It deliberately never resolves check_key against check_definitions (samples.go:19-23) and never caps the distinct tuples per host. SQLStore.RecordObservations (internal/checks/store_sql.go:251, upsert at :332) adds one check_current row per new tuple. check_current is documented as never pruned (internal/db/migrations/00044_check_samples.sql:60-66), and neither is check_items (internal/db/queries/items.sql:34-37). ## One tenant's window-heavy rule can starve the instance-wide rule evaluation ticker

Fingerprint `internal/rules/window_sql.go:windowStatement:unbounded-per-host-window-fanout-starves-shared-eval-ticker`

An operator of organization A (PermChecksWrite) can save one org-scope expression rule of under 4 KiB that names over a hundred distinct window aggregates of up to 24 h each (e.g. `max(disk.used_pct,1440m)>0 or rate(disk.free_bytes,1439m)>0 or ...`). For every reported item of every host of A, on every dirty/due evaluation, the shared evaluation ticker then runs one window statement holding (items x ~123) LATERAL aggregates over up to 24 h of raw check_samples each (a DB-free harness measured 123 distinct window keys from a 4085-byte rule, so 2460 requests and a 21.2 M-row upper bound for a host with 20 disk items at the 10 s minimum interval). The tenant also controls how many items and samples its own hosts report: ingest caps only 1000 observations per batch and 512-byte item names, with no per-host distinct-item cap, no per-tuple sample rate and no stream rate limit, so the row count per window is not bounded by the check interval either. The ticker is one sequential loop per manager (app.go:664) that claims up to 200 hosts of all organizations ordered only by next_due_at and gives the whole batch one 60 s deadline. A host whose evaluation outlives that deadline is rolled back with its cursor untouched, keeps the oldest next_due_at and heads every following claim. In a single-manager deployment (the default compose stack) that would stop rule evaluation for every other organization, and with it the opening and resolving of their alerts and the notifications those state changes produce (escalation of alerts that are already open runs in the separate alert follower loop and continues). Cheaper but still expensive hosts take a disproportionate share of each batch's 60 s, which delays everyone else's evaluations. Both effects keep the shared Postgres busy with A's aggregates. Whether one host's statement actually exceeds 60 s on TimescaleDB is not measured.

**Claimed root cause:** Per-host evaluation cost has no budget. The rule language bounds expression bytes (4096), window length (24 h) and nesting, but not the number of distinct window aggregates per rule. Nothing bounds the rows a host's window statement scans: no statement_timeout, no per-host item cap, and no per-tuple sample rate at ingest. The cross-tenant ticker has no per-organization fairness, no per-host time budget separate from the 60 s batch deadline, and no back-off that moves a repeatedly cut-off host behind other organizations' hosts.

### Trace

1. **entrypoint** `internal/api/rule_handlers.go:481` (POST /api/v1/orgs/{org}/rules (requireOrg PermChecksWrite = operator)): An operator of organization A creates an org-scope expression rule; requireOrg only checks checks.write, and Check/Create run the same validation.
2. **propagation** `internal/rules/service.go:209` (Service.buildRule): The only size bound on the expression is len <= 4096 bytes. Parse/TypeCheck accept any number of window calls with distinct lengths in [1m, 24h] (catalog.go:57, check at catalog.go:247).
3. **propagation** `internal/rules/evaluate.go:192` (WindowRequests): For each reported, non-ignored item judged by the winning rule, every distinct WindowKey of the tree becomes one WindowRequest; deduplication is only per (item, metric, agg, seconds).
4. **propagation** `internal/rules/ticker.go:349` (Ticker.evaluate): All window requests for the host are fetched in one statement inside the host's claim transaction, under the shared batch context created at ticker.go:275.
5. **propagation** `internal/rules/window_sql.go:133` (EvalSQLStore.Windows / windowStatement): windowStatement unnests all requests and runs a LATERAL count/avg/min/max/first/last over check_samples for each, for every sample at or after now minus the window (there is no upper time bound in the statement). It has no row or time limit of its own, and no statement_timeout is configured anywhere in the repository.
6. **propagation** `internal/rules/due_sql.go:147` (EvalSQLStore.ProcessDue): Hosts of every organization are evaluated sequentially. Once the batch deadline fires, the loop stops and leaves every remaining host for the next tick; the cut-off host's transaction is rolled back (evaluateOne, due_sql.go:202) with its cursor untouched.
7. **sink** `internal/db/queries/rules.sql:149` (ClaimDueEvalCursors): The next claim orders all organizations' cursors by next_due_at only, with no org filter or fairness, so A's cut-off host (oldest next_due_at) is first again and consumes the next batch. That delays or blocks other organizations' evaluations and alerts.

### Evidence

- `internal/rules/service.go:36`: maxExpressionBytes = 4096 is the only size bound on an expression; nothing limits the number of window calls.
- `internal/rules/catalog.go:57`: MaxWindow = 24h: each window may span a full day of raw samples.
- `internal/checks/definitions.go:67`: minInterval = 10s: a legitimate agent produces up to 8640 samples per tuple per 24 h window.
- `internal/checks/samples.go:274`: RecordObservations bounds only one batch (MaxObservationsPerBatch = 1000 at line 164, item <= 512 bytes) and timestamp plausibility (-1 h/+2 min). It has no per-host distinct-item cap and no per-tuple rate, so a tenant-controlled host can grow both the item count and the samples per window.
- `internal/rules/ticker.go:73`: batchDeadlineFactor = 4 x the 15 s default interval gives one 60 s deadline for the whole cross-tenant batch; there is no per-host budget.
- `internal/rules/ticker.go:38`: DefaultEvalBatch = 200 hosts drawn from all organizations by one manager-wide ticker (internal/app/app.go:664).
- `internal/db/migrations/00044_check_samples.sql:51`: check_samples_lookup_idx (org_id, host_id, check_key, item, metric, at DESC) makes each window an index range scan with heap fetches for value, so cost scales with windows x items x samples.
- `internal/rules/due_sql.go:227`: LockOneEvalCursor uses SKIP LOCKED: with several managers only the manager holding the expensive host is stalled, so a full stall needs a single manager or at least as many expensive hosts as managers.

### Blockers

- The wall-clock cost of one windowStatement with ~2460 or more 24 h LATERAL aggregates on a TimescaleDB hypertable cannot be measured here, because Postgres/TimescaleDB containers are forbidden in this sandbox. So it is unproven whether a single host's evaluation exceeds the 60 s batch deadline, which would cause a persistent head-of-line stall, or only degrades throughput. That depends on Postgres sizing and buffer-cache state.
- The deployed manager count decides the blast radius. With two or more managers, SKIP LOCKED lets the other managers skip the locked host, so a full stall needs a single-manager deployment (the default compose stack) or at least as many expensive hosts as managers.
