## 2. Security posture

Within this run's scope, Pulsix holds its main trust boundaries. Every run-2 confirmed record whose unit was re-passed is fixed on every traced path (bearer-minted memberships, invite survival, per-account second-factor budget, setup hashing, cross-origin mutations, claim-after-revocation, rotation account, sweep fail-open, pinned SSH options, JSON redaction, chat markup, enrollment token argv). The new backup/restore subsystem gets the hard parts right: every backup is age-encrypted under a key derived from the master key, the whole file is authenticated before anything is wiped, restore identifiers come from the live catalogue and are quoted, row-level security and foreign keys are lifted and restored inside one transaction, the API is instance-admin and session-only, and backup names cannot escape the storage target.

The five confirmed records are all low severity. Two come from one design gap in the backup feature: the plaintext header of a backup file is not authenticated, yet it drives retention (a storage writer can make Pulsix delete every real backup) and is printed raw by `restore --list`. The other three are a bearer token that can still mint lasting worker and agent identities (the variant the run-2 fix 7.31 left open), an invalid-UTF-8 mount point that silences a host's agent stream, and a redaction gap for secrets containing both quote characters. Eight leads need a database, a deployment fact or an owner decision to settle; the most consequential owner decision is whether a restore may reactivate credentials revoked after the backup was taken.

## 4. Confirmed findings in brief

### 4.1 A mount point with a quote and a non-UTF-8 byte still poisons the agent's stream after the 7.40 fix (low)

- **Location:** `internal/agent/checks/disk.go:115` → `internal/agent/session.go:325`
- **Lower-trust principal and conditions:** A local unprivileged account on a monitored host.; The account can create a mount in PID 1's mount namespace, for example FUSE through setuid fusermount/fusermount3, on a directory it controls whose name contains '"' and a non-UTF-8 byte. The 7.40 fix comment and backlog row name this capability as the threat model the fix defends against. Whether a given distribution allows it is a deployment fact.; The disk check runs in discovery mode, with no explicit 'mounts' list. This is the default. Explicit mounts arrive as JSON strings from the manager and are valid UTF-8.
- **Reproduction:** An unprivileged local user on a host running the Pulsix agent, who can mount a FUSE filesystem on a directory they own. Copy the repository to scratch. Add internal/agent/checks/v02_poison_test.go, which writes a fixture mountinfo with a '/' ext4 line, the payload line and a control line /home/u/n\xffz that has no quote. It sets HOST_PROC_MOUNTINFO to the fixture, calls diskPlugin{gopsutilPartitions{}, fakeUsage}.Collect, logs each item's utf8.ValidString and reportableItem result, and proto.Marshals the resulting CheckResults. Add internal/agent/v02_replay_test.go. It starts an in-memory bufconn gRPC AgentService that acks every message and counts stream opens, heartbeats and results. It builds a real Loop with NewLoop and puts the poisoned result plus a good result into the buffer through handleResults. Then, three times: it opens a real client AgentStream, calls activateSender, sends a heartbeat on the same sender, calls Recv, deactivates the sender, and re-adds the poison as a disconnected disk tick would. A control Loop without the poison runs the same steps. Run each test in the approved Docker sandbox (--network none, read-only, env -i, resource limits): go test -count=1 -v -run TestV02DiscoveredMountItems ./internal/agent/checks/ and go test -count=1 -v -run TestV02PoisonReplayBlocksEveryReconnect ./internal/agent/.
- **Result:** Collect returned 9 observations with no error. The item '/home/u/q"\xffz' had validUTF8=false and reportable=true. The control item without a quote was normalised to '/home/u/n\uFFFDz' and was valid. proto.Marshal failed with 'string field contains invalid UTF-8'. In the replay harness, each of 3 reconnects failed the same way. activateSender returned 'replay buffered check results: rpc error: code = Internal desc = grpc: error while marshaling: string field contains invalid UTF-8', the following heartbeat Send returned EOF, and Recv returned the same Internal error. The live sender was never installed, and the buffered count grew 2, 3, 4. The server recorded 3 stream opens, 0 heartbeats and 0 check results. The control loop replayed and sent its heartbeat without error.
- **Impact:** Monitoring of that one host stops persistently while the mount exists. No check results reach the manager, and no heartbeats are sent, which also stops configuration convergence. Threshold alerts for the host cannot fire. The host still looks seen, because stream opens touch last_seen and facts still arrive. Its rule tuples fall to unknown ('no data'), so the gap shows in the UI but is not reported as the host being offline. Other hosts and tenants are unaffected, and no data is disclosed or modified.
- **Priority:** likelihood low (It needs a local account on a monitored host plus the ability to mount in init's namespace, for example FUSE with setuid fusermount. Many hosts allow this, but it is a deployment fact. The attacker needs one directory name and one mount, with no ongoing effort.); impact medium.
- **Smallest fix:** Add utf8.ValidString to reportableItem, which covers both discovered and explicit mounts. Add the same check to the manager's withinContract for parity. Update the plugin's error text and the 7.40 test to cover the UTF-8 rule. Defence in depth in the session: treat a client-side encode failure (codes.Internal 'error while marshaling' returned by Send before anything reaches the wire) as a poison chunk to drop and log rather than re-buffer, so no single result can block heartbeats. Add a regression test with a mountinfo fixture that contains '"' plus 0xFF, expects the mount to be skipped, and expects every Collect output to marshal.
- **Fingerprint:** `internal/agent/checks/disk.go:reportableItem:invalid-utf8-mount-point-poisons-agent-stream`

### 4.4 Forged plaintext backup headers make scheduled retention delete every authentic backup, including the one just written (low)

- **Location:** `internal/backup/storage_dir.go:88` → `internal/backup/ticker.go:143`
- **Lower-trust principal and conditions:** The attacker can create objects in the configured backup destination (the S3 bucket prefix, or the backup folder volume) but holds neither the master key nor the derived backup key. Delete or overwrite rights are not needed. A writer that also has delete rights could delete backups directly, so the added risk is for create-only or put-only writers.; The daily schedule is enabled, because retention runs only after scheduled backups. Any retention values work if the attacker plants objects in enough distinct days, ISO weeks and months to fill every tier. For the defaults 7/4/6, seven objects dated in seven different months are enough.; Permanent loss needs a destination without versioning or object lock. On a versioned bucket the manager's deletes only add delete markers, and with object lock the deletes fail.
- **Reproduction:** A holder of create-only write access to the backup folder or bucket prefix, without the master key, who plants header-only objects once. Copy the source to scratch and add the harness test TestV08ForgedHeadersPruneAuthenticBackups to package internal/backup (scratch/src/internal/backup/zz_v08_forged_prune_test.go). It builds the real backup.Service with the package's fakeStore, fakeDump, fakeMailer and clock fakes, a storageFor that returns backup.NewDirStorage(t.TempDir()), and DefaultSettings() with Enabled=true (folder, 03:00 UTC, retention 7/4/6). Call RunDue at 2026-10-31 03:00:10 and at 2026-11-01 03:00:10 UTC to take two authentic scheduled backups. Write the seven forged files into the folder with os.WriteFile. Call RunDue at 2026-11-02 03:00:30 UTC and list the folder, then call RunDue at 2026-11-03 03:00:30 UTC and list the folder again. Run in the approved sandbox: docker create --pull never --network none --read-only --cap-drop ALL --security-opt no-new-privileges --user 65532:65532 (with the prescribed resource limits, tmpfs, read-only source and module cache, and env -i) golang:1.27.1-alpine ... timeout 300 go test -count=1 -v -run TestV08ForgedHeadersPruneAuthenticBackups ./internal/backup/
- **Result:** The 2026-11-02 run logged 'backup finished ... pulsix-20261102T030030Z-scheduled.pxbak' and then 'pruned scheduled backup' for pulsix-20261102T030030Z, pulsix-20261101T030010Z and pulsix-20261031T030010Z, which left only zz-forged-1..7.pxbak. The 2026-11-03 run wrote pulsix-20261103T030030Z-scheduled.pxbak and pruned it at once. Zero authentic backups remained, while all four scheduled attempts were recorded as succeeded (artifact agents/v08-backup-storage/artifacts/evidence.txt). This reproduces the hunter's result independently and shows that the object names do not matter and that the deletion repeats on later runs.
- **Impact:** After a single write, the manager itself deletes every authentic scheduled backup, including each new one right after it is written. Disaster-recovery capability is lost silently and stays lost after the attacker's access is revoked, and the deletion is permanent on unversioned storage. Manual backups and the live database are not affected, and nothing is disclosed.
- **Priority:** likelihood low (The attack needs write access to the backup bucket prefix or folder. The shipped compose stack mounts the folder only in the manager and cli containers (files 0600, folder 0750), so the realistic routes are an S3 bucket or prefix shared with other writers, or a leaked put-only credential. An attentive administrator could notice forged entries dated years ahead in the listing.); impact medium.
- **Smallest fix:** Stop trusting the plaintext header for destructive decisions. (1) Pass the name of the backup the current run wrote into Prune and always keep it. This alone restores the spec invariant. (2) Authenticate the header: write a MAC over the magic and header line, keyed by an HKDF of the master key with its own label (e.g. 'pulsix backup header v1'). Treat an object whose MAC is missing or wrong like a damaged object: never pruned, never counted toward a tier, and shown as unverified in the listing. (3) As defence in depth, require the name's stamp and kind (ParseObjectName) to match the header, and ignore objects that claim a CreatedAt later than the current run. A date filter alone is not enough, because a forged object dated earlier on the same day as an authentic one can still displace it within that day's bucket. Regression test: plant forged future-dated and same-day scheduled objects, run RunDue, and assert that no authentic backup is deleted, in particular the one just written.
- **Fingerprint:** `internal/backup/retention.go:Prune:unauthenticated-header-drives-deletion-of-authentic-backups`

## 6. Hardening notes and positive patterns

Hardening notes are not findings: each describes a missing defence-in-depth layer or a risk with no demonstrated boundary violation. They are grouped by the coverage unit whose hunter raised them.

**CI and release workflows — Build, image and release integrity**
- internal/worker/runner/runner.go streamEvents now logs a 120-byte prefix of each malformed runner line after redaction; values the redactor does not know (e.g. secrets a play derives at runtime) can reach the worker's own log. Worker logs belong to the worker operator, who can read the org's job credentials by design, so this is not a boundary crossing.
- internal/worker/playprocs.go livePIDsOfUID reports no survivors when /proc is mounted with hidepid=1/2 (other uids' PIDs are invisible), so the 7.35 fail-closed check would silently pass on such a mount; the default container /proc has no hidepid. Consider asserting the worker can see a known play-uid process, or refusing to start under hidepid.
- internal/worker/playbooks/pulsix.bootstrap.yml writes <home>/.ssh and authorized_keys with file/lineinfile as root, following symlinks in the target account's home; an existing account whose home is writable by a different local user could redirect the root write. The target account is granted NOPASSWD sudo in the same play, so its owner gains nothing; using `follow: false` and checking the path is not a symlink would still be tidier.
- deploy/worker/Dockerfile installs apt packages unversioned and pip packages by version without --require-hashes (unchanged since run 2).
- internal/api/cross_origin.go allows unsafe methods carrying neither Sec-Fetch-Site nor Origin (non-browser clients and very old browsers); acceptable given SameSite=Lax cookies.

**Restore and worker re-enrolment commands — Restore refusal while managers run and replaced worker identity**
- restore --list (internal/app/restorecmd.go listBackups) prints object names and the unauthenticated plaintext header's Kind and PulsixVersion raw to the operator's terminal; a writer of the backup storage can embed terminal control sequences there. Strip or escape non-printable characters before printing.
- The restore confirmation is asked before Verify and never shows the authenticated CreatedAt, and Verify does not bind the object name's timestamp and kind (ParseObjectName) to the manifest header. A storage writer can copy an old genuine backup under a newer name, and the operator only learns the real date after the wipe, from printRestored. Compare the name with the manifest, or show the authenticated date and ask before wiping.
- After ErrRestoreIncomplete the database is empty. Starting the manager instead of re-running restore exposes the token-less first-run setup wizard to any caller. A persistent 'restore in progress' marker outside public, or a setup refusal while it exists, would close that window.
- worker add opens the schema-owner URL without an application_name (internal/app/workeradd.go:103) and runs full migrations. Naming it (e.g. pulsix-manager-cli or its own name that restore also refuses on) would let restore detect a concurrent worker-enroll.
- worker add --replace revokes then deletes then registers in three separate calls; a failure after Delete leaves the bundled worker unregistered until the next run (availability only, no identity confusion).

**Agent disk plugin mount points reported as check items — Whole-batch refusal of check results on one over-limit item**
- internal/checks/samples.go withinContract: also refuse invalid UTF-8 in check_key/item/metric/label/error for parity with the agent filter. gRPC proto3 decoding already rejects it today, but that error also ends the stream.
- internal/agent/session.go: a client-side encode failure (codes.Internal from Send before anything reached the wire) should drop the offending chunk with a log line instead of re-buffering it for every reconnect, so that any future item-contract gap cannot become a permanent replay poison.
- internal/agentapi/stream.go: Touch on every heartbeat and RecordFacts on every facts message are unthrottled per stream. They are one-to-one work on one pool connection per agent identity, not amplification, but a minimum interval per serial (like allowResolve) would bound a looping agent.
- internal/checks/resolver.go loadResolveBundle runs one QueryHosts per monitoring group on every resolve, and the number of groups per organization is unbounded. This is operator-configured and scoped to the operator's own org, but a per-org cap or a cached group-membership bundle would decouple heartbeat cost from group count.
- internal/api/item_handlers.go GET /orgs/{org}/items and the ListAllHosts reads in item_handlers.go:320 and monitoring_group_handlers.go:259 are unpaginated, which is the authorized scope but grows with agent-reported cardinality (see the unit-2 candidates).

**Agent check results — Notification payload rendering**
- Agent-chosen item (internal/notify/render.go:248-267): agentText defuses mentions and masked links, but a bare URL inside an item (for example '/mnt/visit-https://evil.example/reset', 512 bytes allowed, no control characters) is still autolinked by Slack, Discord and mail clients. The URL is visible rather than disguised, so this is a residual phishing aid, not a markup injection. Consider replacing '://' or ':' in agentText if that matters.
- The '| json' form of alerts.items (placeholders.go:112, AlertItem JSON tags in event.go:159-170) carries Item raw (json.Marshal escapes only <, >, &, which the receiver unescapes). It is meant for workflow runners. An admin who feeds it to a chat service gets the undefused item. Consider applying agentText to Item in the JSON form as well, or documenting it.
- Operator-chosen names (schedule.name, template.name, host names, org name) reach chat templates only through oneLine/escapedText, with no markup defusing. An operator can therefore put '@everyone' or a Slack '<url|text>' link into an admin-configured chat channel. This is same-org, lower-but-trusted role, so it is not reported.
- Webhook channel update (internal/notify/service.go:198-231): header values listed with a nil value and the signing secret are kept when the URL is changed. Another org admin (or an admin-role pxt_ token) can therefore send a sealed header credential set by the owner to a new URL they control. This is consistent with spec section 14 (admins can read org credentials). Requiring the sealed headers to be re-entered when the URL host changes would make the values truly write-only.
- Private-range allowance (internal/outbound/policy.go:9): an operator of a multi-tenant instance has no way to deny RFC 1918/ULA space to tenant webhooks. PULSIX_NOTIFY_ALLOW_CIDRS only re-admits. Each tenant org admin can make blind POST/PUT requests with chosen headers and body into the manager's LAN and read the status code. This is documented design. A deny-list setting would let a hosted operator close it.
- Instance SMTP (internal/mail/smtp.go:177, internal/api/setup_handlers.go:253-282): the SMTP host is dialled without internal/outbound and the raw error is echoed as 502. This gives the instance admin a TCP connect and banner oracle across the manager network. It is the same principal and the highest web role, so it is not reported.

**Bearer-token-capable org routes that mint worker enrollment tokens, agent tokens and trigger secrets — Credentials do not mint credentials: a pxt_ bearer token must not create a successor that outlives its revocation**
- Trigger create (trigger_handlers.go:158) and rotate-secret (trigger_handlers.go:216) accept a bearer token. The secret only fires one pre-configured template or repo sync, which an operator token can already make persistent through a schedule, so this is not a finding. Gating them with requireInteractiveSession, or documenting them as an intended automation exception, would make the 'credentials do not mint credentials' rule uniform.
- requireInteractiveSession is an opt-in call per handler on the bearer-enabled group. A route-level marker on the org group, listing which operations are session-only, plus a test that enumerates every operation minting a secret or credential, would stop the next minting route from silently missing the rule (this is the second regression after 7.31).

**Org-scoped REST routes — Org membership, role and token authorization**
- Session cookie pulsix_session (internal/auth/middleware.go:13, internal/api/auth_handlers.go:159-161) has no __Host- prefix. A same-site sibling subdomain, or a plaintext-HTTP response to the same host on a deployment without HSTS, can toss an attacker-owned MFA-complete session cookie with a longer Path that takes precedence, a session swap or login CSRF. The 7.19 secret rotation only covers planted pending sessions. Renaming to __Host-pulsix_session (Secure, Path=/, no Domain) closes it when PublicURL is https.
- Argon2id (64 MiB, t=3) runs per failed login and per new-account invite accept with only a per-address limit (clientip.Limiter; IPv6 keyed per /64) and no process-wide concurrency cap. Many source addresses can drive manager memory pressure. A small semaphore around HashPassword/VerifyPassword would bound it.
- POST /api/v1/auth/passkeys/login/begin (internal/api/passkey_handlers.go:193) is unauthenticated, has no rate limit and inserts one webauthn_ceremonies row per call. Rows are reaped after expiry, so growth is bounded by request rate times CeremonyTTL, but a per-address limit would match the other public auth routes.
- gRPC server (internal/grpcsrv/server.go:176-190) sets no MaxConcurrentStreams. A client without a certificate can open many streams and upload up to MaxWorkerToManagerBytes (16 MiB) per message before the auth interceptor refuses the call. The client sends every byte (no gzip decompressor registered), so it is volume, not amplification. A low MaxConcurrentStreams and a smaller limit for Enroll would tighten it.
- Webhook trigger secrets (internal/triggers, org-owned, CreatedBy never consulted at fire time) keep running job templates after their creator is removed, demoted or deactivated, unlike invites since 7.29. This is by spec section 3 and admins can list and delete triggers, but offboarding guidance or a creator-liveness condition would close the gap.
- Invite issuer condition is evaluated at accept time, so re-adding a removed admin revives their old unexpired invites (7-day TTL). This is low impact because the re-added admin can invite again anyway.
- Removing a second factor (DELETE /auth/totp, DELETE /auth/passkeys/{id}) does not revoke the account's other sessions, and there is no 'sign out other sessions' action.

**Agent install command and install.sh token argument — Enrollment token exposed to local readers on the target host during installation**
- deploy/compose/README.md:173-184 tells admins to 'Run that command on the worker's machine' above an example still in the pre-fix form: `-e PULSIX_ENROLL_TOKEN=pxw1.…`, which puts the token in the docker client's argv. The example also has no --init and no PULSIX_WORKER_PLAY_UID. An admin typing from the README brings back run-2 findings 7.39 and 7.32. Fix: update the example to match workerSnippets (env prefix plus bare -e, --init, PULSIX_WORKER_PLAY_UID=65533).
- The docker run snippet (worker_snippets.go:36) relies on the shell-prefix environment reaching the docker client. On hosts where the admin prepends sudo (`PULSIX_ENROLL_TOKEN=… sudo docker run …`), sudo's default env_reset drops the variable, the container starts without a token and fails to enroll. That invites the admin to fall back to the argv form. Fix: note `sudo --preserve-env=PULSIX_ENROLL_TOKEN` or render `sudo env PULSIX_ENROLL_TOKEN` guidance, or offer an --env-file variant written 0600.
- agentInstallCommand (agent_handlers.go:358-359) appends the operator-supplied name hint (max 64/253 chars, otherwise unvalidated) to a shell command line without quoting. Only the creator sees the command, so this is self-harm today. Shell-quote it, or restrict name_hint to hostname characters, so a copied command cannot be split by spaces or metacharacters.
- install.sh read_token_file checks `-f`, `! -L` and stat owner/mode on the path, then reads it again by path with head. If the admin places the token file in a directory another user can write (not /tmp with its sticky bit), the file could be swapped between check and read for an attacker-chosen token valid on the same manager. Read it once through a descriptor that was checked, or require the parent directory to be root-owned and not group/other writable.
- install.sh fetches the binary and its .sha256 from the same BASE_URL, which config.Load accepts with any scheme (config.go:135-138), and curl -L / wget follow redirects without --proto =https. The checksum is therefore an integrity check against corruption, not an independent anchor. Since the manager renders the script, it could embed each binary's sha256 directly in the script and refuse non-https BASE_URLs (or pass --proto =https --proto-redir =https), binding script and binary to one response.
- install.sh keeps --token as a legacy option that still places the token in argv. It is documented and opt-in, but no warning is printed when it is used. Printing a stderr warning (or deprecating it) would steer automation to --token-file.

**Personal activity feed — A user's past membership vs audit events of organizations they left, read unscoped**
- Shared repository definitions (/api/v1/admin/repos/definitions, shared.Service.CreateRepo/UpdateRepo) skip repos.validate entirely: no URL transport/prefix check, no leading '-' or whitespace refusal, no branch/subpath/name pattern and no '..' refusal, and git_repos/shared_repos have no CHECK constraints. Only an MFA-complete instance admin can write them and the worker re-refuses leading '-' and playbook subpath traversal, but findRequirements still joins the unvalidated subpath and file:// or other git 'user'-policy transports are accepted. Reuse repos' validateURL/branch/subpath/name checks in shared.Service and set GIT_ALLOW_PROTOCOL=https:ssh in the worker's git and ansible-galaxy environment.
- GET /api/v1/me/activity is documented as 'across every organization they belong to' but ListAuditEventsForActor has no membership predicate; a removed member keeps reading their own past events (org id + summary) of organizations they left. This exposes only the caller's own authored actions, so it is not a boundary failure, but the doc comment or the query should be aligned (e.g. join current memberships if departed-org history is not intended).
- The rule evaluation ticker has no statement_timeout or per-host time budget distinct from the 60 s batch deadline; even without the candidate above, a host that repeatedly fails by timeout keeps the oldest next_due_at and is retried first on every tick. A per-host deadline plus pushing next_due_at back on failure would bound head-of-line effects.

**Backup name in download and delete — Backup name to storage path or object key**
- internal/backup/storage_dir.go: List/describe/Open use os.Open and DirEntry.IsDir without rejecting symlinks, so a symlink named like a backup in the backup folder is listed as damaged and its target streamed by GET /api/v1/admin/backups/{name}/download. No sensitive manager-readable regular file was found (master key and DB URL are env-only, /proc files stat as 0 bytes), so this is defence in depth: use Lstat and skip non-regular entries in List, and open with O_NOFOLLOW (or Lstat before open and compare os.SameFile with the opened descriptor's Stat) in Open/describe.
- internal/backup/listing.go Service.Open returns the size from the earlier listing Stat while dirStorage.Open reopens the path; take the size from a Stat of the opened descriptor so Content-Length always matches the bytes actually streamed (also closes the list-then-open swap window).
- internal/backup/naming.go ParseObjectName accepts non-canonical stamps (Go time parsing tolerates a fractional second, e.g. pulsix-20260101T000000.5Z-manual.pxbak); requiring ObjectName(at, kind) == name would make the accepted set exactly the produced set. No traversal impact because names must also match a listed object and pass validName.

**Backup settings — S3 credentials storage, return and outbound endpoint**
- internal/backup/settings.go:186-205 Test (and SaveSettings with secret_key absent) reuse the stored S3 secret for whatever endpoint, bucket and access key the request names. SigV4 never sends the secret, so nothing is disclosed today, but requiring the secret again when endpoint, access key or bucket changes would bind the sealed secret to the destination it was entered for (the same gap exists for the SMTP password with the host, outside this unit).
- internal/backup/storage_s3.go:129-141 The S3 endpoint is not checked by internal/outbound, so an instance admin can make the manager send S3 requests to loopback, link-local or cloud-metadata addresses, and POST /admin/backups/settings/test returns up to 1 KiB of a non-2xx non-XML response body through minio-go's error message. Binding the authenticated header (see the candidate) to an instance id, and only pruning own backups, fixes this variant too.
- internal/backup/storage_dir.go:41-50 a crash between create and rename leaves <name>.partial files that nothing ever removes; they are invisible to listings and retention, so they only use up disk space.
- internal/backup/store_sql.go:58-74 the backup lock is a session advisory lock on one pooled connection; if that connection drops during a long backup the lock is gone while the backup continues, so another manager can mark the attempt abandoned and run the same slot again. **SSH credential rotation group — Worker results driving credential re-key and old-key revocation**
- ReportResult/FinishFor is not bound to the worker's current status: terminate's UPDATE (internal/jobs/terminal.go:96-100) neither locks nor re-checks the workers row the way the claim now does (LockActiveWorker). A result call that passed the interceptor before a revocation committed is accepted if its UPDATE runs before RequeueWorkerJobs (internal/workers/revoke.go:62-77). That includes rotate_key and connection_test results, which drive the credential finalize and the old-key revocation. The window is milliseconds, and the call was authorized when it arrived. Suggested fix: run the claim's FOR SHARE active-worker lock inside terminate's transaction whenever t.worker is set.
- A worker's terminal result is not bound to the claim token or attempt: ReportResultRequest carries no worker_token (proto/pulsix/worker/v1/worker.proto:139-144), and FinishFor binds only org, zone and worker_id. A delayed result from the same worker's earlier attempt, after a reaper requeue and re-claim by that same worker, finishes the newer attempt. There is no cross-worker impact. Binding it to the token issued at claim, as the event stream already does, would close this.
- Credential Update accepts new key material while a rotation group of that credential is active (internal/credentials/service.go:258-279). FinishRotation then overwrites it without comparing against the rotation's PreviousPublicKey (internal/credentials/rotate.go:110-137), so a key imported mid-rotation is lost and never revoked. Suggested fix: refuse key-material updates while CountActiveRotationJobs > 0, or make the finalize a compare-and-swap on public_key.
- Service.Rotate reads the credential's PreviousPublicKey (internal/credentials/rotate.go:69,89) before CreateRotationGroup takes the per-credential advisory lock (internal/jobs/store_sql.go:76). If an earlier group's finalize, and all of its revocations, completed inside that window, the new group would revoke an already-removed key and leave the intermediate key authorized. Suggested fix: re-read the public key under the lock and fail on a mismatch.
- Unmanaged hosts whose host_ssh references the rotating credential are excluded from both the rotation and the revocation snapshot (internal/db/queries/credentials.sql:85-95), so the previous key stays authorized there after a rotation. This is deliberate, but the rotate response and audit summary do not name these hosts. Suggested fix: report them so the operator knows a manual cleanup is needed.
- The revocation account is recomputed at revoke-claim time (internal/jobs/system_claim.go:186-194). If the host's SSH username or the credential's username is edited between rotate_key and revoke_key, the revocation fails (it logs in as an account that never received the new key) or targets another account, and the previous key stays on the original account. The failure is visible as a job error. Recording the rotated account in the revocation payload would make it deterministic.

**Job run output, events, stats and error text — Redaction of secrets from viewer-readable job output**
- internal/worker/runner/redact.go:143 pythonJSON(ensureASCII=true) leaves U+007F (DEL) literal, but Python's json.dumps(ensure_ascii=True) writes it as \u007f (ESCAPE_ASCII matches anything outside ' '..'~'). A secret containing DEL shown through to_json is therefore not matched. The sandbox probe confirms the Go output 'abc\x7fdefgh'. Escape r >= 0x7f in the ensure_ascii branch.
- internal/worker/runner/redact.go:248 redactor.value returns numbers and booleans unchanged, and internal/jobs/redact.go only lists string secrets. A secret that a play turns into an int (for example '{{ pin | int }}') survives in res while the stdout display is redacted. - internal/worker/runner/stats.go:28 buildStats copies ansible recap host names into job stats without redaction (event Host fields are redacted at runner.go:450). Apply red.text to unmapped names for symmetry.
- internal/worker/loop.go: the worker reports errText (for example ansible-galaxy stderr, sync.go:219) without passing it through the claim redactor or redactURLs. This was already noted in runs 1 and 2 and is still open.
- internal/worker/runner/inventory.go:381 forcedConnectionVars forces ansible_ssh_executable but not ansible_sftp_executable or ansible_scp_executable (nor ansible_sftp_batch_mode, ansible_control_path, ansible_control_path_dir). - internal/jobs/system_claim.go:126 the comment on credentialTargetPayload says a bastion target is resolved with '(no pin)', but bastionTargetPayload ships the target bastion's pin (system_claim.go:272-283). The stale comment could mislead a future change.

**Backup file format and encryption — Confidentiality and integrity of a backup file at rest**
- Object names are not bound to the authenticated content: Verify/Restore never compare ParseObjectName(name) with the manifest's CreatedAt/Kind, so a storage writer can copy an older authentic backup over a newer name (internal/backup/verify.go:18, internal/app/restorecmd.go:162). Not reported as a finding because the same writer can achieve the same rollback by deleting newer backups and the listing/printRestored show the authenticated date; a warning when the name's timestamp disagrees with the manifest header would make the substitution visible.
- The raw master key is used both as the AES-256-GCM sealing key (internal/crypto/secretbox.go:16) and as HKDF input for the backup key (internal/backup/crypt.go:27). No practical cross-use weakness exists (HMAC-SHA256 vs AES), but deriving a separate sealing subkey would give clean key separation.
- Restore manifest sequence names are not checked against listSequences before setval (internal/backup/restore.go:227); the input is authenticated by the backup key and always qualified to public, so this is defence in depth only.

**Worker enrollment and renewal — Enrollment token and CA pinning**
- Worker enrollment tokens are not bound to the issuer's live authority (contrast the invite fix fc5fc6d / backlog 7.29): a pending pxw1 token created by an admin who is then removed or demoted can still be redeemed for up to EnrollmentTTL (1 h) because Service.Enroll (internal/workers/enroll.go:149-180) and MarkWorkerEnrollmentUsed (internal/db/queries/workers.sql:52-56) never read created_by. Not reported as a finding: pending enrollments are listed and withdrawable by admins (worker_handlers.go:195-250), and the same admin could enroll a worker before removal with an identical, persistent result. Consider voiding pending enrollments whose created_by lost workers.write, as invites now do.
- Identity.Replace reads the current certificate without the lock (identity.go:117-126) while Identity.Reload can swap in a rewritten bundle concurrently; if a renewal answer lands between the two, the old-key renewed certificate is installed and persisted over a bundle whose key.pem now holds the new key, leaving a mismatched on-disk pair (availability only, needs a renewal racing `worker add --replace`). Compare-and-swap on the certificate Replace validated against would close it.
- Identity.Reload and reloadingTLS.refresh accept any loadable key pair and any PEM root file without checking that the certificate chains to the trusted CA or is a worker ClientAuth leaf; safe today only because the bundle directory is writable solely by the worker uid. Keeping that directory 0700 (hardenIdentityDir) is therefore load-bearing for the trust anchor as well as for key confidentiality.
- RunEvents stream revocation is per-process (internal/grpcsrv/streams.go:9-12): with several managers a revoked worker's already-open event stream on another manager keeps appending until it ends; documented as accepted.

**sync_repo job on repository-controlled content as the worker uid — Repository ansible.cfg and requirements vs the worker identity bundle reloaded before every handshake**
- installRequirements runs ansible-galaxy with cmd.Dir=cloneDir and strips ANSIBLE_CONFIG, so a repository-provided ansible.cfg at the clone root is honored (clone dir is 0700, not world-writable). Set ANSIBLE_CONFIG explicitly to a worker-controlled file (or run the galaxy step with a neutral CWD outside the clone) so repo content cannot steer the worker-uid galaxy process via settings such as log_path, roles_path, collections_path or galaxy server list.
- Reject galaxy role/collection names containing '/' or '..' before invoking ansible-galaxy (same defence-in-depth the run-1 reviewer noted for internal/worker/sync.go:installRequirements:galaxy-role-path-escape), keeping installs provably inside the per-repo .galaxy directory rather than relying on ansible-core's -p as a containment boundary.
- Run the sync_repo / ansible-galaxy step under the play uid (65533) rather than the worker uid, or place the repo-cache tree on a separate filesystem/ownership from the identity bundle, so that any worker-uid write escape in sync cannot reach <DataDir>/identity -- aligning sync with the containment that playbook-uid separation already enforces for plays.
- In reload.go, verify a newly read cert/key pair chains to the pinned CA (and optionally matches the expected worker SAN) before installing it, so a bundle rewrite cannot even transiently swap the presented identity to an unusable or unexpected one; today Reload installs any loadable pair and lets the manager be the only check.
