## 2. Security posture

The fixes for run 1's findings (backlog 7.7–7.23) hold. Every one was revalidated against current source: facts render inert, the auth rate limit reserves before the handler, sessions rotate on MFA completion, invitations for existing accounts need that account's session, the job log stream re-checks access, agent renewal locks the live serial, the three reported redaction gaps are closed (one further, doubly escaped spelling is a new finding below), connection-test claims are bound to route and time, and the schemas route is gated. Tenant isolation through `requireOrg`, row-level security and composite foreign keys held across the newly reviewed monitoring/alerting and core CRUD handlers; no cross-tenant read or write was found.

The confirmed weaknesses of this run sit mostly in lifecycle and quota edges rather than in the core boundary. Two concern identity: second-factor guessing is limited only per source address, not per account (medium), and pending invitations survive the issuing admin's removal and cannot be revoked (medium); an API token without token-minting rights can mint a lasting admin membership through an invitation (low). Three concern the worker host: a managed host's facts can replace the pinned SSH options through `pulsix_ssh_common_args` (medium), the Workers page's snippets omit play-uid separation so plays can read the worker key (low), and the new between-jobs sweep runs as the uid it sweeps and fails open (low). Two concern availability of the shared manager: the unauthenticated setup endpoint runs a 64 MiB argon2id hash on every call even after setup (medium), and any enrolled agent can trigger unlimited organization-wide resolves through heartbeats (medium). The rest are narrow: key rotation acts on the credential's username rather than the run's login account (low), a revocation racing ClaimJob still hands out a job (low), a doubly JSON-escaped secret escapes redaction (low), and the agent install command puts the enrollment token in a root process's argv (low).

Seven further leads need a deployment or runtime fact before they can be confirmed or dismissed; they carry no severity.

## 4. Confirmed findings in brief

### 4.1 Any enrolled agent can trigger unlimited organization-wide resolves against the shared database by sending heartbeats in a loop (medium)

- **Location:** `internal/agentapi/stream.go:92` → `internal/hosts/tags_store_sql.go:122`
- **Lower-trust principal and conditions:** The attacker holds a valid, unrevoked agent certificate for one host. That means root on any monitored host of the organization, which is a lower-trust principal with no REST access, or any user who can enroll an agent: operator+ in an organization, and any MFA-complete user can create their own organization.; The attacker must be able to reach the manager's gRPC listener (8444), which agents need anyway. The default compose file does not publish it on the host, but any deployment with remote agents does.; The per-heartbeat cost grows with the organization's host, tag and monitoring-group counts. The same tenant can raise all three without quota.; How far the load spreads to other tenants depends on the deployment's pool size (the pgx default unless the DSN sets one) and on any DSN-level statement_timeout. Code sets neither.
- **Reproduction:** One enrolled agent identity sends Heartbeat messages back to back on several concurrently open AgentStreams, instead of one every 30 s. Copied the repository to scratch and added internal/agentapi/zz_v13_heartbeat_test.go. It uses a real checks.Service (checks.NewService with WithHostRoster and WithMatcher) backed by counting fakes for Store.ListDefinitions, Store.List (10 groups), HostRoster.MonitoredHosts (returns the enrolled host) and HostMatcher.MatchingHosts. Enrolled one agent through the package's own test harness (newHarnessPort, enrollAnAgent). Opened 3 AgentStreams, kept them all open, sent 200 heartbeats on each and read each acknowledgement. Then read the StreamRegistry's tracked-stream count for the host. Ran it in the approved sandbox: go test -count=1 -v -run 'TestV13HeartbeatResolveFanOut|TestConvergenceUnrecognisedVersionPushesOnceThenConverges' ./internal/agentapi/ (no network, read-only source and module cache, 2 CPU / 2 GiB, 300 s limit).
- **Result:** concurrently tracked streams for this one host/serial: 3. streams=3 heartbeats_per_stream=200 acked=600 groups=10 elapsed=16.744667ms. downstream: MonitoredHosts=600 ListDefinitions=600 ListGroups=600 MatchingHosts=6000 total=7800 (3+G=13 per heartbeat). No heartbeat was throttled or refused. The repository's own TestConvergenceUnrecognisedVersionPushesOnceThenConverges also passed, asserting one resolve per heartbeat. The Touch UPDATE on each heartbeat ran against a fake store, so it is not counted in the 7800.
- **Impact:** Each tiny message costs 4+G organization-wide statements on the pool and manager process that all tenants share: 13 store or port calls per heartbeat locally, and about 28 ms of resolve work per heartbeat at 1000 hosts per the owner's measurement. Several looping streams can therefore degrade other tenants' API, ingest and alerting. The effect is not persistent. It needs sustained sending from an attributable serial, and stops when the streams stop or the certificate is revoked.
- **Priority:** likelihood medium (The attack needs one valid agent certificate. Root on any monitored host has one, and any user who can create an organization or holds operator+ can obtain one. The loop is trivial and no server-side control stops it.); impact medium.
- **Smallest fix:** Bound resolve work per agent identity on the server. In processHeartbeat, if this stream resolved less than a minimum interval ago (for example 10 s), skip the resolve and answer from the last ResolvedSet. Put a short-TTL per-organization bundle cache in front of loadResolveBundle (backlog 3.19's named mitigation), so concurrent heartbeats of one organization share one load. Cap concurrent AgentStreams per agent serial in StreamRegistry.track: refuse, or close the oldest stream, beyond a small number such as 2. Optionally set grpc.MaxConcurrentStreams. Add a regression test showing that 100 heartbeats inside one interval cause at most one ResolveHost, and that a third stream for one serial is refused.
- **Fingerprint:** `internal/agentapi/stream.go:processHeartbeat:unthrottled-org-wide-resolve-per-heartbeat`

### 4.2 Second-factor guessing on /auth/totp/verify is limited only per source address, so a password holder can brute-force the TOTP code (medium)

- **Location:** `internal/api/auth_handlers.go:96` → `internal/api/mfa_handlers.go:172`
- **Lower-trust principal and conditions:** Attacker knows the victim's password (phished, reused or leaked) and can open a pending session; no second factor is known.; Guess rate scales with distinct source keys the manager sees: one IPv4 address gives 20/min (about 8%/day); an IPv6 /56 or a pool of addresses gives thousands per minute. Requires the manager to see the true client address (direct exposure, or PULSIX_TRUSTED_PROXIES set for the fronting proxy); behind an untrusted proxy all callers share one key and the global rate is 20/min.; Victim account uses TOTP as its second factor. A passkey-only account has no TOTP secret and Verify always fails; recovery codes are 80-bit and not guessable.; Success is probabilistic per guess (about 3e-6); expected effort is about 333k guesses.
- **Reproduction:** Holder of a dummy victim's password but not the authenticator, sending /auth/totp/verify guesses for one pending session from many source addresses. Copy the repository to scratch, move the other internal/api *_test.go files and internal/api/apitest out of the scratch copy (their testcontainers dependency is not in the read-only module cache), and add the harness test file. Run in the approved sandbox: docker create --pull never --network none --read-only --cap-drop ALL --security-opt no-new-privileges --user 65532:65532 ... golang:1.27.1-alpine go test -count=1 -v -run 'TestV04' ./internal/api/ The harness injects one pending principal, sends 21 wrong codes from one IPv4 address (expect 20x401 then 429), then walks sequential codes starting 2000 below the current valid code, 20 per distinct IPv6 /64, against the same pending session.
- **Result:** phase1 one IPv4 address, 21 wrong codes: status counts map[401:20 429:1]; phase2 distinct /64s: 101, guesses: 2001, refused(429): 0, success at guess #2001 (valid code), MarkSessionMFAComplete UPDATEs: 1, SetTOTPLastStep calls: 1; success Set-Cookie contains pulsix_session: true (agents/v04-session-auth/artifacts/evidence.txt).
- **Impact:** Defeats the second factor and yields an MFA-complete session for the victim: all org roles, credential and job access, and instance-admin powers if the victim holds them.
- **Priority:** likelihood low (Requires the victim's password first. After that, effort depends on how many source keys the attacker has: days from one IPv4 address, about an hour from an IPv6 /56 or a comparable address pool.); impact high.
- **Smallest fix:** Add a per-user (or per pending session) failed second-factor counter in the database (additive migration) and check it before verifying. Increment it atomically on every failed TOTP or recovery-code check through verifyFactorCode, on the verify and the disable path. Past a small threshold (for example 5-10), revoke the pending session and lock verification for that user with exponential backoff; reset on success. Keep the per-address limiter as the outer layer and audit-log lockouts.
- **Fingerprint:** `internal/api/mfa_handlers.go:totpVerify:no-per-account-second-factor-attempt-limit`

### 4.3 Unauthenticated POST /api/v1/setup/complete runs a 64 MiB argon2id hash on every call, even after setup is complete, with no rate or concurrency limit (medium)

- **Location:** `internal/api/setup_handlers.go:81` → `internal/setup/service.go:237`
- **Lower-trust principal and conditions:** None. The route is public and needs no session, token or secret.; The attacker can reach the manager's HTTP listener, which the compose stack publishes on 8080, or reach it through the optional proxy. Any limits in a reverse proxy or gateway that the operator adds are outside the repository.; Applies to every instance for its whole lifetime. On a completed instance, every call is refused with 409 after the hash, so the only effect is resource consumption.
- **Reproduction:** An anonymous network client able to send HTTP POST requests to the manager. Copied the repository into the verifier scratch directory. Removed store_sql_test.go from the copy only, because it needs testcontainers. Added internal/setup/audit_v07_test.go, which defines its own concurrency-safe completedStore: AdminExists always returns true, and the store counts AdminExists calls and writes. The test needs no database and does not reuse the hunter's harness. The test measures runtime.MemStats.TotalAlloc and wall time for Status, which is the cheap baseline, and for Complete with the payload body: one call, then 3 concurrent goroutines. It asserts that every Complete returns ErrAlreadyCompleted, that each call allocates at least 60 MiB, and that the store sees zero writes. Ran it in the approved Docker sandbox: no network, read-only root and source, cap-drop ALL, 2 CPUs, 2 GiB memory, 512 pids, 300 s timeout. Command: go test -count=1 -v -run TestAuditV07CompleteOnCompletedInstance ./internal/setup/. The sandbox run's output is the audit artifact agents/v07-availability/artifacts/evidence.txt (not a repository source). Its line 3 records Complete x1 allocating 67154904 bytes (64.0 MiB) in 120 ms, and its line 4 records x3 concurrent allocating 201417016 bytes (192.1 MiB, HeapSys 199.7 MiB). Every call returned ErrAlreadyCompleted with zero writes, and Status allocated 584 bytes.
- **Result:** Status: 584 bytes, ~18 us. Complete x1: 67154904 bytes (64.0 MiB) allocated, 120 ms, ErrAlreadyCompleted. Complete x3 concurrent: 201417016 bytes (192.1 MiB) allocated, HeapSys 199.7 MiB, 334 ms, all ErrAlreadyCompleted. AdminExists was called 5 times (1 Status + 4 Complete, each after its hash), with 0 writes. PASS. This matches the hunter's independent run: 64.0 MiB per call, and 256.1 MiB for 4 concurrent calls.
- **Impact:** Each ~200-byte request costs 64 MiB of allocation and about 0.1-0.25 s of argon2id work on two threads. Live heap and CPU grow linearly with concurrent requests and nothing bounds them, so a flood can degrade or OOM the single manager process that every organization shares. The effect is transient (restart: unless-stopped, and it recovers when the flood stops) and causes no loss of data, confidentiality or integrity. Operator-added memory limits or proxy limits outside the repository may reduce, but not remove, the degradation.
- **Priority:** likelihood high (Needs no authentication, has no rate limit and takes a trivial well-formed JSON body. It is reachable on every instance for its whole lifetime, from a single source address.); impact medium.
- **Smallest fix:** First, refuse a completed instance before hashing. Add a cheap s.store.AdminExists check before auth.HashPassword and keep the in-transaction re-check for the concurrent first-run race. Second, attach withAuthRateLimit to POST /api/v1/setup/complete; a refused 409 is a 4xx, so it keeps its slot. Third, as defence in depth for every route that reaches argon2id (login also runs a dummy hash for unknown e-mails), bound concurrent argon2id work. Use a semaphore of about runtime.NumCPU() slots that the password hasher owns and that is injected through the constructor, in line with the repository's no-package-state rule. Regression test: on a store whose AdminExists returns true, Complete returns ErrAlreadyCompleted without hashing. Assert this through TotalAlloc staying under 1 MiB or through a hasher seam.
- **Fingerprint:** `internal/setup/service.go:Complete:argon2id-before-already-completed-check`

### 4.4 A managed host's returned facts can replace the pinned SSH options (and add a ProxyCommand) through pulsix_ssh_common_args (medium)

- **Location:** `internal/worker/runner/runner.go:191` → `internal/worker/runner/inventory.go:368`
- **Lower-trust principal and conditions:** The attacker controls a managed host targeted by a run, so it can control the JSON its modules (or the setup module) return. That could be a compromised host, or an impostor accepted by trust-on-first-use for an unpinned host. No Pulsix account is needed.; The run opens another SSH connection to that same host after the fact is returned, which is any multi-task play or any play with gather_facts. The single-task ad-hoc playbook (playbook.go:189-195, gather_facts false) offers no later connection.; Default inject_facts_as_vars=True, which the worker does not change (ansible-core 2.21.4 in the worker image; the default is deprecated for removal in 2.24). With PlayUID set, the ProxyCommand runs as the play uid with group access to the run's work dir. In the embedded worker it runs as the manager uid, which was not examined here.
- **Reproduction:** A compromised managed host (or a TOFU impostor of an unpinned host) in a Pulsix organization that answers a playbook run's module invocation with crafted ansible_facts. In the worker image (noixdev/pulsix-worker:dev, ansible-core 2.21.4) with no network, reproduce the worker's run layout with dummy data. Use an executable inventory script whose host 'victim' (127.0.0.1:2222) has pulsix_ssh_common_args='-o StrictHostKeyChecking=yes -o HostKeyAlias=pulsix-host-<uuid>'. Use an extra-vars file equal to forcedConnectionVars (ansible_ssh_common_args="{{ pulsix_ssh_common_args | default('') }}", ansible_ssh_args with -F ssh_config and the run's known_hosts). Use ansible.cfg as rendered by ansibleCfgText and the subprocess env from Runner.subprocessEnv. Use a play with gather_facts false. T1 is ping over ssh (ignore_unreachable). T2 is a custom module that prints the payload JSON; it runs with connection: local to stand in for module output produced by the managed host's python, and is parsed and cleaned by the same action-plugin path. T3 debugs the resolved values. T4 is ping over ssh (ignore_unreachable). T5/T6 stat the marker locally. Run ansible-playbook -vvvv -i inv.sh -e @extravars.json play.yml and compare the 'SSH: EXEC' lines of T1 and T4. Then check for /tmp/run/h12-marker. Repeat with ANSIBLE_INJECT_FACT_VARS=False (control), and again with the carrier renamed to ansible_ssh_pulsix_common_args (fix check).
- **Result:** Audit artifacts of the validation run (agents/v08-ssh-pins/artifacts/evidence.txt, evidence2.txt, evidence3.txt; not repository sources) record the following. In the worker image, ansible-core 2.21.4 reports INJECT_FACTS_AS_VARS(default) = True with the run's ansible.cfg, and its clean_facts strips returned facts matching the magic variable names, the common connection vars, ^ansible_<connection>_, ansible_become_* and ^ansible_.*_interpreter$, so a pulsix_* fact is not matched. Run A (worker defaults): on T1 the ssh command line carried -o StrictHostKeyChecking=yes -o HostKeyAlias=pulsix-host-11111111-1111-1111-1111-111111111111. After T2 returned ansible_facts.pulsix_ssh_common_args, both pulsix_ssh_common_args and the forced ansible_ssh_common_args resolved to the module-supplied '-o StrictHostKeyChecking=no -o ProxyCommand="touch /tmp/run/h12-marker"'. On T4, ssh ran with -o StrictHostKeyChecking=no -o 'ProxyCommand=touch /tmp/run/h12-marker' and no HostKeyAlias, and the marker file was created on the controller (MARKER_EXISTS=True; the file listing shows it). Run B (ANSIBLE_INJECT_FACT_VARS=False): the pinned options stayed on the T4 ssh command line and MARKER_EXISTS=False. Run C (carrier renamed to ansible_ssh_pulsix_common_args, defaults otherwise): clean_facts stripped the returned fact, the pinned options stayed, and MARKER_EXISTS=False. Not exercised: module output over a real sshd from a remote host, and the ansible-runner wrapper (it sets only a jsonfile fact cache and nothing about fact injection).
- **Impact:** It crosses the managed-host to worker boundary. The host removes its own pin and runs arbitrary commands on the worker as the play uid. That uid can read every credential key file, the inventory document, vault password files and extra vars of the run, which means credentials for the other hosts in the run. It can also rewrite the run's known_hosts to drop other hosts' pins for the rest of the run. The worker's mTLS identity (0700 dir) and other organizations are not shown to be reachable, and the between-job sweep limits persistence of play-uid processes.
- **Priority:** likelihood low (The attacker must already control a managed host targeted by a run (or impersonate an unpinned host at first contact). After that, exploitation is deterministic: any later SSH task to that host in the same run, which most playbooks have, especially with fact gathering on.); impact high.
- **Smallest fix:** Keep the per-host pinned options under a name that ansible-core strips from returned facts, and stop injecting facts as top-level vars. Rename pinnedCommonArgsVar to an ansible_ssh_-prefixed name such as ansible_ssh_pulsix_common_args, which clean_facts removes through its ^ansible_ssh_ rule (verified in run C). Each in-flight call yields at most one job.
- **Reproduction:** A worker whose certificate is being revoked keeps ClaimJob calls in flight. Calls that the interceptor authorized before the revocation committed still claim and receive job payloads after it. The fixture lets the interceptor's lookup succeed and marks the serial revoked immediately afterwards, which is the same race fixture TestRevocationBetweenAuthAndTrackEndsTheStream uses for RunEvents. - **Impact:** The revoked worker receives the payload, possibly including revealed credentials, of at most one queued job per in-flight call. The jobs come from its own org and zone, right after revocation, and the same worker could have claimed them moments earlier. It is a non-atomic cut of an intended revocation guarantee, not a cross-tenant or cross-zone leak. The stray 'running' assignment is later recovered by the reaper.
- **Priority:** likelihood low (This requires a worker certificate under active revocation, a queued job in its own zone, and a ClaimJob call that straddles the revocation commit. The window is short. A malicious worker can widen it by keeping many calls in flight, and Touch blocking on the revoke row lock helps.); impact low.
- **Smallest fix:** Bind the claim to the worker's current registry state inside the claim transaction. For a worker claim (workerID valid), first run a locking read of the worker row, SELECT 1 FROM workers WHERE id = $1 AND status = 'active' FOR SHARE, and claim nothing if it returns no row. Optionally also require an unrevoked worker_certificates row for the presented serial. Under READ COMMITTED this serializes with RevokeWorker's row update. A claim that waits on an open revocation re-reads the committed 'revoked' row and claims nothing. A claim that locks first commits before RevokeWorker can proceed, so RequeueWorkerJobs (which runs after the revoke commit) takes the job back. As defence in depth, mirror RunEvents: after Claims.Claim returns a job, re-run lookupWorker. On refusal, hand the job back through a new Claimer release port that requeues it bound to this worker id, drop the registry binding, and return Unauthenticated instead of the payload. Regression tests: the revokeAfterLookup fixture on ClaimJob must yield Unauthenticated with no job and no registry binding, and a store integration test must show that ClaimFor for a revoked worker returns nil.

## 6. Hardening notes and positive patterns

Hardening notes are not findings: each describes a missing defence-in-depth layer or a risk with no demonstrated boundary violation. They are grouped by the coverage unit whose hunter raised them.

**CI and release workflows — Build, image and release integrity**
- deploy/worker/Dockerfile:69 installs ansible-core/ansible-runner by exact version but without --require-hashes, so transitive PyPI dependencies (jinja2, PyYAML, cryptography, resolvelib, pexpect, python-daemon, ...) float at release-build time. A hashed requirements lock would bind them. ci.yml's e2e-ansible pip install (line 261) has the same gap.
- Released images are pushed unsigned and without consumer-verified attestation, and the compose stack defaults to PULSIX_VERSION=latest (docker-compose.yml:40,123,155; .env.example). Pinning a version or digest in .env.example and signing images (e.g. keyless cosign bound to release.yml@refs/tags/v*) would let consumers verify the producer.
- deploy/compose/docker-compose.yml:16 pins timescale/timescaledb:2.30.0-pg18 by tag only, unlike traefik (line 208), which is pinned by digest.
- tag.yml's commented workflow_run block (lines 38-41) filters only on `branches: [main]`, which matches a triggering run's head_branch. A fork pull request from a branch named main also has head_branch main. Before re-arming, also require github.event.workflow_run.event == 'push' and head_repository.full_name == github.repository.
- release.yml's guard CI query (lines 52-54) should add &event=push&branch=main so a pull_request or feature-branch run of the same SHA cannot satisfy it.
- Traefik (proxy profile) mounts /var/run/docker.sock; ':ro' does not restrict the Docker API. A socket proxy limited to container list and inspect would keep an internet-facing proxy compromise from becoming host root.
- The compose worker shares the default network with db (5432) and the manager's 8080. A separate network attaching worker only to manager would remove operator-code reachability to Postgres (currently guarded only by the random DB_PASSWORD, with pulsix_app NOLOGIN). With the proxy profile, manager 8080 also stays published as plain HTTP on all host interfaces.
- deploy/compose/docker-compose.test.yml publishes Postgres (55432, password 'pulsix') and Mailpit (45025/48025) on all host interfaces of a developer or CI machine. Binding them to 127.0.0.1 would avoid LAN exposure.
- install.sh verifies the agent binary against a checksum from the same origin. Templating the expected sha256 into the served script (the manager knows it at render time) would drop the second fetch, though the trust root (TLS to the manager URL) is unchanged.
- internal/app/workerbundle.go:4 says the worker mounts the bundle volume read-only, but compose mounts it writable for renewal (docker-compose.yml:151-153, 188). The comment is stale; no security effect found.

**Host agent client process (root on every monitored host) — Manager-supplied enrollment, renewal and check configuration handled by a root client**
- internal/agent/session.go:448 and internal/agent/checks/scheduler.go:203: the agent trusts interval_seconds from the manager; a value <= 0 would panic time.NewTicker and crash-loop the root agent. Manager-side bounds (internal/checks/definitions.go:208, DB CHECK 10..86400) make it unreachable today; clamp or skip non-positive intervals agent-side as defence in depth (regression: decodeCheckConfig with IntervalSeconds 0 must not panic).
- internal/agent/enroll.go:86-97: the enrollment answer's leaf certificate is checked only for key match, not chained to the pinned CA with ClientAuth EKU as Identity.Replace does (identity.go:265, 303-319); reuse verifyAgainstStoredCA-equivalent logic on the pinned block before SaveEnrollment for symmetry.
- internal/agent/checks/disk.go:77-121: an explicit 'mounts' list is statfs'd verbatim as root (absolute or relative, any path) and the error text is reported back, giving org members who can edit check definitions a coarse path-existence oracle on the host; ProtectHome/PrivateTmp/ProtectProc limit it. Consider requiring absolute paths that are actual mount points (manager-side validateParams in internal/checks/definitions.go:149-158).
- deploy/install.sh:118-129: PULSIX_ENROLL_TOKEN stays in /etc/pulsix/agent.env (0600 root) after enrollment and is re-presented automatically whenever the identity becomes invalid; tokens can carry up to 100 uses (internal/agents/service.go:286). Consider blanking the token from agent.env after the first successful enrollment.

**Setuid exec helper — Privilege drop to the play uid**
- deploy/worker/Dockerfile:111-123 says the 4750 root:pulsix helper can be invoked 'only' by the worker, but pulsix-play's primary gid is 65532, so every play can execute it as well. It gains nothing today (both modes end as uid 65533/gid 65532), but the comment's safety argument ('4750 removes the question entirely') is wrong. Fix the comment, or give the play a gid the helper's group does not include.
- Helper children that have dropped to the play uid cannot be killed by the worker (EPERM), so exec.CommandContext timeouts in sweepPlayUID (removeGrace), removeAsPlayUID and signalGroup (signalHelperTimeout) do not bound them. A play-uid process that SIGSTOPs such a child could make CombinedOutput wait indefinitely and wedge the claim loop or shutdown. Source-only reasoning, not validated: the sandbox has a single uid. Consider cmd.WaitDelay plus a kill through the helper's signal mode.
- hardenIdentityDir (internal/worker/loop.go:456-478) hardens only filepath.Dir(CertPath). With an explicit bundle whose PULSIX_WORKER_KEY lives in a different directory (for example a /run/secrets mount, often 0444), the key is not protected from the play uid. Harden or check filepath.Dir(KeyPath) as well, and refuse a group- or world-readable key file when PlayUID is set.
- findRequirements (internal/worker/sync.go:170-181) uses os.Stat, so a symlinked requirements.yml makes ansible-galaxy (as the worker uid) read any worker-readable file. This falls under the conceded 'repo content runs as the worker uid' model of the rejected run-1 claim. Lstat it and refuse symlinks, or resolve the path and keep it inside the clone.

**Agent disk plugin mount points reported as check items — Whole-batch refusal of check results on one over-limit item**
- internal/agent/checks/disk.go: Usage (statfs) is called serially per mount with no per-mount deadline; a hung FUSE/NFS mount blocks the disk plugin goroutine and every later mount in sorted order (gopsutil ignores ctx inside the syscall). Run each Usage in a goroutine with a timeout and report the stuck mount as an error observation.
- internal/checks/samples.go: Observation.Err and Label have no length bound (only check_key/item/metric are bounded). They are not indexed and only the gRPC 16 MiB receive cap applies, so this is limited to the sending host's own rows; consider a cap mirroring MaxFactsValueLen.
- internal/checks/definitions.go validateParams: disk 'mounts' and service 'units' entries should be held to the same MaxItemLen/breaksLine contract the ingest enforces, so a definition can never make every agent's batch refusable (variant of the poison-record candidate).
- internal/api/job_sse.go: each job-log SSE stream polls every 500 ms and re-checks access every 2 s with no per-user or per-org stream cap; cost is linear in open streams.
- Unpaginated org reads (fleet, items, rules, checks, alert routes, rotations) are linear in the reader's own authorized org scope with no N+1 fan-out, but there is no per-tenant quota on hosts, tags, groups or definitions, which multiplies the heartbeat-resolve candidate.

**Agent enrollment and certificate renewal — Agent enroll token host binding and renew key binding**
- internal/agentapi/service.go Renew: the renewal CSR's public key is not compared with the presented leaf's key, unlike the worker RenewCertificate (backlog 2.64 peerKeyKey). No current impact because every renewal revokes all previous serials of the host, but binding the key would make the two renewal paths equivalent.

The address becomes ansible_host in internal/inventory/render/render.go:364-368 and internal/worker/sysjob.go:76-81 without ansiblevars.Inert, so Jinja in it is templated on the worker, including inside admin-started rotation and bootstrap system jobs. **Monitoring and alerting REST CRUD handlers — Per-object scope and body-referenced child ids**
- GET /api/v1/orgs/{org}/schedules/{id}/notifications is gated by templates.read (viewer) yet returns each bound channel's id, name and kind (notify_rules_handlers.go:50-62, ListScheduleNotifications), while channels.read itself is operator-only (roles.go:137); likewise GET /alerts/{id} returns escalation_channel_ids to checks.read viewers (alert_handlers.go:183-191). - POST /api/v1/setup/complete is first-caller-wins with no one-time setup token (documented design, run-1 report section on setup). A manager reachable from the network before the wizard runs can be claimed by anyone. Printing a one-time setup token to the manager log would close this.

A second instance admin can point the stored SMTP credential at a server they control and capture it through POST /admin/settings/smtp/test. Tokens stop working only because requireOrg needs a live membership, so re-inviting or re-adding the same user silently revives their old tokens, capped at the new role. Revoke the user's org tokens on removal.
- GET /api/v1/me/activity (ListAuditEventsForActor) returns a user's own audit events from organizations they have since been removed from. The route comment says 'across every organization they belong to'. These are the user's own actions, so this is not a boundary crossing, but the comment and the query disagree.
- The job log SSE re-check (backlog 7.22) checks the session by id. A session secret rotated by a later MFA re-proof (MarkSessionMFAComplete) does not end a stream opened with the earlier cookie. This is not a stated revocation event, so it is not a finding.

**Agent install command and install.sh token argument — Enrollment token exposed to local readers on the target host during installation**
- agentInstallCommand appends `--name <nameHint>` unquoted (agent_handlers.go:355). The API allows any 64-character hint, and only the SPA enforces NAME_RE. A hint with spaces or shell metacharacters produces a command that breaks or runs extra commands as root. The hint's author is the only one who receives the command, so no principal is crossed, but the value should be shell-quoted or restricted server-side to the CheckAgentName shape.

An admin removing someone therefore cannot tell which pending tokens to withdraw. **Public and enrollment endpoints, worker queue, agent streams — Shared manager and worker capacity**
- Login/TOTP/passkey-finish/invite-accept limiter (auth_rate_limit.go) allows 20 concurrent in-flight reservations per address and refunds successful attempts, so one address can run 20 concurrent 64 MiB argon2id hashes (~1.25 GiB) per minute and any credential holder can log in at unlimited rate; add a process-wide argon2id concurrency semaphore (also fixes the setup/complete candidate's amplification).
- Webhook HookIPLimit (triggers/receive.go:73-99) is consulted only after the trigger lookup, HMAC over up to 1 MiB and delivery-row write have run, so it hides outcomes but sheds no work; check the limiter's Refused() before receive() for already-exhausted addresses.

- gRPC server applies the 16 MiB MaxRecvMsgSize to unauthenticated callers before the auth interceptor and sets no MaxConcurrentStreams; consider a small per-method limit for Enroll and an explicit stream cap.
- http.Server sets only ReadHeaderTimeout (cmd/manager/main.go:207-211): add ReadTimeout/IdleTimeout (respecting SSE routes) or a connection cap when the manager port is exposed without a proxy.

**Login and session cookie — Session issuance, lookup and invalidation**
- SecondFactors.DeletePasskey and DisableTOTP (internal/auth/second_factor.go:36-76) check 'not the last factor' and then delete outside a transaction. Two concurrent removals (two passkeys, or the last passkey plus TOTP) by a fresh session can leave the account with zero factors, so the next password login enters enrolment mode. Only the account holder or someone already holding a fresh MFA session can do this. Fix: do the count and the delete in one transaction with a row lock on the user.
- Removing a factor (TOTP disable, passkey delete), regenerating recovery codes and logging out do not revoke the account's other sessions. A session opened with a now-removed passkey or TOTP secret stays MFA-complete until its 12 h TTL. There is no 'sign out everywhere'. Consider RevokeSessionsForUser except the current session on factor removal.
- POST /auth/login and passkey login do not revoke the session whose cookie they overwrite (account switch). The old session stays valid server-side until expiry.
- No Strict-Transport-Security header (internal/api/security_headers.go) and no __Host- cookie prefix. Both make cookie tossing from a sibling host or a plaintext hop easier. See the CSRF candidate.
- requireFreshFactor compares the manager's time.Now() with mfa_at stamped by the database's now() (auth.sql:30). Clock skew between the manager and Postgres widens or shrinks the 5-minute step-up window.
- /auth/totp/confirm has no requireFreshFactor. It is safe today only because the pending secret comes from a fresh, code-checked /auth/totp/enrol and is known only to its caller. A future path that sets a pending secret without that gate would inherit the gap.

**SSH credential rotation group — Worker results driving credential re-key and old-key revocation**
- Credential PATCH (credentials.Service.Update, internal/credentials/service.go:258) is not refused while a rotation group of that credential is in flight. The group's finalize (finishRotation) then overwrites the admin's newly supplied material with the pending key, and the revocation removes only the rotation-start key (PreviousPublicKey). This is a lost update by the same principal (admin), not a privilege gain. Refuse the update, or abort the group, while CountActiveRotationJobs > 0.
- Rotate's count==0 immediate re-key path (internal/credentials/rotate.go:95) bypasses the per-credential lock and the in-progress check in CreateRotationGroup. If the references are dropped while an older group or its revocations are still queued, an immediate re-key can interleave with that group, so its revocations log in with a key the targets never received. Admin-only and visible as failed jobs. Taking the same advisory lock and in-progress check on the immediate path would close it.
- Bastion rotation targets have no post-install verification (rotation.go EnqueueRotation comment): a rotate_key that reports success on a jump host seals the new key and queues revocation of the old one without proving the new key authenticates there. A wrong account or AuthorizedKeysFile causes lockout of the jump host and everything behind it. Consider a hop probe as the bastion's follow-up test.
- snapshotHostTargets (internal/jobs/rotation.go:552) drops snapshot hosts whose row was deleted, on the premise that their authorized_keys left with the host. Deleting a host record does not wipe the server, so the old key stays authorized there. Only a warning is logged; surfacing it on the rotation result would let the admin clean up out of band.
- Failed revoke_key jobs are not retried and no rotation-level outcome records that the old key is still installed. The rotation is only as complete as the operator's attention to individual job failures.

**Public webhook receivers — Untrusted webhook values reaching Ansible**
- internal/triggers/validate.go checkMappingTargets: for a template without an extra-vars schema a mapping may target Ansible engine variables (ansible_become_user, ansible_become_flags, ansible_become_exe, ansible_python_interpreter, ansible_shell_executable, ansible_host, ansible_user ...), because schema.ValidFieldName does not apply the ansible_/pulsix_ reservation that schema validation applies to declared fields. Ansible interpolates several of these unquoted into the remote shell command, so the __ansible_unsafe marker does not make such a value inert. It requires an operator to choose such a target, so it is not a boundary crossing, but refusing reserved prefixes (schema.reserved) for mapping targets, and for untrusted overrides in ValidateOverrides, would make the schema and schema-less paths consistent with the spec's 'payload values are untrusted' promise.
- internal/ansiblevars/untrusted.go Inert still wraps only string values; object keys inside a mapped webhook object reach the extra-vars file unwrapped and pass CheckUntrusted. Safety rests on Ansible never templating dictionary keys, which no repository test verifies for ansible-core 2.21.4 (internal/worker/runner/unsafe_test.go covers values only). Unchanged since run 1; refusing keys containing '{{', '{%' or '{#' in CheckUntrusted is a cheap close.
- internal/triggers/auth.go and receive.go still do not deduplicate deliveries (X-GitHub-Delivery, X-Gitea-Delivery, X-Gitlab-Event-UUID): a captured signed request replays within the 5-minute window, or indefinitely for presets without a timestamp. Unchanged since run 1.
- internal/triggers/service.go Update can remove timestamp_header without rotating the secret; a request captured while the timestamp was on (HMAC over '<ts>.<body>') then verifies as an untimestamped delivery with body '<ts>.<body>', which starts a run for an empty mapping. Unchanged since run 1; rotate the secret or domain-separate the MAC input when the timestamp mode changes.
- internal/jobs/queue_sql.go buildPayload: a webhook-mapped limit replaces the template's own limit (including with '' or '*'), so the sender can widen the run to the template's whole resolved scope; intersecting ('<template limit>:&<webhook limit>') would keep the template's narrowing. Spec-intended, unchanged since run 1.
- internal/triggers/receive.go HookIPLimit comment says a single source 'cannot probe ids or secrets at will', but the limit replaces only hidden 404 outcomes with 429 after the full check runs; a correct secret still answers 202 once the budget is spent. The 256-bit secret makes this moot; the comment overstates the control. Unchanged since run 1.

**Job run output, events, stats and error text — Redaction of secrets from viewer-readable job output**
- internal/worker/runner/redact.go: Python repr spellings (a secret containing both quote kinds is shown with \' escapes, and control characters as \xNN) are not listed. Ansible error messages that repr a value would bypass literal matching. No producer was confirmed offline.
- internal/worker/runner/redact.go base64Spellings: secrets of 4-7 bytes get no aligned core at some offsets (minBase64Core = 6), and line-wrapped base64 (for example a `base64` command's 76-column output) splits any core. Consider decoding base64-looking runs in display text and redacting there.
- internal/worker/sync.go:219 installRequirements: ansible-galaxy stderr goes into the viewer-readable job error without redactURLs, unlike gitDiagnostic. A requirements.yml src carrying user:token@ would be echoed. This is repository content, not a claim secret.
- Vault-decrypted values are never on the redact list. A playbook that prints a vaulted variable shows it to jobs.read viewers. Consider documenting this or offering no_log guidance.
- redactor.text replaces overlapping distinct secrets longest-first, then lexically. Two equal-length overlapping secrets can leave a few characters of the second one visible.

**Invite acceptance — Invite token to account and membership binding**
- Backlog 7.10 residual (accepted by the project): redeeming an unmailed invite link for an address with no account still creates that account with the redeemer's chosen password (service.go:430-441). The real address holder can then never sign in or accept invitations on the instance, and nothing marks the address as unverified. Consider marking unmailed-redeemed accounts as email-unverified and letting a later mailed invitation (or an instance admin) reclaim the address.
- A signed-in user who accepts an invitation for a different, account-less address (supplying a name and password) gets a new-account session cookie that replaces their current session (member_handlers.go:246-254). This is a same-browser UX hazard, not cross-principal.
- Pending invitations are also not invalidated when the invited role later exceeds the issuer's role (an admin demoted to operator still has outstanding admin invites). This is covered by the same fix as the candidate.

**Notification delivery and instance SMTP dial — Outbound reachability of the manager network from tenant-chosen and admin-chosen targets**
- Unchanged since run 1 (REPORT.md hardening, spec v0.2c section 5): the policy allows 10/8, 172.16/12, 192.168/16, 100.64/10 (except 100.100.100.200) and fc00::/7 by design. Any MFA-complete user can create an org and so gain channels.write, which lets them send blind POST/PUT requests with chosen headers and a templated JSON body to the manager's compose network, the Docker host gateway and other internal services. PULSIX_NOTIFY_ALLOW_CIDRS can only re-admit addresses and has no deny counterpart, so a multi-tenant operator has no way to restrict this. Consider an instance setting that refuses private ranges for org-defined channels (or restricts org creation), with PULSIX_NOTIFY_ALLOW_CIDRS as the only re-admission.
- Unchanged since run 1: last_error keeps the redacted transport cause, e.g. 'dial tcp 172.18.0.3:5432: connect: connection refused' or 'the endpoint answered 404' (send.go:183-198, 204-221). The test endpoint returns it synchronously, and channels.read (operator) can read it later, which gives an internal port and path oracle. Generic error classes for refused, timeout and status outcomes would remove it.
- Metadata protection is a list of literal addresses (policy.go:42-45). Besides fixing the IPv6 gap in the candidate, consider also refusing other well-known provider link-local or ULA service endpoints by prefix (e.g. fd00:ec2::/112 for AWS's IPv6 service addresses). Pin each one with a policy_test.go case, so a new provider endpoint becomes a deliberate addition rather than an omission.
- The SMTP dial (internal/mail/smtp.go:176-177) applies no outbound policy. That is acceptable because only the session-bound instance admin can set or test the host (setup_handlers.go:203-245). If SMTP settings ever become org-scoped, they must go through the same policy.

**Worker enrollment snippets (docker run and compose) — Worker enrollment token exposed through docker argv and persisted container or compose config on the worker host**
- The compose snippet persists the (soon spent) token in a compose file and the container's Config.Env (docker inspect); readable only by docker-group/root-equivalent accounts or per the operator's file mode, and the token is single use with a 1 h TTL, so no lower-trust reader holds live power; consider an env file with 0600 or a prompt to delete it after enrollment.
- The worker keeps PULSIX_ENROLL_TOKEN in its own process env for the container lifetime; when a valid bundle already exists (e.g. a reused pulsix-worker-<name> volume) the token is ignored and stays unredeemed for up to 1 h. Children are stripped, but logging a warning and recommending withdrawal of the unused enrollment would close the window.
- worker_snippets.go interpolates name, ServerName and Addr into shell text unquoted; name is constrained by namePattern and the endpoint values are manager config, so no injection today, but quoting would keep it robust.

**Embedded worker zone and org selection — Embedded worker bound to one organization while new organizations can be created**
- internal/app/embedded_worker.go:112-134: the single-organization guard is evaluated only when the default zone is first resolved. Once bound, the embedded worker keeps serving the first organization even after any MFA-complete user creates further organizations via POST /api/v1/orgs (internal/api/org_handlers.go:71), although deploy/compose/README.md states it serves 'only on an instance with a single organization'. Combined with a custom Ansible-capable manager image, the first org's playbook authors could read the manager's master key and DB URL (same uid, /proc/<pid>/environ) covering organizations created later. This is within the documented 'everyone who can write playbooks is trusted with the whole instance' precondition, so not a finding; suggested hardening: re-check the organization count on each claim tick and stop the embedded loop (or refuse organization creation while PULSIX_EMBEDDED_WORKER=1), and make the README wording match.
- internal/worker/runner/runner.go:469 stripPrivateEnv removes PULSIX_* from play subprocess env, but for the embedded worker plays run under the manager's own uid (no play-uid helper in the manager image), so a play can still read the manager process's environment via /proc; env stripping is not a boundary there. Documented and accepted; a future Ansible-capable manager image would need a play uid drop to change this.

**gRPC interceptor — Client certificate to worker or agent principal**
- internal/grpcsrv/events.go eventAt clamps only future timestamps; a worker may date events arbitrarily far in the past. AppendJobEventSQL's max(seq) filter (at >= job created_at, jobs/events.go:469-471) assumes 'an event's at is never before the job existed', so a past-dated event is excluded from later max(seq) computations and its seq is reissued. The PK (job_id, seq, at) admits the duplicate, and recordTest/recordSync's ORDER BY seq DESC LIMIT 1 becomes ambiguous; past-dated rows also land in compressed/retained-early chunks. Only the producing worker's own job is affected (same principal). Clamp at to [job created_at, now] at append.
- hosts.RecordConnectionTest / validHops store the worker-asserted hop State (pinned/changed) without recomputing it from Fingerprint vs the stored bastion pin. After 7.23 the route and time are bound, but a worker of one zone whose host routes through an org-wide bastion can still flip that bastion's latest state (clear or raise 'changed') for other zones' claim guards. The worker-side pinned known_hosts still enforces the key. Derive State server-side from fingerprint vs pin.
- RunEvents' bindStream (events.go) consumes the (job_id, worker_token) pair without comparing the job's worker_id to the authenticated worker. Only the claimer ever receives the token, but binding it to the identity as well would make a leaked token useless to any other worker certificate and keep the revocation cut (tracked by w.ID) aligned with the job's claimer.
- ClaimJob stores req.version (free text, bounded only by the 16 MiB gRPC receive limit) into workers.version on every poll; cap its length.

**Shared definitions projected into every organization — Installation-level definitions vs org-owned projected rows**
- InsertProjectedTemplates still joins git_repos on (org_id, shared_repo_id) without LIMIT. Today this is safe only because nothing outside internal/shared writes shared_repo_id. A partial unique index on git_repos (org_id, shared_repo_id) WHERE shared_repo_id IS NOT NULL would make that invariant structural, as would the same for job_templates.shared_template_id and check_definitions.shared_definition_id. Note that adding the index is additive.
- CreateWithProjections, and its template and check siblings, read ListOrganizationIDs in their own READ COMMITTED transaction. An organization whose CreateOrg transaction is in flight at the same time (it ran ProjectAll*Into before the definition committed, and committed after the definition's org list was read) ends up with no projection of the new definition. That contradicts spec decision 4 ('appears in every organization, including later ones') and the doc comment's claim that the window is closed. It is a lifecycle or monitoring gap, not an attacker-controlled crossing. Serialising the two (for example with an advisory lock taken by both CreateOrg's projection step and Create*WithProjections), or adding a reconcile pass, would close it.
- Changing a shared repository's url (an instance-admin action) clears every projection's git host-key pin (UpdateProjectedRepo url_changed). Each organization's own deploy credential is then presented to the new URL on the next sync without the organization re-confirming. The instance admin is already trusted with the repository content those organizations run, so this is not a boundary crossing. Still, surfacing the url change to each organization, or requiring a re-pin, would make the credential retargeting visible.

**Managed-host and jump-host SSH connections from the worker — Host-key pin enforcement on every SSH path**
- parseHop (internal/worker/runner/sshconfig.go:75) splits user@host at the FIRST '@', but sshconf.usernamePattern (internal/sshconf/service.go:54) allows '@' inside bastion usernames, and OpenSSH splits at the LAST '@'. A pinned or key hop with username 'alice@corp' gets an alias block with 'HostName corp@<addr>' and 'User alice' (harness evidence.txt). The connection fails closed, so only availability is affected. Fix: cut at strings.LastIndex(hop, "@") or forbid '@' in bastion usernames.
- mergeInventory's '!ok' branch after parseProxyJump (internal/worker/runner/inventory.go:88-90) continues without checking pinnedHop. A route with a pinned bastion whose args use another spelling (-J, -oProxyJump=) passes unaliased (harness: err=nil, 0 blocks). The renderer (internal/inventory/render/render.go:385) and sysjob (internal/worker/sysjob.go:105) always emit '-o ProxyJump=' after group vars, so this cannot be reached today. Failing closed there when pinned != "" would make the rule complete.
- claimBastionKeys (internal/jobs/system_claim.go:321-323) returns empty pin maps when q.bastionPins is nil, while claimHostKeys fails closed on the same wiring gap. Production wiring sets it, but the bastion-target rotate/revoke path would ship no pins if it were unwired.
- jobs_require_pinned_hosts (internal/jobs/settings.go:87) covers host targets only. Bastion hops and bastion rotation targets are never required to be pinned (the scope documented in backlog 2.44). Consider extending the org setting to route bastions.

**Whole repository — Secrets, debug gating and basic exposure**
- .gitignore ignores only .env; add .env.*, *.pem, *.key and local identity/data directories so a worker or agent identity copied into the tree is not committed by accident.
- No Strict-Transport-Security header is set and the manager listens in plain HTTP; when PULSIX_PUBLIC_URL is https, emit HSTS from securityHeaders (internal/api/security_headers.go).
- web/src/api/hooks/useJobs.ts:186 builds the EventSource URL from router params without encodeURIComponent (client-side path traversal to same-origin GET only; no impact today). Encode org and id the way openapi-fetch does.
- Invitation tokens travel in the SPA path /invite/<token> (tenancy/service.go Invite link), so chi middleware.Logger writes them to the manager's access log on the page load. Consider a URL fragment, or redacting that path in the logger.
- Anonymous GET /healthz returns the build version (internal/api/api.go:409-416). Consider omitting it, or returning it only to authenticated callers.
- Webhook channels may target RFC1918/ULA addresses by design (internal/outbound/policy.go). Since any MFA-complete user can create an org and own it, every user gets a blind arbitrary-method, arbitrary-header HTTP client into the manager's private network (compose services, other hosts) with a status-code oracle. Consider an instance-level switch that denies private ranges unless PULSIX_NOTIFY_ALLOW_CIDRS admits them.
- Email channels and the test-notification route let any org admin (so any user, through their own org) send to 20 arbitrary recipients through the instance's SMTP relay with org-chosen names in the content. Consider per-org send quotas, or limiting recipients to org members.
- internal/api/openapi_doc.go Document() still uses huma's default SchemasPath "/schemas", so the generated spec's $schema links drift from the served /api/schemas. There is no exposure; align it with api.New.
- web/index.html loads a Google Fonts stylesheet that strictCSP (style-src 'self' 'unsafe-inline') blocks. This is a functional issue only: the fonts never load and no third-party request leaks. Self-host the fonts.

Positive patterns observed during the review include: org scoping through `requireOrg` plus row-level security with composite foreign keys between org-owned tables; mTLS identity for workers and agents bound to registry rows and checked on every RPC; single-use, hashed enrollment and invite tokens; webhook values wrapped as `__ansible_unsafe` with JSON-only extra-vars and a fail-closed YAML guard; a resolve-then-dial outbound client that blocks loopback, link-local and metadata addresses without redirects; a minimal, read-back-verified setuid helper; strict CSP and no DOM-HTML sinks in the SPA; SHA-pinned CI actions and digest-pinned base images.
