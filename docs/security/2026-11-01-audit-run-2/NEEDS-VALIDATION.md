# Needs validation

Prioritized leads without severity. Each names the exact fact that source and the local sandbox could not settle, and a bounded plan to settle it. Do not treat them as confirmed vulnerabilities, and do not test them against a live deployment.

## Release guard and registry credentials sit only in workflow code that any branch or tag author supplies

Fingerprint `github-workflows/release.yml:registry-secrets-reachable-outside-release-guard`

release.yml's guard job (release.yml:24-58) is meant to stop a hand-pushed tag from publishing unless the tagged commit is on main and ci.yml passed for it (comment at release.yml:15-23, backlog 1.32). On a `push` event, GitHub runs the workflow file from the pushed commit (GITHUB_SHA). The guard therefore lives in the same file the tag author chooses, and the publish job's only link to it is `needs: guard` (release.yml:61). The release job has no `environment:` key, and no workflow in .github/workflows declares one. DOCKERHUB_USERNAME/DOCKERHUB_TOKEN (release.yml:118-119) and HARBOR_USERNAME/HARBOR_PASSWORD (release.yml:125-126) are therefore repository or organization secrets. GitHub gives those to any workflow run on any branch or tag of the repository that is not a fork pull request. A principal who can push a v* tag, or any branch carrying a workflow that names these secrets, can drop or edit the guard and push noixdev/pulsix-manager and noixdev/pulsix-worker images to Docker Hub and Harbor, including `latest`. Branch protection on main does not stop that principal. The compose stack defaults to `latest` (deploy/compose/docker-compose.yml:40, 123, 155), so an installation that keeps the default would pull such an image into the manager, which holds the master key and DB URL, and into the worker, which holds its mTLS identity and runs plays with job credentials. tag.yml (workflow_dispatch only, tag.yml:37; `contents: write`, tag.yml:46; `secrets: inherit`, tag.yml:61) is the same exposure through another route. A write user can dispatch it from a branch whose tag.yml they edited, and the 7.16 SHA pin applies only to the main copy. Any branch workflow could also reference the secrets directly, so this adds no new principal. A secondary weakness weakens the guard even when it runs from a genuine main release.yml. Its CI query (release.yml:52-54) takes the newest ci.yml run for the SHA with no event or branch filter. ci.yml triggers on pull_request (ci.yml:2), and a pull_request run uses the workflow file from the PR merge ref but reports the PR head as head_sha. A writer who controls a PR's base branch can therefore produce a green ci.yml run for an existing main commit that originally failed CI. This lets a tag-capable writer publish reviewed main code that failed CI. It does not let them publish arbitrary code. Whether the exposure is real depends on hosted facts: who holds write or tag rights without release authority, where the secrets are scoped, and whether Actions is enabled. Local git history shows a single author (946 commits), and backlog 1.44 and 7.17 say workflows are prepared but not enabled while the repo is private. Backlog 7.16 already lists 'registry secrets belong in a protected release environment' as open.

**Claimed root cause:** Release authorization is enforced only in workflow code that the triggering ref supplies: the guard job in release.yml, plus tag.yml when it is dispatched from a branch. The registry push credentials are not bound to a protected GitHub environment with tag-only deployment rules or required reviewers. Nothing outside the attacker-editable workflow file separates a release-authorized principal from any principal who can push a ref. The guard's CI query also accepts a ci.yml run of any event type, so a pull_request run whose workflow came from an attacker-controlled base branch counts as a pass.

### Trace

1. **entrypoint** `.github/workflows/release.yml:10` (on.push.tags "v*" (lines 9-12)): A v* tag push starts the workflow. For push events GitHub runs the workflow definition stored at the pushed commit (GITHUB_SHA), so the tag author chooses which release.yml runs, including one without the guard job.
2. **propagation** `.github/workflows/release.yml:34` (jobs.guard (lines 24-58)): The on-main check (lines 34-42) and the CI-green check (lines 44-58) live in the same tag-supplied file. The CI query at lines 52-54 is `workflows/ci.yml/runs?head_sha=$SHA&per_page=1`, with no event=push or branch=main filter, so it takes the newest ci.yml run of any event for that SHA.
3. **propagation** `.github/workflows/release.yml:61` (jobs.release.needs): The publish job's only dependency on the guard is `needs: guard` in the same file. The job has no `environment:` key, so GitHub evaluates no deployment protection rule (tag pattern, reviewers) before giving it secrets.
4. **propagation** `.github/workflows/tag.yml:37` (on.workflow_dispatch; permissions (line 46); jobs.tag secrets: inherit (line 61)): workflow_dispatch runs the tag.yml of whatever branch the dispatcher selects, with `contents: write` and `secrets: inherit`. A write user who edits tag.yml on a branch bypasses the commit pin at line 60, which protects only the main copy. This adds no new principal, because a branch workflow can name the secrets directly.
5. **sink** `.github/workflows/release.yml:119` (jobs.release: Docker Hub/Harbor login (lines 115-126) and build-push (lines 128-156)): secrets.DOCKERHUB_TOKEN (line 119) and secrets.HARBOR_PASSWORD (line 126) are used with no environment. build-push-action then pushes the vX.Y.Z and `latest` tags of noixdev/pulsix-manager and noixdev/pulsix-worker to Docker Hub and harbor.cloud.noidee.dev.

### Evidence

- `.github/workflows/release.yml:15`: The comment states the intended invariant: a tag is not evidence, a hand-pushed tag must not be trusted, and the thing that publishes does the checking.
- `.github/workflows/release.yml:63`: The comment's safety argument covers fork PRs only. It assumes anyone with write access who creates a tag is fine, which is the assumption the guard was added to drop.
- `.github/workflows/release.yml:125`: Harbor credentials (lines 125-126), like Docker Hub's (lines 118-119), are referenced in a job with no `environment:`. No workflow under .github/workflows declares any environment.
- `.github/workflows/release.yml:53`: The guard's CI query is scoped to the workflow file and head_sha only, with no event or branch filter.
- `.github/workflows/ci.yml:2`: ci.yml also triggers on pull_request. That run's workflow definition comes from the PR merge ref, while its head_sha is the PR head, so it can satisfy the guard's query.
- `.github/workflows/tag.yml:61`: `secrets: inherit` remains, together with workflow_dispatch (line 37) and `contents: write` (line 46). The pin at line 60 binds only the copy of tag.yml that is dispatched.
- `deploy/compose/docker-compose.yml:40`: The manager runs noixdev/pulsix-manager:${PULSIX_VERSION:-latest}. worker-enroll (line 123) and worker (line 155) use the same default, so a pushed `latest` reaches installations that keep it.
- `docs/BACKLOG.md:555`: Backlog 7.16 lists 'the registry secrets belong in a protected release environment (1.38)' as still open outside this repo. That confirms they are not environment-bound today.
- `docs/BACKLOG.md:102`: Backlog 1.44 says the workflows are prepared but not enabled while the repo is private, so today the path may not run at all.

### Blockers

- Hosted fact: the scope of DOCKERHUB_USERNAME, DOCKERHUB_TOKEN, HARBOR_USERNAME and HARBOR_PASSWORD (repository or organization secret, and for an organization secret its repository access list). Source shows only that they are not environment secrets.
- Hosted fact: whether any principal can push a branch or a v* tag, or dispatch workflows, without being authorized to cut releases. This needs the collaborator, team and app/bot list with write access, branch protection on main, and any tag ruleset on refs/tags/v*. Local history has a single author. If every writer is a release manager, the bypass is same-principal and not a vulnerability.
- Hosted fact: whether GitHub Actions is enabled for NoiXdev/pulsix (backlog 1.44/7.17 say it is not while the repo is private), and whether the Docker Hub/Harbor images are published and consumed by any installation yet.
- No safe local check: proving it needs a real GitHub Actions run, and this audit may not contact GitHub or publish anything.

(a) On main, commit a release.yml with a guard job (fails unless the commit is on main) and a release job that prints sha256(REG_TOKEN). Replace tag.yml's `secrets: inherit` with the single declared secret once the shared workflow declares it (backlog 7.16 follow-up).

## A same-site sibling origin can drive cookie-authenticated POST mutations: SameSite=Lax is the only CSRF control, and huma parses a body with no Content-Type as JSON

Fingerprint `internal/api/auth_handlers.go:sessionCookie:same-site-sibling-csrf-no-origin-check`

The pulsix_session cookie is HttpOnly, SameSite=Lax, Path=/, has no __Host- prefix, and no anti-CSRF token or Origin/Sec-Fetch-Site check exists anywhere in the manager's router chain or handlers. Lax stops cross-site requests only. A same-site origin, such as another subdomain under the manager's registrable domain, gets the cookie attached to its subresource POSTs. huma v2.39.1 (api.go Unmarshal) treats an empty Content-Type as application/json, and a local harness showed text/plain and form bodies get 415 while the same JSON body with no Content-Type runs the operation. Under the Fetch standard, a fetch() POST whose body is an ArrayBuffer or typed array sends no Content-Type, so it is a CORS simple request that needs no preflight. Script on a less-trusted same-site host could therefore make a logged-in victim's browser run any POST operation the victim's role allows, without reading the response. For example, an admin victim could be made to invite an attacker-chosen email address at up to admin role. tenancy.Invite refuses only owner, and mails the accept link to that address, so the attacker joins the org. PUT, PATCH and DELETE routes need a preflight and are not reachable this way. Separately, without __Host- a sibling host can set a same-named cookie scoped to the parent domain. After backlog 7.19 it can no longer fix the victim's own session, but it can still log the victim's browser into an attacker-controlled account. Cross-site attackers stay blocked by Lax.

**Claimed root cause:** sessionCookie (internal/api/auth_handlers.go:159-161) relies on SameSite=Lax alone and uses the unprefixed name pulsix_session (internal/auth/middleware.go:13). The api.New middleware chain (internal/api/api.go:369-403: RequestID/Logger/Recoverer, securityHeaders, staticSessionSkip(CookieMiddleware), requireMFAForExplorer) has no Origin, Sec-Fetch-Site or token check for cookie-authenticated unsafe methods, and does not use http.CrossOriginProtection. huma.DefaultConfig is used unchanged for formats (api.go:433), and huma v2.39.1 api.Unmarshal falls back to application/json when Content-Type is empty, so the 415 for text/plain and form types does not stop a POST with no Content-Type.

### Trace

1. **entrypoint** `internal/api/auth_handlers.go:159` (sessionCookie): The session cookie is issued as pulsix_session with Path=/, HttpOnly, Secure only when PublicURL is https, and SameSite=Lax, with no __Host- prefix. A browser attaches it to any same-site request, including a subresource POST from a sibling-subdomain page, which is the lower-trust entry.
2. **propagation** `internal/auth/middleware.go:30` (CookieMiddleware): The first cookie named pulsix_session is resolved to the victim principal. Nothing about the request origin is consulted.
3. **propagation** `internal/api/api.go:374` (api.New middleware chain): The router-level middleware is securityHeaders, then the session lookup, then requireMFAForExplorer (line 403). None checks Origin, Sec-Fetch-Site or a CSRF token for unsafe methods. huma.DefaultConfig at line 433 keeps huma's empty-Content-Type-to-JSON fallback.
4. **sink** `internal/api/member_handlers.go:142` (POST /api/v1/orgs/{org}/invites): An example state change that needs only the ambient cookie: requireOrg(PermMembersManage) passes for an admin victim, and tenancy.Invite (internal/tenancy/service.go:331-353) creates an invite at up to admin role and mails the accept link to the attacker-chosen address. Every other cookie-authenticated POST operation is reachable the same way. The harness drove one of them, mfa_handlers.go:164.

### Evidence

- `internal/api/auth_handlers.go:161`: SameSite: http.SameSiteLaxMode is the only cross-origin restriction on the session cookie.
- `internal/auth/middleware.go:13`: CookieName = "pulsix_session" has no __Host- prefix, so a sibling host can set a same-named cookie for the parent domain and the browser sends it too.
- `internal/api/api.go:403`: This is the last router-level middleware before the routes. A source grep of internal/ and cmd/ finds no Origin, Sec-Fetch-Site, CSRF/XSRF or CrossOriginProtection handling.
- `internal/api/api.go:433`: huma.DefaultConfig is used without changing Formats. In huma v2.39.1, api.go:361-365 maps an empty Content-Type to application/json ("Default to assume JSON since this is an API").
- `internal/api/mfa_handlers.go:164`: Local harness (agents/h06-session-auth/artifacts/evidence.txt) against the real huma config and this operation: text/plain, text/plain;charset=UTF-8 and application/x-www-form-urlencoded returned 415. The same body with no Content-Type returned 200 with a session-upgrading Set-Cookie and one MarkSessionMFAComplete UPDATE, and returned 401 'invalid code' for a wrong code.
- `internal/tenancy/service.go:332`: Invite refuses only invalid roles and owner, so a forged invite can grant admin, and the accept link is mailed to the request's email (line 352).

### Blockers

- Deployment fact not in source, and decisive: whether any deployment's manager hostname shares a registrable domain with a less-trusted origin that can run script, such as another tenant app, a user-content host or a compromised or third-party subdomain. Without such an origin, SameSite=Lax blocks every cross-site variant and this is defence-in-depth hardening only.
- No browser can run in the approved sandbox. The Fetch standard defines the remaining behaviour: a BufferSource body sets no Content-Type, so the POST is a CORS simple request with no preflight, and a Lax cookie is attached to same-site subresource requests. It has not been observed end to end, and schemeful same-site means an http:// sibling counts as cross-site in Chromium but may not in every browser.

**Local plan:** On an isolated, loopback-only browser fixture, map app.example.test and evil.example.test to 127.0.0.1 and run the manager over HTTPS with a self-signed CA, a disposable database and dummy data on app.example.test. Log in a dummy admin with completed MFA. From an HTTPS page on evil.example.test, run fetch('https://app.example.test/api/v1/orgs/<dummy-org>/invites',{method:'POST',credentials:'include',mode:'no-cors',body:new TextEncoder().encode('{"email":"x@example.test","role":"viewer"}')}). In the devtools network log, check there was no preflight, no Content-Type, and that the pulsix_session cookie was sent. Check that an invite row for x@example.test appears and that the audit log names the victim. Repeat from a cross-site origin (evil.other.test) and confirm no cookie is sent and the request returns 401. Then wrap the router in http.CrossOriginProtection, or add a Sec-Fetch-Site/Origin check for unsafe methods on cookie-authenticated requests, and confirm the same-site request is refused with 403 while the SPA keeps working.

**Owner-observed check:** The owner lists every hostname under the manager's registrable domain and confirms whether any of them serves third-party or user-controlled content or script, is run by a less-trusted party, or is reachable over plain HTTP. If none does, record this as a hardening item: add a Sec-Fetch-Site/Origin check, require Content-Type: application/json on bodies, and rename the cookie to __Host-pulsix_session when Secure is set.

## Worker enrollment token placed in docker CLI argv on the worker host before redemption

Fingerprint `internal/api/worker_snippets.go:workerSnippets:enroll-token-in-docker-argv`

When an org admin adds a worker, the API returns a docker run snippet that passes the one-time worker enrollment token (id, secret and CA pin, pxw1 format) as `-e PULSIX_ENROLL_TOKEN=<token>`. The README tells admins to run that command on the worker machine. The token therefore sits in the docker CLI's command line for as long as that process runs. With `-d` the CLI exits once the container has started, but on a fresh worker host it first pulls the noixdev/pulsix-worker image, which takes seconds to minutes. The container redeems the token only after it starts. On a Linux host where /proc is mounted without hidepid, another local account that is not root and not in the docker group can read /proc/<pid>/cmdline during that window. It can then call the anonymous Enroll RPC (rate-limited per IP, needs no client certificate) with the token and a CSR for its own key. Redemption checks only the secret hash, that the token is unused and that it has not expired. The manager signs the attacker's CSR for the org, zone and worker name the admin chose and marks the token used in the same transaction. The legitimate container's Enroll is then refused, and its restarts are refused too. The rogue holder of the certificate is an authenticated zone worker. It can claim that zone's jobs and receive the decrypted credentials they carry until an admin notices and revokes it. The audit entry 'enrolled from <ip>' shows the worker host's own address, so it does not reveal the swap. The compose variant writes the token into a YAML file whose permissions the snippet leaves to the admin's umask; that file is exposed until `docker compose up` redeems the token. Source fully establishes the code path. Whether a lower-trust local reader exists on supported worker hosts is a deployment fact. This is the same pattern as, but a separate code path from, the agent installer one-liner (`curl … | sudo sh -s -- --token …`, internal/api/agent_handlers.go:349).

**Claimed root cause:** workerSnippets renders the one-time secret as a docker `-e NAME=value` command-line argument (internal/api/worker_snippets.go:29) and not through a channel only the admin can read (for example `--env-file` pointing at a 0600 file, or `-e PULSIX_ENROLL_TOKEN` with no value, inherited from a variable set by `read -s`). The token is also not bound to anything only the intended host holds, so whoever reads it from process metadata first can redeem it (internal/workers/enroll.go:153).

### Trace

1. **entrypoint** `internal/grpcsrv/enroll.go:29` (Server.Enroll): Anonymous Enroll RPC, the one worker method callable without a client certificate and limited only per IP. The local attacker on the worker host calls it with the token id and secret scraped from docker CLI argv, plus a CSR for its own key.
2. **propagation** `internal/api/worker_handlers.go:225` (createWorkerEnrollment): An admin (workers.write) creates a 1-hour single-use token. The response returns the token and embeds it in the docker and compose snippets (line 232).
3. **propagation** `internal/api/worker_snippets.go:29` (workerSnippets): The token is rendered as `  -e PULSIX_ENROLL_TOKEN=<token> \` in the docker run command the admin runs on the worker host, which puts it in the docker CLI's argv for the CLI's lifetime, including any image pull.
4. **propagation** `internal/workers/enroll.go:153` (Service.Enroll): The only checks are a constant-time compare of SHA-256(secret), that the token is unused and that it has not expired. Nothing ties redemption to the intended host or key.
5. **sink** `internal/workers/enroll.go:156` (Service.Enroll): SignCSR signs the presenter's CSR for the token's org, zone and name. The worker row, the certificate and the used mark are written in one transaction, and grpcsrv/enroll.go:54 returns the certificate to the attacker.

### Evidence

- `internal/api/worker_snippets.go:29`: The docker snippet puts the secret on the command line: fmt.Sprintf("  -e PULSIX_ENROLL_TOKEN=%s \\", token). No --env-file or stdin variant exists (repo-wide grep finds no env-file use).
- `internal/api/worker_snippets.go:42`: The compose variant writes the token into a compose file. The snippet does not constrain that file's permissions.
- `deploy/compose/README.md:173`: The documented remote-worker flow tells admins to run the printed docker run command (lines 176-181, including -e PULSIX_ENROLL_TOKEN=pxw1.…) on the worker's machine.
- `internal/workers/enroll.go:117`: The token string carries the enrollment id, the raw 32-byte secret and the CA pin, which is everything a third party needs to redeem it.
- `internal/grpcsrv/enroll.go:31`: Enroll's only gate before redemption is a per-IP rate limit of 10 per minute. A co-located attacker needs one call.
- `internal/worker/enroll.go:89`: The legitimate worker's own Enroll call (ensureIdentity) runs only after the container has started, which is after any image pull, so a fast reader wins the race. When it loses, line 97 returns 'the manager refused enrollment'.
- `internal/agentdist/files/install.sh:118`: Calibration: the agent installer stores its token under umask 077 in a 0600 env file. The project uses a restricted file for at-rest storage there, but the worker snippet has no equivalent.

### Blockers

- Whether worker hosts in supported deployments have local accounts with less authority than the admin running docker (not root, not in the docker group, not able to sudo) is a deployment fact that source does not show. Without such an account no trust boundary is crossed, because root and docker-group users are already root-equivalent on the host.
- Whether /proc is mounted with hidepid=1/2 or invisible (or the host otherwise restricts /proc/<pid>/cmdline) is a host fact. So is how long the docker CLI lives on a first run (the image pull duration). Running docker run on the host is forbidden for this verifier, and the approved sandbox has a single uid, so it cannot model a second OS user.
- Whether the attacker account can reach the manager's gRPC worker endpoint from the worker host is a network-policy fact. The worker host itself must reach it, so it is normally reachable.

**Local plan:** On a disposable Linux VM with default /proc mount options (no hidepid), no network access beyond a local dummy registry, and a dummy unprivileged user 'probe' that is not in the docker group: (1) as the docker-capable admin, remove any local copy of the worker image, then run the snippet exactly as workerSnippets renders it, with a dummy token value such as pxw1.DUMMY and a manager address that does not resolve; (2) while it pulls, have 'probe' run a bounded loop for at most 120 s (grep -a -l 'PULSIX_ENROLL_TOKEN=pxw1.DUMMY' /proc/[0-9]*/cmdline). Record only whether 'probe' saw the dummy value and for how many seconds. Redeem nothing, contact no real manager, and destroy the VM afterwards. Repeat once with the image already present to record the short-window case.

**Owner-observed check:** Owner-observed, read-only, on a real worker host: (a) getent passwd and getent group docker to list interactive accounts that are neither root nor in docker or sudo; (b) grep ' /proc ' /proc/mounts to check for hidepid/subset options; (c) confirm whether worker hosts are documented or provisioned as single-tenant appliances. If lower-trust accounts exist and /proc is not restricted, the finding holds as described.

## One odd mount point on a monitored host makes the manager refuse every disk sample from that host and keeps cutting its agent connection

Fingerprint `internal/checks/samples.go:withinContract:single-disk-mount-item-refuses-whole-agent-batch`

When no 'mounts' list is configured (the seeded default), the agent's disk plugin reports every mount point it finds in /proc/1/mountinfo as a check item, unchanged. The only filter is a pseudo-filesystem one (tmpfs, devtmpfs, overlay, squashfs), so FUSE mounts are included. gopsutil reverses the kernel's octal escaping with strconv.Unquote, so a TAB or newline in a directory name reaches the item as a real control character. The manager's ingest contract refuses the whole CheckResults message if any single item is longer than 512 bytes or contains a control character. agentapi then ends the AgentStream with InvalidArgument. The hunter's sandboxed test (agents/h21-tenant-availability/artifacts/evidence2.txt) shows this: one batch held a valid cpu sample, a valid '/' disk sample and one bad mount item, the client Send returned nil, the stream ended with InvalidArgument and 0 of 3 samples were stored. The agent has no length cap, escaping or skip for these items. The shipped unit sets ProtectHome=true, but that does not help: if the agent cannot stat the mount, the plugin still sends error observations under the same item. The result is that every disk interval (5 min in the seed) drops all of that host's disk samples, including the '/' usage that disk-full alerting relies on, and cuts the stream. The reconnect backoff only resets after a clean session end, so it climbs to the 60 s cap. sendResultsChunked counts a chunk as sent once the client-side Send returns, so results replayed from the disconnect buffer in chunks of 200 are lost too when a chunk also holds the bad disk result, along with any cpu, memory and service samples buffered with it. The effect is limited to the host that carries the mount, within its own organization. It would be a security issue if an unprivileged local user on a monitored host can create such a mount in init's mount namespace, for example a FUSE/sshfs mount through setuid fusermount3 at a path over 512 bytes or with a TAB in it. Whether they can depends on the OS and its packages, which this repository does not show. A second trigger exists on the manager side: an operator-entered disk 'mounts' entry over 512 bytes or with a control character passes validateParams and is refused at ingest in the same way. That case is an operator misconfiguration, not a privilege boundary.

**Claimed root cause:** The check-results item contract (at most 512 bytes, no control or line-separator characters) is enforced only at manager ingest. It is an all-or-nothing batch refusal that also ends the agent stream (samples.go:283-286, stream.go:266-275 and 106-111). The design comment (samples.go:102-125) knows that items are mount points, but it treats any violation as 'the agent is broken or lying'. It does not consider that a mount point, which the host discovers, can legitimately exceed 512 bytes or contain a TAB or newline that gopsutil has unescaped. stream.go:107-110 assumes 'the agent's own collector normalizes', but disk.go:84/99 pass mount points through unchanged. Manager-side validateParams (definitions.go:154-158) rejects only empty 'mounts' entries. Nothing on the path normalizes, escapes, skips or isolates a single bad item, and the agent treats chunks the server refused as delivered.

### Trace

1. **entrypoint** `internal/agent/checks/disk.go:99` (diskPlugin.Collect): Each mount point from gopsutil disk.PartitionsWithContext (/proc/1/mountinfo, unescaped with strconv.Unquote in gopsutil v4.26.8 disk_unix.go:57 and disk_linux.go:314/421) is added to the candidate list unchanged. The only filter is pseudoFilesystems (tmpfs, devtmpfs, overlay, squashfs), so fuse.* mounts pass.
2. **propagation** `internal/agent/checks/disk.go:117` (diskPlugin.Collect): The mount point becomes Observation.Item for three metrics. This happens both when Usage fails (lines 117-119, for example a mount the ProtectHome=true agent namespace cannot reach) and when it succeeds (lines 127-129).
3. **propagation** `internal/agent/checks/scheduler.go:274` (Scheduler run loop for one check): Every interval, the whole Collect output is converted to Results (Item unchanged) and passed to the session sink.
4. **propagation** `internal/agent/session.go:125` (toCheckResultProtos): Item is copied to the wire unchanged. sendResultsChunked (lines 106-117) counts a chunk as sent as soon as the client Send returns nil.

## Outbound webhook policy blocks only AWS's IPv6 metadata address; other providers' IPv6 metadata endpoints in fc00::/7 are dialled

Fingerprint `internal/outbound/policy.go:blockedRanges:ipv6-cloud-metadata-endpoints-unlisted`

The webhook SSRF policy is meant to refuse cloud metadata addresses. The package contract says so at policy.go:6-7. It refuses link-local IPv4 (169.254.0.0/16) and lists four further metadata literals: 100.100.100.200, fd00:ec2::254, 192.0.0.192 and 168.63.129.16. The only IPv6 one is AWS's fd00:ec2::254. All other ULA space (fc00::/7) is allowed as private self-hosted space. None of the IPv4-in-IPv6 extractors (NAT64 well-known, IPv4-compatible, SIIT, 6to4, Teredo, ISATAP, operator NSPs) matches a ULA address. So the IPv6 metadata literals that other providers publish pass Policy.Check. Examples are Google Compute Engine's fd20:ce::254 and Oracle Cloud's fd00:c1::a9fe:a9fe; the OCI address carries 169.254.169.254 in its low 32 bits, under a prefix no extractor recognises.
