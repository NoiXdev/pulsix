# Needs validation

Prioritized leads without severity. Each names the exact fact that source and the local sandbox could not settle, and a bounded plan to settle it. Do not treat them as confirmed vulnerabilities, and do not test them against a live deployment.

## Release job's QEMU/BuildKit images are pulled by mutable default tags and run privileged around the registry credentials

Fingerprint `github-workflows/release.yml:setup-qemu-buildx-default-unpinned-images`

release.yml pins docker/setup-qemu-action (line 99) and docker/setup-buildx-action (line 102) by commit SHA but passes no 'image' input to setup-qemu and no driver/driver-opts to setup-buildx, so both fall back to whatever container images the actions default to at those SHAs. Upstream, these defaults have historically been docker.io/tonistiigi/binfmt:latest (run --privileged to register QEMU binfmt_misc handlers on the runner kernel) and a docker-container BuildKit builder from moby/buildkit:buildx-stable-1 (a privileged daemon that executes every RUN step of the multi-arch build, assembles and pushes the images, and obtains the Docker Hub/Harbor credentials stored by login-action through the buildx session when it pushes). If the defaults at the pinned SHAs are still tag references, whoever controls those Docker Hub tags (their third-party maintainers, or anyone who compromises those accounts) at release time can change the bytes of the published noixdev/pulsix-manager and pulsix-worker images on both registries, including the arm64 variants whose RUN steps (npm ci, go build of the manager and embedded agent binaries, pip/apt in the worker) execute under the registered QEMU interpreter, or capture the push credentials, with no change to this repository. Repository-side triggers and the guard job are sound (tag push is writer-only, ancestry and CI checks on github.sha, tag regex-validated via env); this is the one executable input of the privileged release build not covered by the SHA/digest pinning policy of backlog 1.32. The lower-trust actor is an upstream image publisher outside this repository's review, so impact is high but likelihood is low.

**Claimed root cause:** The action SHA pins do not cover the container images those actions pull at runtime; release.yml sets no setup-qemu 'image' input and no setup-buildx driver-opts image, so binfmt and BuildKit are resolved from the actions' default (expected mutable tag) references instead of digests.

### Trace

1. **entrypoint** `.github/workflows/release.yml:10` (on.push (tags: v*)): A v* tag push (writer-only) starts guard and then the release job, which holds DOCKERHUB_TOKEN and HARBOR_PASSWORD.
2. **propagation** `.github/workflows/release.yml:99` (jobs.release.steps[docker/setup-qemu-action]): Only 'platforms: arm64' is set; no 'image' input, so the action's default binfmt image (expected docker.io/tonistiigi/binfmt:latest) is pulled and run privileged to install QEMU handlers on the runner.
3. **propagation** `.github/workflows/release.yml:102` (jobs.release.steps[docker/setup-buildx-action]): No inputs; the default docker-container driver starts a privileged BuildKit container from the action's default image (expected moby/buildkit:buildx-stable-1).
4. **propagation** `.github/workflows/release.yml:108` (jobs.release.steps[Log in to Docker Hub] (and Harbor, line 115)): Registry credentials are written to the runner's docker config; buildx serves them to the BuildKit daemon over the build session when it pushes.
5. **sink** `.github/workflows/release.yml:118` (jobs.release.steps[Build and push the manager image] (worker at line 133)): The BuildKit builder builds linux/amd64 and linux/arm64 and pushes noixdev/pulsix-manager and pulsix-worker as :vX.Y.Z and :latest to Docker Hub and harbor.cloud.noidee.dev.

### Evidence

- `.github/workflows/release.yml:99`: docker/setup-qemu-action@99012661954931238ded8c8b007157a8430204e1 # v4.4.0 with only 'platforms: arm64' (line 101); no image input.
- `.github/workflows/release.yml:102`: docker/setup-buildx-action@f87e5991a6d7451dcb8d9637bfbc97413f497069 # v4.4.1 with no 'with:' block at all (no driver, driver-opts or version input).
- `.github/workflows/release.yml:122`: platforms: linux/amd64,linux/arm64 for the manager (line 137 for the worker): arm64 stages execute under the QEMU handler registered by setup-qemu.
- `deploy/docker/Dockerfile.manager:48`: Build stage FROM golang:1.27.1-alpine@sha256:... without --platform=$BUILDPLATFORM, so for arm64 'go mod download', scripts/agent-binaries.sh and the manager go build (lines 53, 72, 79) run emulated; line 38 (node stage, npm ci/build) likewise.
- `deploy/worker/Dockerfile:57`: Worker runtime stage FROM python:3.13-slim@sha256:... (and build stage at line 33) also without --platform, so arm64 RUN steps of the worker image run emulated.
- `docs/BACKLOG.md:93`: Backlog 1.32 records SHA pinning of actions as the release-integrity policy; nothing in the repository pins the images these actions pull (grep for binfmt/buildkit/driver-opts/BUILDPLATFORM finds no other occurrence).

### Blockers

- The default image references of docker/setup-qemu-action at 99012661954931238ded8c8b007157a8430204e1 and docker/setup-buildx-action at f87e5991a6d7451dcb8d9637bfbc97413f497069 (and any image caching behaviour such as setup-qemu's cache-image) are defined in those actions' sources, which are not in this repository and could not be fetched: the verifier's sandbox has no network access.
- Hosted-runner behaviour is not observable locally: which image references (tag or digest) were actually pulled in past release runs, that the binfmt and BuildKit containers run privileged, and that the BuildKit daemon receives the registry credentials through the buildx session.

**Local plan:** Read-only, no execution of target code: obtain the two action repositories at the pinned SHAs (owner side, since this needs network) and check `git show 99012661954931238ded8c8b007157a8430204e1:action.yml` for the default of the 'image' input (and 'cache-image') and `git show f87e5991a6d7451dcb8d9637bfbc97413f497069:action.yml` plus its src for the default driver and BuildKit image. The finding stands if either default is a tag without @sha256; it is refuted if both defaults are digest-pinned.

**Owner-observed check:** Owner check, non-destructive: in the logs of the most recent release run, expand the setup-qemu and setup-buildx steps and record the pulled image references and digests (e.g. 'docker.io/tonistiigi/binfmt:latest', 'moby/buildkit:buildx-stable-1') and whether the builder runs with --privileged. If they are tag references, pin them in release.yml: setup-qemu 'image: docker.io/tonistiigi/binfmt:<ver>@sha256:<digest>' (and cache-image: false if present), setup-buildx 'driver-opts: image=moby/buildkit:<ver>@sha256:<digest>' (or 'driver: docker' with the containerd image store), and consider FROM --platform=$BUILDPLATFORM with GOOS/GOARCH cross-compilation in Dockerfile.manager's build stage so QEMU is out of the Go build path. Do not push a test tag to verify; review the workflow change instead.

## Release tag workflow runs a cross-repo reusable workflow from a mutable @main with contents: write and all repository secrets

Fingerprint `github-workflows/tag.yml:reusable-workflow-at-mutable-main-with-secrets-inherit`

tag.yml grants GITHUB_TOKEN contents: write and calls NoiXdev/github-workflows/.github/workflows/create_go_changelog_version_release.yaml@main with secrets: inherit. It is the only workflow reference in .github/workflows that is not pinned to a full commit SHA. Both repositories are in the NoiXdev organization, so secrets: inherit applies. When a pulsix writer dispatches the workflow, whatever commit is on the shared repository's main at that moment runs with a contents: write token on pulsix and with every repository and organization secret pulsix can read. After the planned re-arm (backlog 1.38), the same happens automatically on every green ci run on main. Those secrets include DOCKERHUB_USERNAME/DOCKERHUB_TOKEN and HARBOR_USERNAME/HARBOR_PASSWORD. release.yml reads them in a job without an environment: key, so they are repository- or organization-level, not environment-scoped. Code holding those credentials can push noixdev/pulsix-manager and pulsix-worker images directly, including :latest, the compose default, and so bypass release.yml's main-ancestry and green-CI guard. Anyone who can change the shared repository's main is therefore a release authority for pulsix without any pulsix review. Today the called file is missing from that main, so a dispatch fails. Whoever first adds it there decides what runs. Creating a tag needs neither registry secret. Whether this crosses a trust boundary depends on whether the shared repository's main writers and protections are narrower than pulsix's release maintainers. That cannot be seen in source.

**Claimed root cause:** tag.yml references the reusable workflow by a mutable branch ref (@main) instead of a reviewed commit SHA. That breaks the repository's own SHA-pinning policy (backlog 1.32), which every other uses: line in .github/workflows follows. The call also passes secrets: inherit instead of an explicit minimal secret list, inside a workflow whose top-level permissions are contents: write. Because the registry credentials are not scoped to a protected environment, the inherited set includes them.

### Trace

1. **entrypoint** `.github/workflows/tag.yml:34` (on.workflow_dispatch): A pulsix writer can dispatch the workflow. The automatic workflow_run trigger on ci completing on main (lines 35-38) is commented out, and backlog 1.38 plans to re-arm it. The code that runs is chosen by the shared repository's main, not by pulsix.
2. **propagation** `.github/workflows/tag.yml:43` (permissions): Top-level permissions give the called workflow's GITHUB_TOKEN contents: write.
3. **propagation** `.github/workflows/tag.yml:49` (jobs.tag.secrets): secrets: inherit passes every repository and organization secret available to pulsix, including the registry credentials release.yml uses, to a workflow in the same organization.
4. **sink** `.github/workflows/tag.yml:48` (jobs.tag.uses): Runs NoiXdev/github-workflows' create_go_changelog_version_release.yaml at the mutable ref @main, the only unpinned workflow reference in the repository.

### Evidence

- `.github/workflows/tag.yml:48`: uses: NoiXdev/github-workflows/.github/workflows/create_go_changelog_version_release.yaml@main is a branch ref, not a commit SHA. A grep of every uses: line in .github/workflows finds no other reference without a 40-hex SHA.
- `.github/workflows/tag.yml:49`: secrets: inherit, with no explicit secret list.
- `.github/workflows/release.yml:108`: DOCKERHUB_TOKEN is read in the release job, which declares no environment: key (lines 60-71). The secret is therefore repository- or organization-level, so secrets: inherit in tag.yml passes it on.
- `.github/workflows/release.yml:115`: HARBOR_PASSWORD is read in the same environment-less job, so it is also passed on.
- `docs/BACKLOG.md:93`: Backlog 1.32 records the SHA-pinning policy ('the SHA pinning was already in place and stays') in the same item that introduced tag.yml's @main call.
- `docs/BACKLOG.md:96`: Backlog 1.38: the called file exists only on the shared repository's chore/pin-actions branch, with no pull request. The plan is to re-arm the automatic trigger once it reaches main.

### Blockers

- Who can push, merge or force-push to NoiXdev/github-workflows' main is a hosted setting not visible in source: its collaborators and teams, branch protection and rulesets, required reviews, and bypass actors. The candidate is a real boundary crossing only if that set is broader or less protected than pulsix's own release maintainers.
- Whether NoiXdev/github-workflows allows other organization repositories to call its workflows (Settings > Actions > Access) is a hosted setting. If access is not granted, the call fails closed and nothing runs.

**Local plan:** Source-only, already settled. (1) grep -n 'uses:' .github/workflows/*.yml shows tag.yml:48 as the only reference not pinned to a 40-hex SHA. (2) release.yml's release job (lines 60-71) declares no environment:, so DOCKERHUB_* and HARBOR_* cannot be environment-scoped secrets. (3) tag.yml:43 and :49 grant contents: write and secrets: inherit. Nothing in the repository can show the shared repository's write access, so no local execution can decide the blocker. Do not dispatch the workflow or push a tag to test it, because that publishes.

**Owner-observed check:** Owner check, without dispatching anything. (1) In NoiXdev/github-workflows, list the users, teams and apps with write, maintain or admin access, and check main's branch protection and rulesets: required pull-request reviews, restricted pushers, force-push and deletion blocks, bypass list. Compare that set with the people allowed to release pulsix. (2) In NoiXdev/github-workflows, check Settings > Actions > General > Access to see whether pulsix may call its workflows. (3) In pulsix, and in the org's Settings > Secrets, confirm which secrets pulsix can read: DOCKERHUB_*, HARBOR_*, and any PAT used for tagging. The finding holds if the shared repository's main can be changed by anyone outside pulsix's release maintainers, or without a required review. Fix: pin the call to a full commit SHA of a reviewed shared-workflow revision, with a version comment. Replace secrets: inherit with an explicit list of only what tagging needs, which excludes the registry credentials. Move DOCKERHUB_* and HARBOR_* into a protected 'release' environment that only release.yml's release job uses.

## Agent certificate renewal racing an admin revocation re-creates the agent registration with a fresh unrevoked certificate

Fingerprint `internal/agentapi/service.go:Renew:register-without-live-serial-recheck`

Renew (internal/agentapi/service.go:237) trusts the interceptor's earlier serial lookup (internal/grpcsrv/auth.go:225-235) and then, after signing the CSR, calls agents.Register unconditionally. SQLStore.Register upserts host_agents, revokes the host's serials that are still unrevoked, and inserts the new serial with revoked_at NULL. If POST /api/v1/orgs/{org}/agents/{host_id}/revoke (agents.Service.Revoke -> SQLStore.Revoke: revoke all certificates, delete host_agents) commits after the interceptor's lookup and before Register's upsert, Register inserts a new host_agents row for the new serial. LookupAgentSerial then resolves that serial as live. Revoke's CloseHost cuts the old streams, but the agent reconnects with the new certificate and keeps authenticating, streaming facts and check results, and renewing. The handler also set the host's monitored flag to false, so the UI shows the agent as revoked while it is still connected. Only the timing is uncertain. If Register commits first, Revoke revokes the new serial too and the outcome is safe. AgentStream closes the same window with a post-track GetBySerial re-check (stream.go:56-65). Renew has no such check, and grpcsrv has no renewal rate limit, so a holder of the agent key can call Renew repeatedly to widen its chance of hitting the window.

**Claimed root cause:** agentapi.Service.Renew (service.go lines 237-260) never re-checks, after signing, that the presenting serial is still the host's active, unrevoked certificate before calling Register. SQLStore.Register (store_sql.go lines 151-174) and UpsertHostAgent (agents.sql lines 61-70, INSERT ... ON CONFLICT (host_id) DO UPDATE) have no guard such as 'existing row present AND cert_serial = presented serial AND that certificate revoked_at IS NULL'. Register therefore re-creates a row that a concurrent Revoke deleted. The transaction uses the default READ COMMITTED isolation (pool.Begin in internal/db/scope.go), which does not serialize the two transactions.

### Trace

1. **entrypoint** `internal/grpcsrv/auth.go:225` (Server.lookupAgent): The mTLS interceptor resolves the agent's presented serial and refuses unknown or revoked serials (line 233). This is the only liveness check before the Renew handler runs.
2. **propagation** `internal/api/agent_handlers.go:190` (POST /api/v1/orgs/{org}/agents/{host_id}/revoke): A concurrent admin revocation calls agents.Service.Revoke. SQLStore.Revoke (store_sql.go line 239) marks every certificate of the host revoked and deletes the host_agents row in one transaction.
3. **propagation** `internal/agentapi/service.go:242` (Service.Renew): The new certificate is signed for the identity resolved earlier by the interceptor. Liveness is not re-checked before Register (line 250).
4. **sink** `internal/agents/store_sql.go:153` (SQLStore.Register): UpsertHostAgent re-inserts the host_agents row that Revoke deleted. InsertAgentCertificate (line 165) adds a new serial with revoked_at NULL, which LookupAgentSerial (agents.sql line 97 join) resolves as live.

### Evidence

- `internal/agentapi/service.go:250`: Register is called without re-checking that agent.Serial is still live and still the host's active serial.
- `internal/agentapi/stream.go:60`: The sibling AgentStream re-reads the serial after tracking specifically to close the revocation race. Renew has no equivalent.
- `internal/db/queries/agents.sql:67`: ON CONFLICT (host_id) DO UPDATE re-creates, without any precondition, a host_agents row that Revoke deleted.
- `internal/agents/store_sql.go:165`: The new serial is inserted with revoked_at NULL regardless of the presenting serial's state.
- `internal/agents/store_sql.go:239`: Revoke deletes host_agents and revokes certificates, but nothing stops a Register that runs afterwards from undoing the deletion.
- `internal/db/scope.go:105`: WithWriteTx begins with pool.Begin (default READ COMMITTED), so the Revoke and Register transactions are not serialized against each other.

### Blockers

- The decisive Postgres interleaving (SQLStore.Revoke commits between the interceptor's GetBySerial and SQLStore.Register's UpsertHostAgent) needs internal/db/testdb (testcontainers plus the host Docker socket), which the approved sandbox forbids. Only the in-repo fake store was exercised. Hunter artifact agents/h01-agent-facts/artifacts/evidence.txt shows Renew succeeding after Revoke, a live new serial, a restored registry row, and a second Renew accepting the post-revoke certificate. The SQL shape is the same in source.
- The real width of the window (interceptor lookup, then CSR signing, then the Register upsert, against the revoke commit) under a real deployment was not measured. Exploitation also requires the attacker to hold the agent's private key (a compromised or malicious host agent).

**Local plan:** Add an integration test (internal/agentapi or internal/agents) against internal/db/testdb with the real agents.SQLStore and agents.Service. Enroll an agent. Wrap the AgentSigner so that SignAgentCSR first runs agents.Service.Revoke(org, host) on the real store before returning, then call Renew with the enrolled certificate's identity in context (or over bufconn through the real interceptor). Confirmed if all of the following hold: Revoke returns nil; Renew returns OK; GetBySerial(newSerial) returns Revoked=false; GetByHost finds the host again with cert_serial = newSerial; a second Renew authenticated with the new certificate succeeds. Refuted if Renew fails or the new serial resolves as revoked or not found. Then verify the fix the same way. Either re-check GetBySerial(agent.Serial) inside Register's transaction and refuse with Unauthenticated when it is revoked or not found, or make UpsertHostAgent an UPDATE ... WHERE host_id = $1 AND cert_serial = <presented serial> that requires one affected row with that certificate's revoked_at IS NULL, so a deleted row is never re-inserted.

**Owner-observed check:** Owner-observed and non-destructive, on a staging manager with a dummy host. Enroll a test agent. Have it call Renew in a loop while an admin calls POST /api/v1/orgs/{org}/agents/{host_id}/revoke. Then query agent_certificates for that host (SELECT serial, revoked_at FROM agent_certificates WHERE host_id = <dummy>) and host_agents. Any unrevoked serial, or a host_agents row present after the revoke returned 200, confirms the race.

## Session id is not rotated on MFA completion, so a planted pending session is upgraded by the victim's own second factor

Fingerprint `internal/auth/session.go:MarkMFAComplete:no-session-rotation-on-assurance-change`

Password login creates a session that is not MFA-complete. POST /api/v1/auth/totp/verify upgrades that same session row in place (mfa_complete=true, mfa_at=now()) and sends no new cookie. TOTP enrolment confirmation and passkey-registration completion do the same through completeEnrolment. Sessions are not bound to client IP or user agent, and the cookie name has no __Host- prefix. Suppose an attacker who knows a victim's password creates a pending session for the victim's account and can also place that cookie in the victim's browser for the Pulsix host, for example with a Domain-scoped, Path=/api cookie set from a sibling subdomain, or over plain HTTP when the deployment has no HTTPS or HSTS. The SPA's /auth/me call then sees the pending session and sends the victim to /login?step=totp. The victim's valid code makes the attacker's copy of the session MFA-complete, and it also counts as a fresh factor for step-up. The in-place upgrade is clear from source. Whether the attack works depends on whether the deployment gives an attacker a way to inject the cookie.

**Claimed root cause:** Sessions.MarkMFAComplete (internal/auth/session.go:115, query MarkSessionMFAComplete at internal/db/queries/auth.sql:28) raises assurance on the existing session id. It does not revoke the session and issue a new id and secret. The verify handler returns okOutput with no Set-Cookie. The cookie is named pulsix_session with no __Host- prefix (internal/auth/middleware.go:13, internal/api/auth_handlers.go:160), and the application sends no HSTS header. Nothing stops a cookie of the same name planted from a sibling host or over plain HTTP from being chosen by r.Cookie, which takes the first match.

### Trace

1. **entrypoint** `internal/api/mfa_handlers.go:148` (POST /api/v1/auth/totp/verify): The victim's browser submits its TOTP code together with whichever pulsix_session cookie it sends first. This route accepts pending sessions through requireSession.
2. **propagation** `internal/auth/middleware.go:30` (CookieMiddleware): r.Cookie(CookieName) takes the first pulsix_session cookie. A planted cookie with a longer path (Path=/api) is sent ahead of the victim's host-only Path=/ cookie.
3. **propagation** `internal/api/mfa_handlers.go:153` (verifyFactorCode): The code is checked against p.UserID, the owner of the planted session, which is the victim's account. The victim's genuine code therefore passes.
4. **sink** `internal/auth/session.go:115` (Sessions.MarkMFAComplete): The same session id is marked mfa_complete and mfa_at is set to now. No new credential is issued, so the attacker's copy of the cookie is now fully authenticated and fresh for step-up.

### Evidence

- `internal/db/queries/auth.sql:28`: UPDATE sessions SET mfa_complete = true, mfa_at = now() WHERE id = $1 upgrades the row in place without changing id or secret_hash.
- `internal/api/mfa_handlers.go:159`: The verify handler returns &okOutput{} without setting a cookie, so the session credential is the same before and after the assurance change.
- `internal/api/auth_handlers.go:160`: sessionCookie sets Name pulsix_session, Path=/, HttpOnly, SameSite=Lax, and Secure only when PublicURL is https. There is no __Host- prefix.
- `internal/api/auth_handlers.go:333`: completeEnrolment also upgrades the existing session id in place after a passkey registration finishes.
- `internal/auth/enrolment.go:57`: ConfirmTOTP upgrades the existing session id in place inside the enrolment transaction.
- `internal/db/migrations/00003_sessions.sql:2`: The sessions table has only id, user_id, secret_hash, mfa_complete and timestamps. No client binding such as IP or user agent limits where a copied cookie can be used.
- `web/src/routes/RootRedirect.tsx:53`: When a pending session already has a factor, the SPA routes it to /login?step=totp, which prompts the victim to enter the code.

### Blockers

- The attack requires an attacker who can set a pulsix_session cookie in the victim's browser for the Pulsix host. That needs a same-site sibling subdomain the attacker controls, plain-HTTP access without HSTS (the application sends no HSTS itself), or another injection position. These are facts about the deployment and DNS, not about the repository.
- The attacker must already know the victim's password to create the pending session for the victim's account. The cookie ordering (longer path sent first) and the SPA prompt flow are browser behaviour that cannot be observed in the approved sandbox. The DB-backed apitest harness cannot run there either, so even the server-side lack of rotation is established from source only.

**Local plan:** In an environment that can run the apitest harness against a real Postgres: create user A with a confirmed TOTP factor. Log in with the password and record the pending cookie C. Call POST /api/v1/auth/totp/verify with cookie C and a valid code, and assert that the response has no Set-Cookie. Then call GET /api/v1/auth/me with the original C and assert mfa_complete=true. A fix should make C return 401 after verify, and the verify response should set a new session cookie.

**Owner-observed check:** The owner checks whether any less-trusted host shares the Pulsix registrable domain and could set Domain cookies, and whether the reverse proxy enforces HTTPS and HSTS with includeSubDomains. If injection is possible, the owner can test in their own test browser with dummy accounts: set a Domain-scoped pulsix_session cookie with Path=/api holding a pending session for a test account, confirm the SPA shows the TOTP prompt, enter the test account's code, and check that the planted cookie now reports mfa_complete=true on /api/v1/auth/me.

## One tenant's duplicate playbook path blocks creation of a shared job template for every organization

Fingerprint `internal/db/queries/shared.sql:InsertProjectedTemplates:duplicate-playbook-path-fanout`

InsertProjectedTemplates (internal/db/queries/shared.sql:316-321) writes one projected job_templates row per organization by LEFT JOINing that organization's playbooks rows at the definition's playbook_path, and assumes there is at most one per (org_id, repo_id, path). Nothing enforces that. The playbooks table (00018_jobs.sql:32-40) declares only PRIMARY KEY(id) and UNIQUE(org_id, id), and no later migration adds a constraint or index on playbooks. POST /api/v1/orgs/{org}/playbooks (operator, PermPlaybooksWrite) calls playbooks.Service.CreateRepo. CreateRepo only checks the path's shape and that the repository exists in the org (repos.Get also returns the org's projection of a shared repository). It then inserts a new row unconditionally, so calling it twice with the same repo_id and path stores two rows. When the instance admin later creates a shared template that names this shared repository and path, the LEFT JOIN yields two rows for that organization that carry the same generated id i.id and the same name. The INSERT fails with a unique violation (job_templates PRIMARY KEY id / UNIQUE(org_id, name), 00018_jobs.sql:43,48). CreateTemplateWithProjections (store_sql.go:461-467) passes the error to collisionFromTemplateRace. Because Service.CreateTemplate's pre-flight check has already ruled out a real name collision, that function falls through to a bare ErrNameTaken (store_sql.go:497), and the shared handler maps it to HTTP 409 'name already in use' (shared_handlers.go:609-610). withTx rolls back the definition and every organization's projection. Result: an operator in one tenant, on purpose (by pre-registering likely paths such as site.yml, since the file need not exist) or by accident, stops the instance admin from distributing that shared template to every other tenant. The error names neither the organization nor the cause. The single-organization InsertProjectedTemplate (shared.sql:327-335) and UpdateProjectedTemplate (shared.sql:383) use a scalar subquery with LIMIT 1 and are not affected, so the problem is limited to the initial create. Impact is limited to availability of one instance-admin operation. It does not disclose or change data across tenants.

**Claimed root cause:** The bulk projection query relies on a uniqueness assumption (one playbook per org/repo/path). Neither the schema (playbooks lacks UNIQUE(org_id, repo_id, path)) nor playbooks.Service.CreateRepo enforces it. Unlike the single-org InsertProjectedTemplate and UpdateProjectedTemplate, which use a scalar subquery with LIMIT 1, the bulk LEFT JOIN in InsertProjectedTemplates has no LIMIT, DISTINCT ON or per-organization aggregation. Duplicate rows a tenant controls therefore fan out the per-organization insert into a PK/unique violation that rolls back the installation-wide create.

### Trace

1. **entrypoint** `internal/api/playbook_handlers.go:118` (POST /api/v1/orgs/{org}/playbooks): Gated by requireOrg(PermPlaybooksWrite), so operator or above. The caller sends the repo_id of the org's projection of a shared repository and a path. Calling it twice with the same values calls deps.Playbooks.CreateRepo each time.
2. **propagation** `internal/playbooks/service.go:143` (playbooks.Service.CreateRepo): Checks only the path pattern and that the repository exists in the org (repos.Get, which includes shared projections). It does not check for an existing playbook at the same repo and path.
3. **propagation** `internal/playbooks/service.go:153` (playbooks.Service.CreateRepo -> store.Create): Inserts a new playbooks row with a fresh UUIDv7 on every call (CreatePlaybook is a plain INSERT with no ON CONFLICT).
4. **propagation** `internal/db/migrations/00018_jobs.sql:32` (CREATE TABLE playbooks): Only PRIMARY KEY(id) and UNIQUE(org_id, id). There is no uniqueness on (org_id, repo_id, path), so both duplicate rows are accepted. No later migration adds an index or constraint on playbooks.
5. **propagation** `internal/shared/store_sql.go:461` (SQLStore.CreateTemplateWithProjections): The instance admin creates a shared template that names that shared repo and path. One InsertProjectedTemplates statement runs for every organization inside the same transaction as CreateSharedTemplate.

## A worker-supplied event timestamp lets one zone's worker keep an org-wide jump host's key-observation state indefinitely

Fingerprint `pulsix:jobs/recordTest:worker-event-at-orders-bastion-observations`

When a connection_test job finishes, the manager turns its final run event into a host_connection_tests row. The row's `at` is the RunEvent timestamp the worker sent. grpcsrv eventAt stores it as-is, with no clamp or skew bound against manager time. The row's hop_keys list is checked for shape only: the bastion ids are not checked against the route that the job's claim payload rendered. Bastions belong to the organization, not to a zone, so one jump host can serve routes in several zones. Two consumers pick the newest observation per bastion by `at` across all of the org's tests: the claim-time key-change guard (ListBastionKeyChanged, used by excludeChangedBastions for runs and refuseChangedBastions for bootstrap, rotate_key and revoke_key) and the admin's 'pin what you saw' input and fingerprint display (ListLatestBastionObservations). Connection tests are not refused through a changed bastion, but a genuine test cannot win the newest-by-`at` comparison either. Take a zone worker identity (a compromised worker host, or a play acting as the worker where play-uid separation is off) that is handed a connection_test for one of its own hosts whose route crosses a shared bastion B. The daily re-test hands out such jobs with no user action. Its final event can be dated years ahead with hop_keys=[{bastion_id:B, state:'changed'}]. B then reads as changed for every zone of the org. Runs exclude hosts behind B, and bootstrap, rotate_key and revoke_key claims through B are refused. No later genuine connection test from any zone can supersede the row. Re-pinning does not unblock the bastion by design. No retention, prune or direct DELETE exists for host_connection_tests. The only ways out are to delete the host whose test row carried the injected hop (ON DELETE CASCADE) or to repoint every route and recreate the bastion under a new id. The same future-dated row also stops the daily re-test of the attacker's own host (ListHostsDueForTest) and can plant an attacker fingerprint as the observation an admin is asked to pin. The spec names a zone with its own worker as a trust domain and says a worker is accepted results only for jobs it claimed. This path lets one zone's worker control trust state for a jump host that other zones depend on. The scope stays within one organization: every query filters on the job row's org_id. Naming a bastion that is on none of the worker's own routes would also need that bastion's random UUID, which the worker is not given.

**Claimed root cause:** The manager treats a worker-controlled field as a control-plane fact. grpcsrv eventAt keeps RunEvent.at verbatim, appendEvent stores it as job_events.at, and recordTest passes it to hosts.Service.RecordConnectionTest as the observation time of host_connection_tests.at. The newest-by-at selection in ListBastionKeyChanged and ListLatestBastionObservations then lets a single future-dated row stay authoritative for an org-wide bastion indefinitely.
