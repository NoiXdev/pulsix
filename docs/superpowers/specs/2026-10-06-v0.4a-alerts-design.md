# Pulsix v0.4a — Alerts and their lifecycle design

The rule engine (v0.3b-2) knows what a host's current state is. Nobody can yet
say "host X was critical from 14:03 to 14:51 on Tuesday, Anna acknowledged it at
14:12". This sub-project builds that record: the alert as a durable,
acknowledgeable episode, with snoozing, silencing and a timeline.

It deliberately stops before notification. Who hears about an alert — routes,
schedules, escalation chains — is v0.4b. The seam holds because v0.4b needs
nothing from this work but a stable alert identity and an acknowledgement
signal, and because everything here is useful on its own: the GUI gains a
history and an acknowledge button without any delivery machinery.

## What v0.4 already contains, and what is left

| Row | Backlog claim | Reality |

| 4.5 | Channels: email (SMTP) | **Built** in v0.2d (`notify.KindEmail`) |
| 4.6 | Channels: generic webhook | **Built** in v0.2d (`notify.KindWebhook`) |
| 4.11 | Maintenance windows | **Built** in v0.2d (`internal/maintenance`), except silencing |
| 4.1 | Monitoring groups: selector + manual members + exclusions | **Partly** — selectors only |
| 4.2 | Check templates attached to monitoring groups | **Probably redundant** — v0.3b-2 already binds rules per group through precedence; a second template mechanism would duplicate it. To be settled on the backlog, not here. |
| 4.7, 4.8 | Further channel kinds | Additive repetitions on the existing `Kind` interface; one bounded task each, no spec needed |

What is left and architectural: 4.9, 4.10, 4.12 — and the foundation all three
need and none of them has, the alert as a row. This sub-project builds that
foundation plus 4.10 and 4.12; 4.9 (escalation) belongs to v0.4b.

`check_state_changes` already exists (v0.3b-2, migration 00046): a hypertable
with 90-day retention, written in the evaluator's transaction on every
transition, indexed on `(org_id, host_id, check_key, item, metric, at DESC)`.
Section 11's "record every state change" is therefore already satisfied. The
alert row is not a second copy of that log — it is the durable identity that
spans one episode of it.

## Decisions

Each of these was settled during design; the rationale matters because the
implementation is only correct relative to it.

1. **One episode, one alert.** A tuple running `ok → warn → crit → warn → ok`
   produces exactly one alert, which carries `peak_severity = crit`. The
   alternative (a new alert per severity step) produces precisely the noise the
   escalation chain would later have to suppress again. The severity steps
   inside the episode stay visible — they are already in `check_state_changes`.
2. **A worsening severity voids an acknowledgement.** An alert acknowledged at
   `warn` counts as unacknowledged again once it reaches `crit`, so that nodding
   off a nuisance cannot silence the serious case. Stored as
   `acknowledged_severity` next to `acknowledged_at`, which makes "does the ack
   still cover this" a comparison rather than a second state to maintain.
   Improvement does **not** void it: `crit → warn` keeps the acknowledgement.
3. **Two muting mechanisms, not three.** Snooze stays its own thing because it
   is genuinely different: it hangs off one open alert and can end "when the
   state changes". It costs two columns, no CRUD surface. Silence is **not** a
   second subsystem — it is the face of a maintenance window: a one-off window
   with internal visibility and `reason = 'silence'`. That reuses targets,
   overlap, RLS, API and GUI, and closes the silencing gap v0.2d left open
   instead of routing around it. Whatever the source, **exactly one place**
   answers "is this muted right now, and why". **As built:** "reuses targets"
   means host, inventory group and organization in v0.4a — not monitoring
   group. The schema's target kind is widened to include it (see "Data
   model" below), but nothing resolves monitoring-group *membership* to a
   set of hosts for suppression purposes, so a monitoring-group silence
   would have nothing to check alerts against. That resolver is future work
   (backlog); the API's own enum does not offer the kind today.
4. **`unknown` opens one alert, at the host.** The literal reading of section 11
   (alerts open on `warn` or `crit`) leaves the worst case — we no longer hear
   from the machine — as the only one that raises nothing. Opening a tuple alert
   per `unknown` tuple turns a dead agent into an alert storm. So the host
   roll-up in `check_host_states` opens a single alert with `scope = 'host'`,
   and tuple-level `unknown` opens none. **Accepted gap:** a single broken check
   whose tuple reads `unknown` while the host is otherwise healthy raises no
   alert. It is visible on the host and items pages; nobody is woken.
5. **An alert whose subject disappears closes as `stale`, swept centrally.**
   Four paths remove a tuple without it ever reaching `ok`: the rule is deleted,
   the check is taken off the host, the item is dropped by decision (v0.3b-3
   deletes the state row without writing a transition), or the host is
   decommissioned. Closing those as `resolved` would be a lie in the one table
   whose job is the record. The sweep lives in one place rather than obliging
   each of the four deletion sites to close alerts too — that would scatter
   alert knowledge across four packages that should not have it, and the fifth
   deletion site somebody adds next year would forget.
6. **A flapping tuple does not close its alert.** It closes when the tuple is
   `ok` **and** no longer flapping. This is decision 1 on the time axis instead
   of the severity axis; the flapping flag's own hysteresis (set at 5 changes in
   30 minutes, cleared below 3) guarantees it cannot hang forever. **Accepted
   cost:** an open alert can sit on a tuple that currently reads `ok`, so the UI
   must show alert-openness and current tuple state as two separate things.
7. **Alert lifecycle lives in `internal/alerts`, writing in the evaluator's
   transaction.** Not inside `internal/rules` (acknowledge, snooze and
   suppression have no business in an evaluation package, and the alert logic
   would only be testable through the evaluator), and not decoupled over the
   change log (which buys a cursor, lag and double-processing for a problem we
   do not have). The shape is the one `notify.Outbox` already sets:
   `Enqueue…(ctx, tx, …)`.

## Package boundary

`internal/alerts` needs `rules.Change`, `rules.State` and `rules.TupleState`, so
it imports `internal/rules`. `internal/rules` therefore must not import back.
It declares the sink next to its use instead:

```go
// internal/rules
type AlertSink interface {
	// Apply runs inside the evaluator's transaction, per host.
	Apply(ctx context.Context, tx pgx.Tx, in AlertInput) error
	// Sweep runs once per tick, outside any host's transaction.
	Sweep(ctx context.Context, now time.Time) error
}

type AlertInput struct {
	OrgID, HostID uuid.UUID
	At            time.Time
	Changes       []Change
	States        []TupleState // the states after this evaluation
	Host          HostState    // the roll-up, home of decision 4
}
```

`alerts.Service` satisfies it, so the cycle never forms. The sink is a
**required positional constructor argument**, not an `Option` — the same ruling
`internal/items` got in v0.3b-3, for the same reason: a forgotten wire must be a
compile error, not half the alerting silently not running.

The input carries states and the roll-up, not only changes, because decision 4
needs the roll-up and decision 6 needs the `flapping` flag; neither is on a
`Change`.

## Data model

Migration 00049. Two tables, RLS policy pairs in the shape of 00037.

### `alerts`

The centre of the table is not a column but an index:

```sql
CREATE UNIQUE INDEX alerts_one_open_per_subject
  ON alerts (host_id, scope, check_key, item, metric)
  WHERE closed_at IS NULL;
```

Decision 1 becomes a database invariant rather than a convention the evaluator
has to honour. Two concurrent managers cannot produce two open alerts on one
subject.

Columns, in groups, each pair tied by a `CHECK` in the shape `check_states`
already uses for `candidate_state`/`candidate_since`:

- **Subject** — `scope` (`tuple` | `host`), `host_id`, `check_key`, `item`,
  `metric`. A `CHECK` forces the three text columns empty when
  `scope = 'host'` and `check_key`/`metric` non-empty when `scope = 'tuple'`.
- **Course** — `opened_at`, `severity` (current), `peak_severity`, `closed_at`,
  `closed_reason` (`resolved` | `stale`), the last two set together or not at
  all.
- **Acknowledgement** — `acknowledged_at`, `acknowledged_by`,
  `acknowledged_severity`, `ack_note`.
- **Snooze** — `snoozed_until`, `snooze_until_change`.
- **Flapping** — `was_flapping`.

`opened_at` is the state's `since`, **not** the tick's `now`: the episode began
when the state began, not when the ticker came past.

**No retention policy.** An alert is one row per episode, not per sample, and it
must outlive the 90 days of `check_state_changes`. Accepted consequence: a
year-old alert still stands while its detailed timeline is gone.

### `alert_events`

```
alert_events (id, org_id, alert_id, at, kind, actor_id, payload)
  kind ∈ opened | severity_raised | acknowledged | ack_voided
       | snoozed | unsnoozed | closed
```

It carries its **own** `org_id`: RLS cannot reach through `alert_id`, and a
policy that joined back to `alerts` would be both slow and circular.

This exists because of decision 2. An acknowledgement can be **silently voided**
by a rising severity; with only the columns on `alerts`, the operator would see
"unacknowledged" with no trace that anyone ever held it — which is exactly the
question asked after an incident. The columns on `alerts` remain as the fast
current state; the events are the history. v0.4b hangs its escalation steps here
without a new table.

### `maintenance_windows`

Two additions, nothing else: a `reason` column (`maintenance` | `silence`,
default `maintenance`) and the target kind `monitoring_group`. **As built:**
the column is additive and the migration widens the `target_kind` CHECK, but
v0.4a stops there — no code path resolves monitoring-group membership to
hosts, so a window of that kind cannot be created through any endpoint today
(the API's own enum omits it; see "API and permissions"). v0.4a silences
target host, inventory group and organization only; `monitoring_group`
silences wait on that resolver.

Explicitly **no `item` target.** It was in an earlier draft and is redundant:
v0.3b-3 can already ignore an item permanently by decision, with a preview. A
second way to mute the same item would be the duplication the table merge exists
to avoid, and it would have cost the window three ill-fitting columns, because
an item is not a `uuid` target.

## Lifecycle

`Apply` splits into pure deciding and blunt executing, the way `rules.Evaluate`
does: `Reconcile(in AlertInput, open []Alert) []Action` decides, the store
executes. `Reconcile` takes no `now`: every timestamp on the returned `Action`s
comes from `in` — a tuple state's own `Since` for an opening only, so a slow
ticker cannot move an alert's history forward, and `in.At` for everything else
(a severity rise, a flap latching, a close), each dated by when this
evaluation observed it rather than by when the underlying state happened to
begin. That is also what makes `opened_at` provably the state's `Since`
rather than the tick's `now`. The whole lifecycle is then table-driven
testable without a database.

Per host and tick, inside the transaction that already writes states, changes
and the roll-up:

1. **Open and advance.** Every state at `warn`/`crit` without an open alert
   opens one, `opened_at = state.since`. An existing one has its `severity`
   updated, its `peak_severity` raised only (never lowered), `was_flapping` set
   once the tuple flaps, and an `ack_voided` event written when the severity
   rises above `acknowledged_severity`.
2. **Close.** An open alert whose tuple is `ok` **and** not flapping closes as
   `resolved`.
2a. **A tuple that goes `unknown` changes nothing.** An alert open at `crit`
   whose tuple now reads `unknown` keeps its severity and stays open: `unknown`
   is not `ok`, so it cannot close, and decision 4 says `unknown` is answered at
   the host, so it must not be adopted as the alert's severity either. Without
   this rule a dying agent quietly turns the fleet's worst alerts into
   `unknown` ones.
3. **Host alert.** If the roll-up says `unknown`, exactly one open alert with
   `scope = 'host'` exists; otherwise it closes as `resolved`.

### The sweep

The sweep is **not** per host. `Ticker.Tick` works a due queue, and a host whose
last check was taken away **never becomes due again** — a per-host sweep would
therefore miss precisely the case it exists for.

`Ticker.Tick` calls `AlertSink.Sweep` once per tick, after `ProcessDue`
returns — on the same interface, so there is no second wire to forget. It is
driven by open alerts rather than by states:

```sql
WITH swept AS (
  UPDATE alerts a SET closed_at = $1, closed_reason = 'stale'
  WHERE a.closed_at IS NULL AND a.scope = 'tuple'
    AND NOT EXISTS (
      SELECT 1 FROM check_states s
      WHERE s.host_id = a.host_id AND s.check_key = a.check_key
        AND s.item = a.item AND s.metric = a.metric)
  RETURNING id, org_id
)
INSERT INTO alert_events (org_id, alert_id, at, kind)
SELECT org_id, id, $1, 'closed' FROM swept;
```

**As built:** this is not the single `UPDATE` an earlier draft of this
section prescribed. That draft predates `alert_events` in this same design
— the single statement was written before decision's own event table
existed and the two were never reconciled — so as written it left every
`stale` close with no matching `closed` row: Task 10's own timeline would
have rendered a swept alert as an episode that opened and never ended,
while a `resolved` close (written by `Execute`, Task 5) always paired its
`UPDATE` with an event. The CTE closes that gap in the same statement: the
`UPDATE`'s own `RETURNING` feeds the `INSERT` directly, so a swept row and
its event are never two statements that could partially fail, only one.

Cheap precisely because open alerts are few by definition, and it needs no
organization loop — it runs in the same security context in which `ProcessDue`
already works across organizations. It runs in its own transaction, not inside
one host's evaluation, so that concurrent managers do not contend. Host-scope
alerts are excluded: they have no state row by construction, and a deleted host
takes them with it through `ON DELETE CASCADE`.

## Suppression

Three actions on `alerts.Service`: `Acknowledge(alertID, note)`,
`Snooze(alertID, until | untilChange)` and their reversals. Silencing is not an
alert action at all — it is a maintenance window with `reason = 'silence'`.

**Acknowledging is not muting.** An ack says "a human knows" and will stop
escalation in v0.4b; it suppresses nothing. Snooze, silence and maintenance say
"do not notify". The two must never collapse into one column.

Decision 3's single place is a pure function:

```go
func Mute(a Alert, windows []maintenance.Occurrence, now time.Time) Suppression
```

No database access, table-driven testable, in the shape of `rules.Evaluate`. The
store answers "which windows cover this host right now", group resolution
included — that belongs in SQL; the function decides from it. `Suppression`
carries `Muted`, the reason (`snooze` | `silence` | `maintenance`), the end and
the window id where there is one.

When several apply at once the answer needs a **strict total order**, or the
reported reason depends on slice order — the mistake v0.3b-2 already avoided in
rule precedence. The order: **the one that ends latest wins**, because "muted
until X" is the fact the operator needs. An unbounded snooze ("until the state
changes") beats every bounded mute, because it still holds afterwards. Ties
break on a fixed order of reasons, then on uuid.

In v0.4a suppression has no effect beyond display — nothing is notified. It is
computed and served anyway, because v0.4b will do nothing but ask for it, and
because the list cannot label "in maintenance" otherwise.

## API and permissions

`internal/api/alert_handlers.go`, six endpoints:

- `GET /orgs/{org}/alerts` — list, filtered by open/closed, severity, host,
  scope, acknowledged, muted. The host view is a filter on this list, not its
  own endpoint.
- `GET /orgs/{org}/alerts/{id}` — the alert with its timeline: its events
  interleaved with the transitions from `check_state_changes` in
  `[opened_at, closed_at]`.
- `POST` / `DELETE /orgs/{org}/alerts/{id}/acknowledge`
- `POST` / `DELETE /orgs/{org}/alerts/{id}/snooze`

The maintenance endpoints gain `reason`. **As built:** they do not gain the
`monitoring_group` target — the huma enum stays `enum:"host,inventory_group,org"`
(`maintenance_handlers.go`, `calendar_handlers.go`), deliberately, for the
reason "Decision 3" and "Data model" now both say: there is nothing yet to
resolve that target to a set of hosts. Nothing else there changes.

Acknowledging and snoozing require the **existing** monitoring write permission;
v0.4a introduces no new one. An ack is arguably a lighter act than rewriting
thresholds and a separate, lighter permission would be defensible — that is a
backlog question, not a reason to grow the permission model here.

## GUI

A new page **Monitoring → Alerts**: the list with its filters, row actions for
acknowledge (dialog with note) and snooze (duration picker), plus an alerts
section on the host page reading the same endpoint filtered.

The list shows **three things separately**, because decisions 1, 2 and 6 require
it: whether the alert is open, the episode's peak severity, and how the tuple
reads *right now*.

Deliberately **not** built: bulk acknowledge. Decision 4 takes the peak off the
alert storm; if it turns out to be missing it is a backlog row, not a rebuild.

## Testing

One test per decision, because the implementation is only correct relative to
them:

- **Decision 1** — `warn → crit → warn → ok` yields exactly one row with
  `peak_severity = crit`.
- **Decision 2** — ack at `warn`, rise to `crit` → an `ack_voided` event, the
  alert counts as unacknowledged; and the other direction, `crit → warn` keeps
  the acknowledgement.
- **Decision 4** — every tuple `unknown` → one host alert, **zero** tuple
  alerts.
- **Decision 6** — `ok` with the flag set holds the alert open; the flag falling
  below the hysteresis closes it.
- **Decision 5 / the sweep** — a host whose last check was removed, and which
  therefore **never becomes due again**, still gets its alert closed as `stale`.
  This is the case the first draft of the sweep got wrong; it belongs in the
  repository as a test, not only as a sentence in this spec.
- **Concurrency** — two managers evaluating one host at once; the partial unique
  index permits only one open alert.
- **RLS** — `assertOnlyOrgAVisible` over `alerts` and `alert_events`, in the
  shape `internal/rules` already uses.
- **Timestamps** — `opened_at` is `state.since`, not `now`.

Plus `Mute` table-driven including the total order under several simultaneous
mutes, API tests through `apitest`, Vitest for list and dialogs, and one
Playwright run over a whole episode: the alert appears, is acknowledged, the
labelling is right.

Gates as always: Go ≥ 80 % (the new package aims higher), SPA ≥ 70 %,
`make test` over the groups in `scripts/test-groups.sh`, `golangci-lint run`.
**As built corrects this:** `internal/alerts` holds to the repo-wide 80 % floor,
not a higher one — see "As built" below for why.

## Review focus

1. The sweep must catch the never-due-again host. A per-host sweep is wrong.
2. `opened_at` must be `state.since`. A slow ticker must not move history.
3. `peak_severity` rises and never falls.
4. The ack comparison uses `acknowledged_severity`; improvement does not void.
5. `Mute`'s order is total — no result may depend on slice order.
6. `AlertSink` is positional in the constructor, so a missing wire fails the
   build. Check the bare-`Deps` test helpers in `internal/api` too: that is how
   the last two milestones each shipped a gate regression.
7. Host-scope alerts are excluded from the sweep.

## Explicitly not in this sub-project

- Notification of any kind — routes, schedules, escalation, delivery. v0.4b.
- Bulk acknowledge.
- Item-level silencing (v0.3b-3's item decisions cover it).
- Monitoring group manual members, exclusions, nesting, inheritance (4.1/4.1a/4.1b).
- Check templates on groups (4.2) — likely redundant, to be settled on the backlog.
- Further channel kinds (4.7/4.8) — bounded tasks, no design needed.
- A history table for host-level state, so a host alert's timeline consists of
  its own events only.

## As built

Ten tasks shipped this design with three places where the document above has
now been corrected in place (`Reconcile`'s signature, decision 3's silence
targets, and the sweep's statement) rather than merely noted here. What
follows is everything else that differed, gathered from the execution
ledger (`.superpowers/sdd/2026-10-06-v0.4a-alerts/progress.md`):

- **The Alerts route is `/o/$org/alerts`, not `/monitoring/alerts`.** The
  design's own "GUI" section invented a path; every org-scoped route in this
  SPA is flat (`/o/$org/{groups,hosts,runs,...}`), and no `/monitoring/`
  nesting exists anywhere else, so the implementer followed the app instead
  of the document.
- **The alert list DTO carries the host's name, not only its id.** A first
  pass left the list showing a truncated host id on every row, because
  client-side resolution cannot map an arbitrary id without fetching every
  page of a paginated host list. Fixed before ship by joining `hosts` in the
  list/detail queries — a plan defect (the design never named the one field
  that makes a row identifiable on the feature's own front page), not a
  deviation from anything the design asked for.
- **`internal/alerts` holds to the repo-wide 80% floor, not the ≥ 90% this
  document's own "Testing" section implied for it.** That figure was set on
  the premise the package would be pure logic; it now also contains the SQL
  store, the service and their database paths — exactly the shape CLAUDE.md
  puts at 80% (90% is reserved for auth, tenancy and db). See the task-11
  report for the actual measured number.
- **`HostAlertsCard` shows open alerts only**, not the full history the
  design's "an alerts section on the host page reading the same endpoint
  filtered" could be read either way. A host page answers "what is wrong
  right now", and the empty "this host is healthy" state is unreachable if a
  closed alert stays listed forever. The closed-alert history did not
  disappear: it moved to the org-wide Alerts page, reached via a link that
  seeds that page's `?host=` filter (`alertsRoute`'s own `validateSearch`) —
  a compensating mechanism the design never described, built only after a
  review caught that the first cut's ruling had quietly removed the only
  GUI path to it.
- **`was_flapping` renders on both open and closed rows, with tense-aware
  copy** ("flapping" vs. "flapped") rather than being gated on `open` the
  way a first pass read decision 6. The flag only ever latches and never
  clears, so hiding it on close would lose part of an episode's own history;
  what needed fixing was the tense, not the presence.
- **`AcknowledgeAlert` stamps `acknowledged_severity` from the row's own
  pre-update value, inside the same statement** (`UPDATE … SET
  acknowledged_severity = severity WHERE …`), not from a value the service
  read moments earlier. The design names the action (`Acknowledge(alertID,
  note)`) but not this detail; without it, a severity rise landing in the
  gap between a read and a write would silently ack at the old severity on
  a row already at the new one — exactly the silent-ack gap decision 2
  exists to close.
- **`AlertDetailDTO` needed a fix to appear in the generated OpenAPI schema
  at all** — huma skips an embedded struct field whose type is unexported,
  and the first cut embedded an unexported `alertDTO`. Pre-existing from the
  API task, caught before the SPA task that actually consumes the type.

Two rulings the design left open are now settled, in the backlog rather than
here: monitoring-group silence resolution (see decision 3's own correction
above) and whether 4.2 (check templates on monitoring groups) is redundant
against the rule engine's own precedence.
