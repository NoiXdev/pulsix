# Pulsix v0.3b-1 — Check pipeline design

**Status:** approved 2026-09-27. Supersedes nothing; refines the architecture
spec's §9 (check engine) and §10 (time series) for the first of three
sub-projects that together deliver v0.3b.

**Goal:** an operator sees, for every monitored host that runs an agent, its
processor, memory and disk usage and the state of the services that matter —
as a current value and as a graph over 1 h / 24 h / 7 d — and can configure
those checks: interval, parameters, enable/disable, and which hosts they
apply to.

## Why this is one of three

The architecture spec's §9 describes plugins, check definitions, probes with
fail policies, web assertions, discovery with per-item overrides, a rule
engine with precedence and hysteresis, time series, retention and graphs.
That is not one implementation plan. v0.3b is therefore cut into three
sub-projects, each with its own spec, plan and milestone:

1. **The check pipeline (this document).** Definitions as data, agent-side
   execution of four plugins, samples in a hypertable, values and graphs in
   the GUI. No evaluation of any kind.
2. **Rules and states.** Form and expression modes over one AST, precedence
   with the effective-rules view, hysteresis, flapping, `unknown` on missing
   data, host and group state roll-up.
3. **Discovery and item overrides.** Items as first-class rows, ignoring
   them, overriding rules per item.

Synthetic checks (HTTP, TCP, TLS, DNS, ICMP with probes and assertions) hang
off workers as vantage points and are their own subject, after these three.

## Division of labour

**The manager owns what is measured.** It resolves bindings into a concrete
set of checks per host, stamps that set with a version and delivers it.

**The agent measures and sends.** It holds a timer per check, reads the
value and ships the observation with its own timestamp. It knows no
threshold, no severity, no duration and no state: a service check reports
the observation (`active`, `failed`), never its meaning.

**The manager decides what a value means** — in sub-project 2. This
sub-project contains no evaluation at all, which is why it can ship without
rules being designed yet.

The agent schedules its own sampling because the connection is outbound —
the manager cannot reach in, only speak on a stream the agent opened — and
because the spec allows an interval per check. A manager that commanded
each sample would be chatty at fleet scale and would stop measuring
entirely whenever the connection blinked.

## Decisions

| Decision | Choice | Why |
|---|---|---|
| Operator capability | See **and** edit definitions | An operator who cannot retune an interval has to ask someone else to |
| Binding targets | Organization, monitoring group, host | The spec's model; adding groups later means migrating existing bindings |
| Monitoring group | A named, saved host-tag selector with a priority | `internal/hosts/selector` already resolves these expressions; the group is a name and a row, not a new resolution problem |
| Visibility | Current values **and** per-host graphs | A time series nobody can see over time is a gauge; the query and downsampling questions belong in the cut that creates the data |
| Plugin set | `cpu`, `memory`, `disk`, `service` | Together they force both result shapes — numbers and a discrete observation — so the pipeline never needs re-opening for the first state-shaped check |
| Disconnected agent | Keeps measuring into a bounded in-memory ring, replays on reconnect | A manager restart otherwise tears a hole in every graph, precisely during the incident when the data matters |
| Sample timestamp | The agent's, not arrival time | Required by replay; a plausibility window contains the damage a wrong clock can do |
| Item dimension | Present from day one | The disk plugin reports per mount on day one; without the dimension it would have to invent an aggregate. Only item *management* is deferred |
| Discrete observations | Their own column, not a number | Mapping `active`/`failed` onto 0/1 is an invention the rule engine would have to undo |

## Data model

All tables are organization-owned and carry the standard row-level security
pair. Migrations are additive.

**`monitoring_groups`** — `id`, `org_id`, `name`, `selector` (the existing
host-selector expression), `priority int not null default 0`, timestamps.
Unique on `(org_id, name)`.

**`check_definitions`** — `id`, `org_id`, `key`, `plugin`, `params jsonb`,
`interval_seconds`, `enabled`, `origin` (`seed` | `custom`),
`binding_kind` (`org` | `group` | `host`), `group_id` null, `host_id` null,
timestamps, `created_by`.

- `key` defaults to the plugin name **on create** and is what overriding
  matches on (see *Resolution*). An update must name it: on a full-replace
  `PUT` the same default would be a silent rename of an existing definition,
  moving the identifier precedence keys on, so a blank or absent key there is
  refused (`400`) rather than defaulted. Unique on
  `(org_id, binding_kind, group_id, host_id, key) NULLS NOT DISTINCT` —
  without that clause Postgres treats every NULL as distinct, and two
  organization-bound definitions with the same key (both binding columns
  NULL) would not collide at all, which is exactly the case the constraint
  exists for. PostgreSQL 18 is the deployed version, so the clause is
  available.
- The binding is two nullable foreign keys plus a `CHECK` that exactly the
  column matching `binding_kind` is set. A polymorphic id column would put
  referential integrity beyond the database's reach.

**`check_samples`** — hypertable on `at`, one-day chunks:
`at`, `org_id`, `host_id`, `check_key`, `item`, `metric`,
`value double precision` null, `label text` null, with a `CHECK` that
exactly one of the two is set. `item` is `''` for whole-host metrics.

Samples are keyed by `check_key`, not by definition id: a definition that is
edited or deleted must not orphan or rewrite history, and the key is what
the operator recognises on a graph.

**`check_current`** — `org_id`, `host_id`, `check_key`, `item`, `metric`,
`value`, `label`, `at`, `error text` null; primary key over
`(host_id, check_key, item, metric)`. Upserted on ingest. Lists read this
instead of scanning the hypertable.

**Retention:** a Timescale retention policy of 90 days on `check_samples`,
instance-wide, set in the migration. Per-organization retention (30/90/365)
is deferred; so are continuous aggregates — a 7-day graph for one host is
roughly ten thousand points per metric, which `time_bucket` answers from
raw data. The fleet overview is what will need them, and that is a later,
visible step.

**Seed set:** `Linux base` ships as rows with `origin = 'seed'`, created per
organization when the organization is created and backfilled for existing
ones by the migration. Rows, not code, so an operator can disable a seeded
check or copy it and edit the copy.

## Resolution

For one host: start with the organization's definitions, overlay the
definitions of every monitoring group whose selector matches the host, then
overlay the host's own.

- **Overriding matches on `key`.** `disk` bound to the organization and
  `disk` bound to a group are the same check at different scopes, and the
  narrower scope wins. An operator who wants a second disk check gives it
  its own key (`disk-var`).
- **Precedence:** host > group > organization. Among groups, higher
  `priority` wins; a tie is broken by the older group, deterministically.
- **`enabled = false` at a narrower scope disables the check**, rather than
  removing the row, so the GUI can show that it was turned off here.
- The resolved set is what the host page's *effective checks* view shows,
  each entry naming the scope it came from. That view is the answer to "why
  does this check run on this host", and it falls out of the resolver.

Only hosts with `monitored = true` and a live agent resolve to anything.

## Configuration delivery

The resolved set is serialised canonically and hashed; that hash is the
**configuration version**.

- The agent reports the version it is running in its heartbeat.
- The manager compares it against the version it computes for that host and
  pushes the full set when they differ. **It keeps no record of what it
  sent**: what the agent reports is the truth, which removes a second
  bookkeeping system that could disagree with reality.
- On connect, the agent reports its version before anything else, so a push
  missed during a disconnect is repaired immediately.
- Every 60 seconds the agent re-asserts its version as a safety net
  (`PULSIX_CONFIG_INTERVAL`, clamped to 30–600 s as the architecture spec
  allows).

`ManagerMessage` gains a `CheckConfig { version, checks[] }` body — today it
is a bare `ack`. No new RPC: both push and heal ride the stream that
already exists.

When a definition, a group, a host tag or a host's `monitored` flag
changes, the manager recomputes the affected hosts and pushes to those
currently connected. A missed notification self-heals within 60 seconds,
which is why this path may stay simple.

## Sample delivery

`AgentMessage` gains `CheckResults`, a batch of results — one message per
metric would be one message per host per metric per interval.

Each result carries the check key, the item, the timestamp, and either a
numeric value or a label, or an error string when collection failed. The
agent flushes every 10 seconds or when 200 results have accumulated,
whichever comes first.

- **Plausibility window.** Samples more than 2 minutes in the future, or
  older than 1 hour (the 15-minute ring plus generous slack for a slow
  reconnect), are rejected and counted. A skewed agent clock must not move graphs, and dropping data
  without counting it is silent forgetting.
- **The ring is bounded** — 15 minutes of samples at the configured
  intervals — and drops the oldest when an outage outlasts it.
  That, too, is counted: a gap in a graph should have a cause somebody can
  read.
- **A collection error is not a sample.** No row goes into the time series;
  `check_current` carries the error text, so the page shows "collection
  failed" rather than a stale number that looks fresh.

Ingest writes the batch in one transaction: the hypertable rows and the
`check_current` upserts commit together.

## API and permissions

New permissions `checks.read` (viewer) and `checks.write` (operator),
mirroring `agents.*`: checks are part of operating a host.

Routes under `/api/v1/orgs/{org}`:

- `GET|POST /checks`, `GET|PUT|DELETE /checks/{id}` — definitions.
- `GET|POST /monitoring-groups`, `GET|PUT|DELETE /monitoring-groups/{id}`,
  plus a preview that resolves a selector to matching hosts before saving.
- `GET /hosts/{id}/checks` — the effective set with its sources and current
  values.
- `GET /hosts/{id}/metrics?check=&item=&metric=&range=` — the graph series,
  bucketed server-side.

Mutating routes are audited like every other.

## GUI

- **Checks page** (organization): definitions with plugin, key, binding,
  interval and state; create, edit, delete; seeded rows marked as such,
  disableable and copyable.
- **Monitoring groups page**: name, selector, priority, with a live match
  count while typing — a selector with no visible matches is guesswork.
- **Host page, monitoring section**: the effective checks with their source,
  the current value or collection error per check, item and metric, and a
  graph over 1 h / 24 h / 7 d for numeric metrics.

uPlot is the one new frontend dependency, as the architecture spec names.

## Testing

- **Resolver:** table-driven over the precedence rules — host over group
  over organization, priority and age as tie-breaks, override by key,
  disabling at a narrower scope. Errors here are the kind nobody notices
  until a check runs at the wrong interval on the wrong host.
- **Plausibility window and ring:** injected clock, including the overflow
  case and the counters.
- **Stores:** against the real database, with two-organization isolation.
- **Stream:** the new messages in the `agentapi` harness, both directions.
- **Agent:** collectors behind injected providers (as `internal/agent/facts`
  does), the scheduler on an injected ticker, buffering across a simulated
  disconnect.
- **SPA:** Vitest per page; the graph component against fixture series.
- **E2E gate — the seam that matters:** enrol an agent, watch samples
  arrive, change an interval in the GUI, watch the configuration version
  change and the agent adopt it. That is the test that proves both
  directions of the contract fit together.

Coverage floors as elsewhere: ≥ 80 % per package, and the new resolver
package is worth ≥ 90 % given what a silent mistake there costs.

## Explicitly not in this sub-project

Rules, states, thresholds, alerts, hysteresis, flapping. Discovery
management and per-item overrides. Synthetic checks, probes, fail policies
and web assertions. Custom `script` checks, `agent.yaml` and secret
references. Windows and macOS collectors. Per-organization retention and
the fleet overview. Continuous aggregates.
