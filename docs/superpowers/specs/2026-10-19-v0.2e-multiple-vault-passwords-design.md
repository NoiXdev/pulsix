# v0.2e — More than one vault password per play

Status: approved, not yet planned
Backlog: 2.89
Milestone: v0.2e, a correction to the Ansible line rather than a new one

## The problem

`git_repos.vault_credential_id` is a single nullable column
(migration 00055), and the runner writes exactly one password file and
one `vault_password_file` line into the generated `ansible.cfg`
(`internal/worker/runner/inventory.go`). A repository can therefore
decrypt exactly one vault.

Real playbook repositories do not work that way. Production and staging
variables are encrypted with different passwords on purpose, so that the
staging credential cannot open production. Ansible has supported this
since 2.4 — `--vault-id label@file`, repeatable, or `vault_identity_list`
in `ansible.cfg` — and Pulsix is the thing standing in the way.

This surfaced while preparing the first production use with real
customers, which is also why it is worth doing before that use rather
than after.

## The label is not decoration

`ansible-vault encrypt --vault-id prod@…` writes the label into the
encrypted file's own header. At decrypt time Ansible looks for the
password whose label matches and only then falls back to trying the
others in order.

Two consequences shape the data model:

- A label belongs to the **encrypted content**, not to the password. The
  same credential may legitimately be `prod` in one repository and
  `production` in another, because that is what somebody typed when they
  encrypted the files. So the label lives on the link row, never on the
  credential.
- Getting it wrong is slow rather than broken: Ansible still tries every
  password. That is exactly the kind of failure that hides, so the label
  is required rather than optional.

## Decisions

### 1. Both the repository and the job template carry vault passwords

The repository holds the base set — the encrypted files live there, so
that is where the passwords belong, and a repository used by ten
templates is configured once.

A job template may add more, for the case where different teams share one
repository and one of them holds a password the others must not have.

Rejected: repository only (a template could never narrow or extend) and
template only (ten templates on one repository means maintaining the list
ten times, which is the duplication this product is trying to remove
elsewhere).

### 2. The resolved set is the union, and the template wins a collision

A run receives the repository's set unioned with its template's. Where
both name the same label with different credentials, the **template's
wins** — the more specific beats the more general, which is the
precedence rule `internal/rules` already uses for org → group → host →
item.

### 3. The run shows which vault ids it received, and where each came from

This is the price of decision 1 paid back. Two places to configure means
two places to search when a play cannot decrypt, and Ansible's own error
does not say which one was missing — it reports a decryption failure, not
an absent label.

The run detail therefore lists the vault ids the run was given and
whether each came from the repository or the template. Without it,
decision 1 trades one real problem for a quieter one; with it, the
question is one glance instead of two forms.

This is not an extra: it is the condition under which decision 1 is
acceptable.

### 4. Labels are validated against what Ansible accepts

Non-empty, no `@` (the separator in `label@file`), no comma (the
separator in `vault_identity_list`), **no leading or trailing whitespace,
and no Unicode control (category Cc) or format (category Cf) character**.
Rejected at write time with a readable message, the way every other input
in this codebase is.

The Cc/Cf rule is an amendment made during implementation, and it matters
more than the other two fixed characters. A label is written verbatim
into the generated `ansible.cfg`, so `@` or a comma forges one extra
identity entry — wrong, but confined to the vault line. A control
character (Cc, where the newline and carriage return cases that started
this amendment live) forges an entire configuration key: a label ending
in a newline followed by `host_key_checking = False` would quietly undo
the host-key pinning that same file exists to enforce. A format character
(Cf) is a different hazard on the same label: Cf is invisible-by-design —
the byte-order mark U+FEFF and the bidirectional-override characters
around U+202E are both in it — so a label carrying one can render on an
operator's screen as something other than the bytes it actually is. That
matters more here than anywhere else in this codebase, because this is
the one form whose entire job is telling an operator which password opens
which file; a label that displays as `prod` while the bytes something
else decrypts is the spoofing case this category closes. Cc and Cf were
chosen over a fixed character list because a reviewer found the narrower
rule disagreed with itself across the stack (the BOM case: JavaScript's
`trim()` strips U+FEFF as whitespace, so the browser rejected it as empty
after trimming, while Go's `strings.TrimSpace` does not, so the server
accepted it outright) — rejecting the whole category removes that
disagreement by removing the individual-character list it was fought
over.

Validation at write time is the rule, but it is not the only gate. The
runner rejects the same characters again before it renders the file,
because it is the last thing to run before a config that carries secret
material, and because it already treats the label as untrusted when
deriving filenames — applying that posture in one place and not the other
is how the gap appeared in the first place.

### 5. The old column is left behind, not dropped

Migrations here are additive. The link tables are created, every existing
`git_repos.vault_credential_id` is backfilled as a link row labelled
`default` — Ansible's own default label, so behaviour is unchanged for
every repository that has one — and nothing reads the column afterwards.
Dropping it is a separate cleanup row, not this sub-project's business.

## Data

```sql
CREATE TABLE git_repo_vault_credentials (
  org_id        uuid NOT NULL,
  repo_id       uuid NOT NULL,
  credential_id uuid NOT NULL,
  label         text NOT NULL,
  PRIMARY KEY (repo_id, label),          -- one password per label
  FOREIGN KEY (org_id, repo_id)       REFERENCES git_repos (org_id, id)   ON DELETE CASCADE,
  FOREIGN KEY (org_id, credential_id) REFERENCES credentials (org_id, id)
);
```

and the same shape for `job_template_vault_credentials`, keyed on
`(template_id, label)`. Both carry the `org_isolation` /
`org_isolation_bypass` policy pair with `ENABLE` and `FORCE ROW LEVEL
SECURITY`, copied from the newest migration rather than written afresh.

The primary key on `(parent, label)` is what makes "one password per
label" a schema fact rather than a service rule. A credential may appear
twice under different labels; a label may not appear twice.

Note the deliberate asymmetry in the foreign keys: the parent cascades,
the credential does not. Deleting a repository takes its links with it;
deleting a credential that a repository still uses is refused, which is
the behaviour `credentials`' own store already maps to `ErrInUse`.

## The worker

`proto/pulsix/worker/v1/worker.proto`'s `Job` carries
`string vault_credential_id = 20` today. It gains a **new** repeated
field of `{credential_id, label}` — a new number, with 20 marked
`reserved`, never reused.

This matters and is easy to get wrong: changing field 20 from `string` to
a repeated message while keeping the number is wire-incompatible. A
worker built against the old descriptor would read the new bytes as a
malformed string rather than failing cleanly, and protobuf gives no
warning. A fresh number means an old worker simply does not see the field
— which, per the risk below, fails loudly.

The resolution itself is the manager's: the worker is handed the answer,
never the rule, exactly as it is handed resolved channels rather than
routes.

The runner then writes one 0600 file per credential and emits

```ini
vault_identity_list = prod@/path/one, staging@/path/two
```

in place of the single `vault_password_file`. A job with no vault
credentials emits neither line, as today.

## Risks

- **A secret reaching a run that should not have it.** The union in
  decision 2 widens what a run can decrypt. Every resolution path needs a
  test that a template's set does not leak into a sibling template's run.
- **Label collisions across the two sources** are resolved silently by
  decision 2. The run detail from decision 3 is what makes the resolution
  visible; without it the rule is invisible and therefore untrustworthy.
- **The proto change is wire-visible.** A manager and a worker of
  different versions must not silently drop vault ids — the repeated
  field is new, so an old worker ignores it and decrypts nothing, which
  fails loudly rather than quietly. Worth a test, and worth naming in the
  upgrade notes.

## Acceptance

- A repository with two labelled vault passwords runs a playbook whose
  files are encrypted with both.
- A template adds a third, and a sibling template on the same repository
  does not receive it.
- The same label on both sides resolves to the template's credential, and
  the run detail says so.
- A label containing `@` or a comma is refused with a readable message.
- An existing repository with one vault credential keeps working with no
  configuration change, its password appearing as `default`.
- Deleting a credential a repository still names is refused; deleting the
  repository removes its links.
- `make test`, `golangci-lint run`, the SPA suite, the coverage gates and
  `npm run e2e` all pass.
