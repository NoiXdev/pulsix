# Pulsix v0.4b — Alert routes design

Monitoring can raise an alert, hold it, suppress it and close it, and it
can show all of that in the GUI. What it cannot do is tell anyone. This
sub-project is the bridge: which alert reaches which notification
channel, and when.

The spec is binding for the implementation plan that follows it. Where it
records a decision, that decision was taken deliberately and the
reasoning is kept, because the reasoning is what a later reader needs in
order to change it well.

## What already exists, and what is left

Pulsix has a complete delivery system, built in v0.2d: notification
channels (e-mail through the instance SMTP, a generic webhook), an outbox
with a queue shared by every manager, leases, up to six attempts per
message, a delivery log and weekly digests.

All of it is wired to **automation runs only**. `internal/schedules`'
digest path is its single caller, and `notify.Category` has exactly four
values — `failure`, `change`, `success`, `skipped` — which are Ansible run
outcomes. Between `internal/alerts` and `internal/notify` there is no code
dependency at all, only a comment. Monitoring cannot notify anybody.

So v0.4b builds a bridge, not a notification system. The channels, the
queue, the retries and the delivery log are reused as they stand.

What v0.4b deliberately leaves for later sub-projects, because each is
independent and each is easier to design once routes exist and have been
lived with:

| | |
|---|---|
| v0.4c | Notification schedules: time windows, weekdays, on-call rotation (backlog 4.4). Nothing of it exists today — `internal/schedules` is job timetables and `internal/schedule/retest.go` is the daily connection re-test; neither is this |
| v0.4d | Escalation chains: after N minutes unacknowledged, the next channel (backlog 4.9) |
| v0.4e | The notification bell and a per-user inbox with an unread count (backlog 1.12a) |

## Decisions

**1. A route notifies on any of the seven event kinds, each selectable.**
`alert_events` already records `opened`, `severity_raised`,
`acknowledged`, `ack_voided`, `snoozed`, `unsnoozed` and `closed`. All
seven are offered per route rather than a machine-state subset. The
recommendation at design time was the three machine-driven kinds, on the
grounds that operator actions are visible in the GUI anyway and that
acknowledgement is wanted as a *signal* for escalation (v0.4d) rather
than as a message. That was overruled deliberately: in a team, "someone
has taken this" is worth saying out loud. The GUI consequence — seven
checkboxes — is answered by grouping them, see GUI below.

**2. A route selects on scope, severity set and event kinds; routes add
up.** A route is (scope, severities, event kinds) → channels, where scope
is organization, monitoring group or host. Routes **union**: this follows
backlog 4.1b, which already ruled that rules override (deepest wins) while
"check templates / routes / maintenance add up", and which names a
"route-union view per host" in the same breath.

Scope deliberately reuses the vocabulary of the rule engine rather than
introducing a second targeting language. A monitoring group already *is*
a tag selector (`role=db AND env=prod`, plus manual members and
exclusions, backlog 4.1), so pointing a route at a group buys the selector
for free.

**3. Severity is a set, not a threshold.** The design first said "minimum
severity" and that was wrong. The house ordering is
`crit(3) > warn(2) > unknown(1) > ok(0)` — `rules.StateRank`, where
`unknown` ranks *below* `warn` on purpose, so that one expired mount
cannot mask a real `crit` on the same host. Under a threshold, "at least
warn" would therefore exclude `unknown`, which is exactly the
lost-contact case, and "crit and unknown but not warn" could not be
expressed at all. With three values a set is both simpler and more
honest.

**4. Suppression blocks delivery, and what was suppressed is caught up.**
While an alert is muted — `maintenance`, `silence` or `snooze`, the three
reasons `alerts.Mute` resolves — nothing goes out. When the suppression
lapses and the alert is still open, the notification is sent then. The
alternative, dropping it, means a host that broke during a maintenance
window and is still broken afterwards is never reported; a maintenance
window would swallow findings permanently rather than defer them.

**5. Events are coalesced per channel, not per event.** v0.4a's decision 4
already took the peak off a storm (an `unknown` opens one host-scope
alert, never one per tuple), but fifty hosts filling their disks are still
fifty alerts. Events are collected for one tick (default 60 s) and
delivered as one message per channel listing them.

Per *channel*, not per route-and-channel: the question at design time was
phrased "per route + channel", but decision 2's channel union — two routes
pointing at one channel means the alert reaches it once — contradicts
that. The union won, so the group key is the channel.

**6. The bridge follows the event log; it does not intercept the
writes.** `alert_events` is append-only and every one of the seven kinds
lands there. A ticker reads events nobody has decided about yet, resolves
routes, and enqueues.

The two alternatives were weighed and rejected on evidence. Emitting
inline from the six `alerts.Service` methods would first require the store
to report reliably what it changed — backlog 4.24 ("writes history for
rows it may not have changed") and 4.31 ("a zero-row update means two
different things") describe exactly that gap — would need a separate
buffer for coalescing, and **would still need a ticker for the catch-up**,
because "the maintenance window ended" is not an event in the log. It is
the chosen approach plus extra work. Extending v0.4a's existing
`AlertSink` in the evaluator is cheaper still but structurally incapable:
acknowledging and snoozing run through `alerts.Service` from the API, not
through the evaluator, so four of the seven kinds would never reach it.

**7. No cursor; the ledger is the cursor.** The follower was first
described as a cursor and ticker, after `check_eval_cursor`. That does not
hold here. `alert_events.id` is a `gen_random_uuid()` and therefore not
monotonic, and a watermark over `at` would *lose* events: a transaction
that takes its timestamp early and commits late slips behind a watermark
that has already advanced. An alert that reaches nobody because two
transactions overtook each other is the kind of fault that is never found
in production.

Instead `alert_notify_state` carries one row per decided event, and the
forward pass is an anti-join against it. Ordering stops mattering,
overtaking stops mattering, and the primary key *is* the idempotency.

**8. A route that stops working says so.** Backlog 4.29 records the trap:
a maintenance window whose cron or timezone stops parsing goes silently
inactive, and the visible symptom is "alerts fired during a maintenance
window" with nothing pointing at why. The same trap is open here and would
be worse, because a route that quietly stops matching means nobody is
told and nobody notices. Every such state is therefore a queryable fact —
see Error handling.

## Package boundary

A new package, `internal/alertroutes`, carries the bridge. It depends on
both sides: alert types, monitoring-group membership, and the outbox. That
is what a bridge does.

The direction that matters is the other one: **`internal/alerts` and
`internal/notify` learn nothing about it.** Both stay exactly as testable
and as readable as they are today, and v0.4a's inversion of `AlertSink` —
which exists so that `alerts` does not depend on the evaluator — is not
weakened by a second dependency pointing the other way.

Within the package:

- `route.go` — the `Route` type and its validation
- `match.go` — `Match(event, alert, routes, membership) []Route`, pure,
  no database, table-driven under test
- `store_sql.go` — CRUD and the two passes' queries
- `service.go` — route CRUD for the API
- `follow.go` — the ticker

## Data model

Migration `00052`, additive, with the house conventions: an RLS policy
pair (`org_isolation` / `org_isolation_bypass`), `UNIQUE (org_id, id)`,
and composite foreign keys per backlog 1.30.

### `alert_routes`

`id`, `org_id`, `name`, `enabled`, `scope` ∈ {`org`, `monitoring_group`,
`host`}, `scope_id` (NULL when `scope = 'org'`), `revision` for `If-Match`
per backlog 1.31, `created_at`, `updated_at`.

`UNIQUE (org_id, name)`. When the scope target is deleted the route goes
with it, by composite foreign key: a route whose group or host no longer
exists means nothing, and leaving it in the list would be a lie.

### `alert_route_severities`, `alert_route_events`, `alert_route_channels`

One row per selection. `alert_route_channels` references
`notification_channels (org_id, id)` — the uniqueness it needs is already
there — so deleting a channel removes the link rather than orphaning it.

A route with no channels is rejected at creation. If its last channel is
deleted later the route survives but is reported ineffective, per
decision 8.

### `alert_notify_state`

`org_id`, `alert_event_id` PRIMARY KEY, `state` ∈ {`sent`, `suppressed`,
`unrouted`, `expired`}, `decided_at`. Foreign key to `alert_events` with
`ON DELETE CASCADE`, so the ledger ages out with the history it describes.

`expired` is the terminal state for an event that was suppressed and
whose alert closed before the suppression lapsed — it can never be caught
up, and keeping it as `suppressed` would leave it in the catch-up pass's
working set forever. A partial index on the rows still worth examining
(`WHERE state = 'suppressed'`) is what keeps that pass cheap.

### One change to an existing table

`notification_deliveries.event_kind` carries a CHECK list of five values
today (`run.finished`, `schedule.skipped`, `schedule.failed`,
`digest.weekly`, `test`). It gains the alert kinds. Additive, like every
migration in this repository.

## Resolution

`Match` is pure. A route matches when it is enabled **and** its scope
covers the alert's host **and** the alert's severity is in its severity
set **and** the event kind is in its event set.

Scope coverage follows the ruling already recorded as backlog 4.30:
`monitoring_group` covers **every member, including unmanaged hosts**,
because "an unmanaged host still reports checks and still raises alerts".
That is the definition the suppression CTE uses, and deliberately not
`maintenance.HostsInMaintenance`, which covers managed hosts only because
a run that cannot touch a host has no reason to be guarded on its account.
Each of those two doc comments names the other; this third site joins the
same note.

Channels union, messages do not: if two routes point at the same channel
the alert reaches it once. That is why the union happens in resolution
rather than in delivery.

The severity matched against is the one on the `alerts` row at the time
the follower processes the event, not a value frozen into the event. This
is deliberate: if an alert climbs from `warn` to `crit` inside the
coalescing window, "it is critical now" is the more useful statement than
"it was a warning forty seconds ago", and the `severity_raised` event
makes the climb visible regardless. One source of truth.

Host-scope and tuple-scope alerts need no special case — both carry
`host_id`.

## The follower

One tick, per organization, under an advisory lock, after the pattern of
`auth.Reaper` and `schedule/retest.go`, so a second manager skips rather
than races.

**Forward pass.** Events with no row in `alert_notify_state` (anti-join)
→ resolve routes → decide → write the row. `sent` when channels were
found and the alert is not suppressed, `suppressed` when it is,
`unrouted` when no route matched.

**Catch-up pass.** Rows with `state = 'suppressed'` whose alert is still
open and no longer suppressed → send → update to `sent`. This is
decision 4, in the same table rather than as a second mechanism.

**Enqueue.** Per channel, one `Outbox` row with
`event_key = alert.batch:<channel>:<tick>`; the outbox's own
`(org_id, event_key, channel_id)` idempotency key protects a retried tick.

**The ledger write and the enqueue share one transaction.** This is not a
detail. Writing `sent` and then failing before the outbox row exists
would mark an event delivered that nobody will ever receive, and the
anti-join guarantees it is never looked at again — a silently dropped
alert, which is the one outcome this design exists to prevent. The same
holds for the catch-up pass's update to `sent`. Both passes therefore
decide, enqueue and record atomically, or do none of it.

**Retiring suppressed rows.** A `suppressed` row whose alert closed while
still muted can never be caught up: the catch-up pass requires the alert
to be open. Those rows are retired to a terminal state as they are
encountered, so the catch-up working set stays bounded by what is
genuinely still pending rather than growing with every suppressed event
in the history.

**Failure ends at the enqueue.** Delivery, retries and failures belong to
the existing dispatcher — six attempts, leases, the delivery log — and
v0.4b changes none of it. If a tick fails, no rows were written and the
next tick finds the same events again; nothing is lost, because nothing
was advanced.

## API and permissions

- `GET` / `POST` `/orgs/{org}/alert-routes`
- `GET` / `PATCH` / `DELETE` `/orgs/{org}/alert-routes/{id}` — `PATCH`
  requires `If-Match` and carries `revision`, per backlog 1.31
- `GET` `/orgs/{org}/hosts/{id}/alert-routes`

The last is not an extra. Backlog 4.1b names it ("route-union view per
host"), and with routes that add up it is the only answer to "why did no
mail arrive?" and to "why three?". The rule engine has its effective-rules
view for the same reason. Without it the union semantics are not
followable by a user.

Permissions are `PermChannelsRead` and `PermChannelsWrite`, not the check
permissions. A route decides where data leaves the system — to which
address, to which webhook — which weighs more than acknowledging an alert,
which v0.4a deliberately placed under `PermChecksWrite`. The consequence
is intended and worth stating plainly: being allowed to acknowledge an
alert does not carry the right to decide where it is reported.

## GUI

Routes belong to `features/notifications`, beside `ChannelsPage`,
`DeliveryLog` and `DigestCard` — they are configuration, not operations.

- `AlertRoutesPage` — name, scope, severities, channels, enabled
- `RouteDialog` — name; scope picker (organization / monitoring group /
  host); three severity checkboxes; the seven event kinds **grouped**, as
  decision 1 requires, into *state* (`opened`, `worsened`, `closed`) and
  *operator action* (`acknowledged`, `acknowledgement voided`, `snoozed`,
  `unsnoozed`); channel selection
- On the host detail page, a card listing the routes that cover this host
  — the union view, where it is needed

## Error handling

Decision 8 in practice. Every way a route can stop working is a fact that
can be queried or seen, never a silence:

- `state = 'unrouted'` means "considered, no route matched". "Nobody was
  told" is a row, not an absence.
- A route with no channels is rejected at creation, and reported
  ineffective in the list and the union view if its last channel is
  deleted later.
- A route whose scope target is deleted is deleted with it.
- Delivery failures stay with the existing dispatcher and its log.

## Testing

Failing test first, per the house rules.

- `Match`, table-driven, no database: union, scope coverage including
  unmanaged members, severity sets, event sets
- The store as an integration test against Postgres, RLS in **both**
  directions
- The follower as an integration test, with four obligatory cases: the
  forward pass; suppressed then caught up; running twice yields **one**
  message; and explicitly the case a cursor would have lost — two events
  committed in the reverse order of their timestamps must both arrive
- The API through `apitest`, the GUI with Vitest, and one Playwright pass:
  create a route, raise an alert, see the delivery in the log

**A dependency on backlog 1.36.** The coverage floor for
`internal/alertroutes` must be set under honest measurement. Go 1.27.1
gave every coverage block the statement count of its enclosing function,
inflating packages built from a few large functions; setting a floor under
it would carry that error forward into a new package.
