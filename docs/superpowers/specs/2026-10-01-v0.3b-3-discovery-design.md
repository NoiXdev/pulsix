# Pulsix v0.3b-3 — Discovery and item decisions design

**Status:** approved 2026-10-01. The third and last of the sub-projects that
together deliver v0.3b. It builds on v0.3b-1 (`2026-09-27-v0.3b-checks-design.md`),
which measures, and v0.3b-2 (`2026-09-29-v0.3b-2-rules-design.md`), which judges.

**Goal:** the things a check measures — mounts, service units — stop being
strings an operator types from memory and become rows the product knows
about: when each first appeared, whether it is still being reported, and
whether anybody wants it judged at all.

## What is already built, and what is left

Backlog row 3.6c reads "discovery of items with per-item overrides", and
half of it shipped in v0.3b-2 without being marked as such. A rule already
binds to `(host, check_key, item)`; item already beats host beats group
beats organization; a rule whose item disappears already survives and is
labelled. "New items inherit rules" is already true, because rules bind to
a metric rather than to a list of items.

What does not exist is the item itself. Items are strings in
`check_samples`, `check_current`, `check_states` and `check_rules`, and
nothing records that `/var` on this host is a thing with a history.
`internal/checks/items.go` only derives, on read, whether a check still
*asks* for an item, so that "you stopped asking" can be told apart from
"the agent went quiet" (backlog 3.28).

So this sub-project delivers three things:

1. **Discovery** — items become rows, with the moment each was first seen.
2. **Ignoring** — a decision that an item should not be judged, as a single
   item or as a pattern, with a host able to overrule the organization.
3. **A picker** — the rule editor and the host page offer the items that
   actually exist instead of a text field and a good memory.

## Decisions

| Decision | Choice | Why |
|---|---|---|
| What "ignored" means | Keep measuring, stop judging | The graph is the thing an operator wants to keep: a volume that is deliberately 95 % full still has a growth curve worth reading. Only the verdict is unwanted |
| Where discovery runs | In the evaluation ticker, not in ingest | The ticker already loads every current tuple of a host, in a transaction it already opens. Ingest is the ~7 000 samples/s path that the whole cursor design exists to keep free |
| `last_seen` | Not stored; read from `check_current` | Storing it would mean one write per item per host per tick — twenty mounts, every fifteen seconds, forever. `check_current` already carries the latest timestamp per tuple, so this is a read, not a write. `check_items` is written once per item and never again |
| Items with an empty name | Not rows | `cpu` and `memory` report one whole-host reading with no item. There is nothing to discover and nothing to ignore, and a row per host per check would be noise every query carries |
| Item rows are never deleted | `first_seen` only; absence shows as a stale `last_seen` | Nothing observes a mount disappearing — the agent simply stops sending it. The same convention `check_current` carries and backlog 3.28 resolved as a read-side filter |
| Discovery and decisions | Two tables, separate lifecycles | One is written by the machine and belongs in no audit log; the other is an operator's decision and belongs in every audit log. Keeping them apart makes discovery idempotent and conflict-free, and gives the override semantics somewhere visible to live |
| Scope of a decision | Organization or host; exact item or glob | Chosen over single items only. A fleet where the same kind of item recurs should not need one decision per host |
| Overruling | A host decision beats an organization one; exact beats glob | Chosen over purely additive ignores. An organization that ignores `/mnt/scratch-*` must still be able to watch `/mnt/scratch-db` on the one host where it matters, without rewriting a pattern that is right for ninety others |
| The third value | `watch` is a stored decision, not an absence | It is the overrule, and storing it as a value lets the interface tell "somebody looked at this and said watch it" from "nobody has ever looked" |
| Glob syntax | `*` only, whole-string match | No `?`, no character classes, no `**`. The same restraint as the fleet's `tag` filter, for the same reason: a syntax explained in one sentence raises no support questions |
| State of an ignored item | The stored state row is **deleted** | Unlike the `Interval == 0` exclusion, which leaves the row standing. An operator who ignores a `crit` volume must not be left with a row that still says `crit` because nothing re-judged it |
| `ignored` as a state | No — the state space stays four-valued | Being ignored is a statement about a decision, not about a measurement. A fifth enum value would force every comparison, every roll-up order and every future alerting migration to have an opinion about it |
| History of the transition | None written | `check_state_changes` holds states, and this is not one. "Why did this stop being red" is answered by the audit log, which is also the only place the *reason* lives — the decision's own note |
| What the agent measures | Unchanged | Ignoring never touches the configuration pushed to an agent. This is a commitment, not an omission: nobody should later "optimise" it into dropping the measurement |
| Package | A new `internal/items` | `internal/rules` must not import `internal/checks`, and evaluation needs the ignore decision. A package both may use resolves that without a third adapter layer |

## Data model

One migration, `00048_check_items.sql`, two tables. Both org-owned, both
carrying the RLS policy pair in migration 00037's shape and the composite
`(org_id, …)` foreign keys the schema convention requires.

### `check_items` — what the machine found

```
primary key (host_id, check_key, item)
org_id, host_id, check_key, item
first_seen timestamptz not null
```

Written only by the evaluation ticker, as `INSERT … ON CONFLICT DO NOTHING`
— so an item costs exactly one successful write in its lifetime. `item` is
never empty: a whole-host reading has no item to be.

A row is never deleted. "Last seen" is `max(at)` over that tuple's
`check_current` rows, read when it is needed.

### `check_item_decisions` — what a person decided

```
id          uuid primary key
org_id      → organizations
scope       text not null check (scope in ('org','host'))
host_id     uuid null            -- scope='host'; FK (org_id, host_id) → hosts
check_key   text not null
match_kind  text not null check (match_kind in ('exact','glob'))
pattern     text not null
decision    text not null check (decision in ('ignore','watch'))
note        text not null default ''
created_by, created_at, updated_at
```

A `CHECK` ties `scope` to its column, exactly as `check_rules` does.

`note` is load-bearing. An operator six months later needs to read why a
volume was ignored before they dare switch it back on, and the audit entry
alone records who and when, not why.

Decisions and items are deliberately decoupled: a decision may name an item
that does not exist yet, and survives one that disappears. Neither table
references the other.

## Resolving a decision

For one `(host, check_key, item)`, collect every decision whose scope
matches (the organization's, plus this host's) and whose pattern matches
the item. The most specific wins:

1. `host` beats `org`
2. within the same scope, `exact` beats `glob`
3. a remaining tie goes to the older `created_at`, then the smaller id,
   byte for byte

That last step is the same strict total order `rules.Resolve` already
implements, and exists for the same reason: a winner that depended on map
iteration order would flip between ticks and the interface could never
explain itself.

With no match, the item is watched. `watch` as a stored value therefore
only ever matters as an overrule: a `watch` at organization scope changes
nothing on its own, because watching is already what happens by default.
The interface should not offer it there as though it did.

**The glob.** `*` matches any run of characters, including none. Every
other character is a literal. The match is anchored at both ends. That is
the whole syntax.

## Discovery and evaluation

`Load` already reads the host's current tuples, so the item names come out
of data it holds. In the same per-host transaction `Apply` opens, it
inserts any item it has not seen before.

`Load` also reads this organization's and this host's decisions — one
query, not one per item — and resolves them per item. An ignored tuple is
skipped exactly as a tuple with no resolved interval is skipped: no state,
no roll-up contribution, no due time. One mechanism, not two.

With one difference, which is why it is written down: `Apply` **deletes**
the stored `check_states` row of an ignored tuple. The read side therefore
cannot learn "ignored" from a state — it resolves the same decisions the
ticker did, through the same function at a second call site, the way
`Resolve` already has two.

**Watching an item again** re-creates its state row on the next tick, with
`since` set to that moment. The row cannot claim a continuity it does not
have: nothing judged the item while it was ignored, so the honest answer to
"since when" is "since it was watched again".

## API and permissions

Org-scoped under `/api/v1/orgs/{org}/`. Reads at the checks read
permission; decisions at the checks write permission, because a decision
changes what is judged.

| Route | Purpose |
|---|---|
| `GET /hosts/{id}/items` | this host's items: check, name, `first_seen`, last reported, the effective decision and where it came from |
| `GET /items` | organization-wide, filtered by check and item glob — the same one-character glob the decisions use, so an operator learns one syntax — and it answers "which hosts have a `/backup`" |
| `GET/POST /item-decisions`, `GET/PUT/DELETE /item-decisions/{id}` | the decisions |
| `POST /item-decisions/preview` | which currently known items a pattern would match |
| `GET /hosts/{id}/checks` | **existing** route, extended additively with `ignored` per tuple |

`preview` is the counterweight to having chosen patterns at all: a glob
that catches more than intended silently stops watching things somebody
wanted watched, and silence is the problem. It is a read-shaped POST and
gets the house treatment — on the audit allowlist with its own reason, like
`/monitoring-groups/preview` and `/rules/validate`.

The three mutating decision routes **are** audited, with scope, pattern and
decision in the summary.

## GUI

- **Host page, monitoring card.** An ignored row says "ignored" as text, not
  by colour alone, and names its origin when opened — "by the organization
  pattern `/mnt/scratch-*`" or "set on this host". The action to ignore or
  watch sits on the row itself, because that is where an operator stands
  when they decide.
- **A fourth tab, "Items"**, beside Checks, Monitoring groups and Rules: the
  decisions organization-wide, with the pattern editor and its preview. That
  is where someone tidying a fleet goes, rather than host by host.
- **The rule editor's item field** becomes a picker over the selected host's
  discovered items. Free text stays allowed — a rule may name an item that
  has not appeared yet, the same decoupling the decisions have.
- **The effective-rules panel** can now date its "no longer observed" label.

No new frontend dependency and no new chart.

## Testing

- **Unit, table-driven:** the glob, exhaustively — anchoring, `*` at the
  start, middle and end, several of them, and literals that would be
  metacharacters in a richer syntax. The resolution, over every
  scope/match-kind pair, the tie-break, and the case `watch` exists for.
- **Integration against Postgres:** `ON CONFLICT DO NOTHING`; `first_seen`
  not moving when an item is seen again; the RLS pair on both tables;
  cross-org isolation on every read.
- **API** through `internal/api/apitest`, including that `preview` persists
  nothing and that the audit entries carry what they should.
- **SPA:** Vitest for the tab, the row action and the picker; Playwright for
  the tab and for ignoring an item from the host page.
- **E2E:** the whole arc — an item appears, crosses a threshold, is ignored,
  the host goes green, it is watched again, the host goes red.
- `internal/items` joins `scripts/coverage-gate.sh`'s 90 % list: it decides
  what gets judged, and a silent mistake there is a monitor that stopped
  watching without telling anybody.

## Review focus

1. **A pattern of `*`.** Nothing prevents an operator muting the whole
   fleet. The preview's match count, shown before saving, is the only brake
   there is — it has to work.
2. **A decision that predates its item.** When the item appears it must be
   ignored from the first tick, not after a round.
3. **An organization pattern and a host `watch` on the same item.** The host
   wins, and the view says why.
4. **Two equally specific patterns both matching.** The same winner every
   time, from the total order rather than from iteration order.
5. **The ignored item is the host's only `crit`.** The host turns green in
   the same tick, and the fleet's counts agree with the host page.
6. **Ignoring an item that already has a state row.** The row goes, and the
   interface says "ignored" rather than "not yet evaluated" — two different
   statements, and conflating them is the kind of lie this milestone's
   predecessor went out of its way to avoid.
7. **`first_seen` after a gap.** A mount gone for two weeks and back is the
   same item; the timestamp must not jump.

## Explicitly not in this sub-project

Alerting in every form — alerts as rows, routes, escalation, acknowledge,
snooze, silence, notifications (v0.4). Any change to what an agent
measures. Synthetic checks, probes and web assertions. The two deferred
v0.3b-2 rows 3.32 and 3.37, which stay together as a measurement-driven
pair. Per-organization retention and continuous aggregates. SPA i18n.

## As built

Where the implementation deviated from what is approved above — every one a
deliberate decision made during Tasks 1–9, not a drift nobody noticed.

- **`internal/items` imports neither `internal/rules` nor `internal/checks`.**
  The package doc comment's own ruling (`items.go`) holds exactly as
  written, but the mechanism it needed was not obvious from the "Package"
  decision row above: the set of valid `check_key` values a decision may
  name is a required *positional* constructor argument to
  `items.NewService` (`checkKeys func() map[string]struct{}`), not an
  `Option` and not a lookup this package performs itself. The obvious
  alternative — `items` importing `internal/checks` or `internal/rules` for
  its own catalogue — would have become a real import cycle the moment the
  evaluation ticker needed `items.Decide` (`internal/rules` already depends
  on `internal/items`, so the reverse edge cannot exist), not a hypothetical
  one; making the dependency a required constructor argument means
  forgetting it is a compile error at every call site, rather than a
  `Service` that silently accepts a check key naming no real metric. The
  real catalogue is supplied only at the one point that may import both —
  `internal/app`, from `rules.Catalogue()`.
- **`CreateDecision` takes the acting user and stamps `created_by`.** Not
  named in the data model above (which lists `created_by` as a column but
  not as a parameter), but the same shape every comparable domain in this
  codebase already takes: `schedules.Service.Create`,
  `triggers.Service.Create` and `maintenance.Service.Create` all accept an
  actor for the same reason `items.Service.CreateDecision` now does — a
  decision is an operator's call, and `created_by` is what lets a reader six
  months later answer *who*, without digging through the audit log for the
  matching create event (the note already answers *why*).
- **The API refuses `scope=org` together with `decision=watch`** —
  `items.Service.buildDecision`'s own `invalidf` — rather than merely
  having the GUI not offer the combination, which is as far as "Resolving a
  decision" above goes ("The interface should not offer it there as though
  it did"). Watching is already the default everywhere a decision does not
  apply, so an organization-wide watch can never have an effect; refusing it
  at the one place every caller goes through means the rule and the absent
  GUI option say the same thing, and no such row can ever exist for a
  client other than this SPA to later have to render truthfully and refuse
  to save.
- **`Preview` validates only the fields it reads — scope, host, check key,
  match kind and pattern — never verdict or note.** Unstated above, and
  deliberate: neither verdict nor note can change what a pattern matches,
  so a preview with no verdict chosen yet (or an over-long note, still
  unremarkable while an operator is shaping the pattern) must not turn a
  match count into a 422. A previewed input that passes can still be
  rejected by `CreateDecision`/`UpdateDecision` for verdict or note — the
  dialog already has to let a pattern be previewed and then abandoned.
- **Creating, changing or deleting a decision marks the affected monitored
  hosts' evaluation cursors dirty, in one batched statement for an
  organization-scoped write.** The spec above never says *when* a decision
  takes effect, and the honest default — the host's own next due time —
  could be minutes away on a quiet host, which reads as "I ignored it and
  nothing happened." `internal/api/item_handlers.go`'s `markDirtyForDecision`
  calls the exact same single-row upsert `internal/checks`' own ingest path
  already issues on every accepted batch (`rules.DirtyMarker.MarkHostDirty`)
  for a host-scoped decision, and its batched sibling
  (`MarkHostsDirty`, one multi-row upsert) for an organization-scoped one —
  narrowed to *monitored* hosts, since an unmonitored host runs no checks
  and so has nothing an item decision could ever change the judgment of.
  Best-effort, deliberately: the decision write has already committed by
  the time this runs, and failing the whole request over a missed
  prompt-evaluation hint would turn a successful write into an error the
  operator cannot act on. An edit that moves a decision between hosts (or
  between host and org scope) marks both the old and the new target.
- **Discovery and the decision read run outside the per-host claim
  transaction.** "Discovery and evaluation" above says `Load` inserts newly
  seen items "in the same per-host transaction `Apply` opens" — true of
  every other read `Load` performs (`ListCheckCurrent`, `ListRules`,
  `GetHostFacts`, `ListCheckStates`), but not of `items.SQLStore`:
  `EvalSQLStore.Load` calls `s.items.Discover`/`s.items.Decisions`
  (`internal/rules/load_sql.go`) straight on the `items.Store` interface,
  whose `SQLStore` (`internal/items/store_sql.go`) runs every statement
  through `gen.New(d)` on the package's own `*db.DB` wrapper — which looks
  for a transaction bound under `db.WithOrgScope`'s own context key
  (`boundTxKey`, `internal/db/scope.go`) — while the claim binds the host's
  transaction under a different, package-private key
  (`evalTxKey`, `internal/rules/due_sql.go`). The two context-binding
  schemes were never bridged, so both calls run on the pool, not inside the
  claimed host's transaction. Judged harmless and left as is: `Discover` is
  `ON CONFLICT DO NOTHING` (a crash between it and the claim's own commit
  loses nothing but re-does a no-op insert next tick), the design already
  decouples items and decisions from the evaluation outcome they feed
  (`Load`'s own read, not `Apply`'s write), and under Postgres' default READ
  COMMITTED isolation a statement run inside the same transaction would take
  its own snapshot at the start of that statement regardless — the
  transaction boundary buys atomicity with the *write-back*, which these two
  reads do not need. Bridging the two schemes would mean teaching
  `internal/db` or `internal/items` about the other's transaction key, which
  is a larger change than this sub-project's own scope; recorded as backlog
  3.38.
