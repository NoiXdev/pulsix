# v0.2c/v0.2d Automation — design

Date: 2026-09-18 · Status: approved in brainstorming · Covers backlog 2.13, 2.13a–2.13c,
2.23, 2.24 and the push-webhook half of 2.8. Parent spec:
`2026-09-10-pulsix-architecture-design.md` (§7 Ansible execution, §11 Alerting, §14
Security).

## 1. Scope and slicing

One design, two implementation plans, each merged on its own and shippable:

| Plan | Contents |
|------|----------|
| **v0.2c Automation core** | Schedules (cron/simple, timezone, overlap and catch-up guards, pause, per-schedule overrides), incoming webhook triggers for job templates and Git repos, the Workers page with token enrollment, certificate renewal and revocation |
| **v0.2d Notifications & calendar** | Notification channels (email, generic webhook) with a delivery queue, maintenance windows (host, inventory group, org) and the maintenance guard, schedule notification rules and the weekly digest, the activity view of triggered runs, the calendar |

Channels and maintenance windows are pulled forward from v0.4 in minimal form: two
channel kinds and three maintenance targets. v0.4 extends the same tables (more
channel kinds, monitoring-group targets, routes, escalation); v0.5 adds public
maintenance announcements. Nothing here is built twice.

The v0.2d plan is written after v0.2c is merged, against the real code.

## 2. Schedules (v0.2c)

### Data

`schedules` (org-scoped, RLS policy pair, composite FK `(org_id, template_id)`):

| Column | Notes |
|--------|-------|
| `id`, `org_id`, `template_id` | several schedules per template |
| `name` | unique per org |
| `mode` | `cron` or `simple` |
| `cron` | 5-field cron plus the macros `@hourly @daily @weekly @monthly`; for `simple` the compiled expression |
| `simple` | jsonb, the form's input (`every_minutes`, `every_hours`, `daily {time}`, `weekly {days, time}`, `monthly {day, time}`), kept so the form round-trips |
| `timezone` | IANA name, validated with `time.LoadLocation` |
| `guards` | jsonb: `overlap` (`skip` default, or `queue`), `catch_up` (`{enabled, window}`, default disabled, window 1 h, max 24 h). v0.2d adds `maintenance` |
| `limit`, `extra_vars` | optional overrides, validated exactly like a manual run (template schema, sealing of secret values, the connection-security denylist of 2.36) |
| `paused`, `next_run_at`, `last_run_at` | |
| `created_by`, `created_at`, `updated_at`, `revision` | `revision` drives If-Match like other editable objects |

`schedule_runs` (org-scoped): `schedule_id`, `due_at`, `decided_at`, `outcome`
(`triggered`, `skipped_overlap`, `missed`, `failed`), `reason`, `job_group_id`
(nullable). Retention: the last 500 per schedule (trimmed by the ticker).

Simple mode compiles to cron on save; one evaluator runs everything. Minimum interval
is 1 minute. Cron evaluation uses a maintained library that supports time zones; the
plan picks it (robfig/cron is excluded: unmaintained since 2020) or writes a small
parser if none qualifies.

DST: occurrences are computed in the schedule's time zone. A local time skipped by a
spring-forward runs at the next valid minute; a local time repeated by fall-back runs
once (first occurrence).

### Ticker

A manager goroutine ticks every 15 s (config `PULSIX_SCHEDULE_TICK`, min 5 s):

1. In one transaction, `SELECT … FROM schedules WHERE NOT paused AND next_run_at <= now()
   ORDER BY next_run_at LIMIT 50 FOR UPDATE SKIP LOCKED` (bypass scope; every statement
   filters by org_id, same pattern as the job reaper).
2. For each row: if `now - next_run_at` exceeds the grace period (2 × tick), the run is
   *late*. A late run is triggered only when `catch_up.enabled` and it is inside the
   window; otherwise it is recorded as `missed`. Several missed occurrences collapse into
   one `missed` row and at most one catch-up run.
3. Otherwise the overlap guard: with `skip`, a non-terminal job of the same template
   records `skipped_overlap`; with `queue` the run is enqueued anyway.
4. Enqueue through the existing template-run service path (same validation, zone split,
   host-key checks as manual runs) with trigger `schedule` and actor `schedule:<id>`.
   An enqueue error records `failed` with a generic reason; the detail goes to the log.
5. Record the `schedule_runs` row, set `last_run_at`, compute the next `next_run_at`
   from `now` (not from the old due time, so a long downtime never replays a backlog).

`SKIP LOCKED` makes several managers safe (v0.6 HA) without a leader.

### Actor and permissions

Scheduled runs keep running when the creator loses access; the audit records actor
`schedule:<id>` plus `created_by` and `template_id`. Managing schedules needs
`templates.write`; viewing needs `templates.read`. Pause/resume and "run now" are
audited. Deleting a template deletes its schedules (FK cascade) — the UI warns first.

Jobs gain `trigger_kind` (`manual`, `schedule`, `webhook`, `system`) and
`trigger_ref` (schedule or trigger id), additive migration, shown in the runs list
and run view.

### UI

Follows the mockup's Scheduler artboard (`design/mockups/build.mjs`, "SCHEDULER"): a
Schedules tab next to Repositories / Job templates / Editor, listing all schedules of
the org (status dot, name, template · scope, cron + human text, next, last result),
"Pause all", "New schedule", and a detail panel (template, timezone, simple/cron
switch with the next 5 occurrences, guards, overrides, recent runs, run now, pause,
save). The template page links to its schedules. The mockup's week calendar and
notification rules arrive with v0.2d.

## 3. Webhook triggers (v0.2c)

### Data

`job_triggers` (org-scoped): `id` (uuid v7, the URL identifier), `org_id`, `kind`
(`template_run`, `repo_sync`), `template_id` or `repo_id` (exactly one, check
constraint), `name`, `enabled`, `auth` (`hmac` or `token`), `secret` (sealed like
credentials, AAD `trigger:<org>:<id>`), `signature_header` (preset: Pulsix
`X-Pulsix-Signature-256`, GitHub `X-Hub-Signature-256`, Gitea `X-Gitea-Signature`,
GitLab `X-Gitlab-Token` as token mode), `timestamp_header` (optional replay window
±5 min), `allow_cidrs` (cidr[], empty = any), `mapping` (jsonb), `on_active`
(`queue` or `skip`), `rate_limit` (`{count, per}`, default 10/min),
`created_by`, timestamps, `revision`.

`trigger_deliveries` (org-scoped): `trigger_id`, `at`, `source_ip`, `outcome`
(`triggered`, `skipped_active`, `rejected_ip`, `rejected_auth`, `rate_limited`,
`invalid_payload`, `disabled`), `reason`, `job_group_id`. No request body is stored.
Rejected deliveries are throttled to one row per trigger, outcome and minute. Last
500 kept per trigger.

`trigger_buckets`: `trigger_id`, `tokens`, `updated_at`; token bucket updated with
one `UPDATE … RETURNING` so several managers share the limit.

### Endpoint

`POST /api/v1/hooks/jobs/{trigger_id}` and `POST /api/v1/hooks/repos/{trigger_id}`,
outside the session/CSRF middleware, no org in the path (the trigger id resolves it
through a bypass-scoped lookup that returns only what the check needs).

Client IP: the API has no trusted-proxy handling yet (chi's RealIP is deliberately
not mounted). v0.2c adds `PULSIX_TRUSTED_PROXIES` (CIDR list, default empty): only
when the TCP peer is inside it, the client IP is the right-most `X-Forwarded-For`
entry that is not itself a trusted proxy; otherwise it is the TCP peer. The same
helper serves the enrollment rate limit and audit source IPs.

Check order: body ≤ 1 MiB → trigger exists and enabled → client IP in allowlist
→ signature over the
raw body with HMAC-SHA256, or the bearer token, both compared in constant time, plus
the optional timestamp window → rate limit → mapping → validation → enqueue.

Responses: `202 {"run_id": …}` or `202 {"status": "skipped"}`; unknown trigger,
disabled trigger, wrong IP and wrong signature all answer `404` with an empty problem
body, so trigger ids cannot be probed; `413`, `422` (generic reason naming the field,
never echoing values), `429` with `Retry-After`. The secret travels only in headers;
a `?token=` query parameter (shown in the mockup) is not supported because URLs end
up in proxy logs.

### Mapping

`mapping` holds `{"extra_vars": {"<var>": "<jsonpath>"}, "limit": "<jsonpath>"}`.
Paths use the RFC 9535 subset: root `$`, member names (dot and bracket), array index,
wildcard `[*]`. A wildcard result maps to a list (for `limit`, joined with `,`).
Missing path = unset. Mapped values then go through the template's normal
validation: schema types, required fields, the 2.36 denylist; secret-typed fields
cannot be mapping targets (rejected at save). `repo_sync` triggers take no mapping.

### Audit and UI

Every triggered run records actor `webhook:<trigger_id>` and the source IP. The
template detail shows a Triggers card as in the mockup: URL with copy, auth mode,
allowlist, mapping, rate limit, `on_active`, "Rotate secret", "Test call" (a signed
request from the manager to itself, recorded like any delivery), the last 50
deliveries, and copy-ready snippets (curl, GitHub, GitLab, Gitea). The secret is shown
once at creation and at rotation. The repo page gets the same card for `repo_sync`
(this closes the 2.8 push-webhook item). Permissions: `templates.write` /
`repos.write` to manage, `.read` to view (never the secret).

## 4. Workers, enrollment, certificates (v0.2c)

### Token enrollment

"Add worker" (zone, name) creates `worker_enrollments`: `id`, `org_id`, `zone_id`,
`name`, `secret_hash` (SHA-256 of 32 random bytes), `expires_at` (1 h), `used_at`,
`created_by`. The UI shows the token once:
`pxw1.<enrollment-id>.<secret>.<ca-sha256>` (base64url parts), plus docker run and
compose snippets.

gRPC gains `Enroll(EnrollRequest{token_id, secret, csr, version}) → {certificate,
ca_chain, worker_id}`. The server's TLS switches from `RequireAndVerifyClientCert` to
`VerifyClientCertIfGiven`; a unary/stream interceptor requires a verified client
certificate for every method except `Enroll`. `Enroll` is rate limited per source IP.
The worker dials with the CA pinned to the fingerprint in the token (no system
roots), so a first contact cannot be intercepted. The manager checks the token
(unused, unexpired, constant-time secret compare), validates the CSR (Ed25519 or
ECDSA P-256, no extensions honoured, CN set by the manager), issues the certificate,
creates the `workers` row and marks the enrollment used — one transaction.

The worker keeps key, certificate and CA in its state directory. On start, a valid
bundle wins and `PULSIX_ENROLL_TOKEN` is ignored. The CLI (`pulsix-manager worker
add`) and the compose `worker-enroll` service stay.

### Certificates, renewal

`worker_certificates`: `serial` (PK, decimal text), `org_id`, `worker_id`,
`not_before`, `not_after`, `revoked_at`. The existing `workers.cert_serial` column is
backfilled into it and no longer read (additive migration; the column stays).

New leaf validity: 90 days (was 825; existing certificates keep theirs). The worker
calls `RenewCertificate(csr)` over its mTLS connection when less than a third of the
validity remains (checked at start and every 6 h); the new certificate is written
atomically (temp file + rename) and used for new connections. The old one stays
valid until it expires, so open streams are not cut.

### Revocation (2.24)

"Revoke" sets `revoked_at` on every certificate of the worker and the worker's
`status = revoked` (row kept for audit), closes its open event streams, and requeues
its non-terminal jobs (counting as an attempt, reason "worker revoked"). The
interceptor looks up the serial on every RPC: unknown or revoked → `Unauthenticated`.
A revoked serial stays refused even if a worker row with the same name is recreated.
"Delete" is allowed only for revoked workers.

### Workers page

Per org: name, zone, status (`online` = seen within 2 min, `offline`, `revoked`), last
seen, version, certificate expiry (highlight under 14 days and offline workers),
current job. Actions: add (token dialog), revoke (confirm), delete. Pending
enrollments are listed with their expiry and can be withdrawn. Permissions:
`workers.read`, `workers.write` (owner and admin by default). The navigation entry
"Workers" exists in the mockup shell.

## 5. Notification channels (v0.2d)

`notification_channels` (org-scoped): `kind` (`email`, `webhook`), `name`, `config`
jsonb with secrets sealed (AAD `channel:<org>:<id>`), `enabled`.

- email: recipient list; sent through the instance SMTP (`internal/mail`). Without
  instance SMTP the kind is unavailable and the UI says why.
- webhook: method (POST/PUT), URL, headers (values sealed), body template (Go
  `text/template` over a fixed event struct, JSON-escaped helpers), optional
  HMAC-SHA256 signature header.

Every channel has "Send test". Delivery: `notification_deliveries` (channel,
payload, status, attempts, next_attempt_at, last_error) processed by a manager
worker with `SKIP LOCKED`; exponential backoff, at most 6 attempts, then `failed`.
The delivery log is visible per channel.

Outbound webhook safety: resolve then dial the resolved IP; private ranges are
allowed (self-hosted targets are normal), loopback, link-local and metadata
addresses (`169.254.0.0/16`, `fe80::/10`, `127.0.0.0/8`, `::1`) are refused unless an
instance allowlist (`PULSIX_NOTIFY_ALLOW_CIDRS`) permits them. Redirects are not
followed. Timeout 10 s.

## 6. Maintenance windows (v0.2d)

`maintenance_windows` (org-scoped): `name`, `target_kind` (`host`, `inventory_group`,
`org`), `target_id`, one-off `starts_at`/`ends_at` or recurring (`cron` + `duration` +
`timezone`, same evaluator as schedules), `note`, `created_by`. v0.4 adds
monitoring-group targets and alert silencing; v0.5 adds public announcements.

Maintenance guard per schedule: `ignore` (default; patch runs often belong inside a
window), `skip` (record `skipped_maintenance` when any target host is in a window),
`exclude_hosts` (drop hosts in a window; if none remain, `skipped_maintenance`).

## 7. Schedule notifications and digest (v0.2d)

`notify_rules` on the schedule: a list of `{on: failure | change | success |
skipped, channels: [...]}`. `change` = at least one host reported changed. `skipped`
covers `skipped_*` and `missed`. At most one message per run and channel (rules
merged). Messages carry schedule, template, result, counts, duration and a link to the
run — never log output or variables.

Weekly digest per org: channels, weekday, time, timezone. Content: runs per schedule,
failures, skips/misses, slowest runs over the past 7 days.

## 8. Activity and calendar (v0.2d)

The runs list gains filters by trigger kind and schedule. The activity page gets the
object types `schedule`, `trigger`, `worker`, `channel`, `maintenance`.

Calendar (Schedules tab, as in the mockup: week, month, list): occurrences are
computed server-side (`GET /api/v1/orgs/{org}/calendar?from&to`, range ≤ 6 weeks),
past occurrences show their `schedule_runs` outcome and job status, maintenance
windows are drawn as bars. Clicking opens the schedule or run.

## 9. Security notes

- Webhook and enrollment endpoints are the first unauthenticated write paths besides
  login/setup: body limits, constant-time compares, uniform 404s, per-trigger and
  per-IP rate limits, no secrets in URLs or logs.
- Trigger secrets, channel secrets and schedule extra-var secrets are sealed at rest.
- Scheduled and webhook runs pass through the same enqueue validation as manual runs,
  including host-key pin checks and the 2.36 denylist.
- Spec §14 gains the enrollment trust model (CA pin in the token, one-time secret,
  key never leaves the worker) and the outbound webhook rules.

## 10. Testing

- Cron/simple compilation, DST forward/back, time zones, catch-up and missed
  collapsing: table-driven with an injected clock.
- Ticker against the Postgres container, including two concurrent tickers (each
  occurrence decided exactly once).
- Webhook API matrix: auth modes, presets, timestamp window, allowlist, rate limit
  across two "managers", mapping (paths, wildcard, missing, secret target refused,
  denylist), `on_active`, uniform 404s.
- Enrollment: single use, expiry, wrong CA pin refused by the worker, CSR validation,
  renewal, revocation cuts streams and requeues jobs; E2E enroll → claim → revoke.
- v0.2d: delivery queue against fake SMTP/HTTP servers, backoff, SSRF refusals,
  maintenance guard modes, rule merging, digest content, calendar occurrence API.
- SPA: Vitest for the schedule form (simple/cron, next 5), trigger card, token dialog,
  workers page, calendar. Coverage floors unchanged.
