# v0.2f — Resources the installation owns

Status: approved, not yet planned
Backlog: 2.90
Milestone: v0.2f, the second half of the production-readiness pair that
began with v0.2e

## The problem

A service provider runs one Pulsix for several customers. Their customers
are organizations inside it. Today every organization is a sealed world:
the same playbook repository, the same job templates and the same check
definitions must be created again in each one, and every later correction
must be made again in each one.

That is the duplication this product removes everywhere else, reappearing
at the tenancy boundary. It surfaced while preparing the first production
use with real customers, alongside v0.2e.

## What may be shared, and why that list is short

Shared: **playbook repositories, job templates, check definitions** — the
provider's own intellectual property.

Excluded on purpose: **credentials and jump hosts**. A credential reachable
across a customer boundary is a lateral-movement path, since anyone who may
start a run in customer A would reach customer B. Hosts, alerts, runs and
maintenance windows are customer data by definition.

The exclusion is not a policy bolted onto the design; it is the design. A
shared definition carries **no secret by construction**, so there is nothing
for a policy to get wrong.

## Decisions

### 1. A shared definition is projected into each organization, not referenced from it

The obvious shape — `org_id` nullable, meaning "the installation owns this
row" — does not survive this schema, and the reason is structural rather
than awkward.

Tenancy here rests on two independent mechanisms: row-level security, and
composite foreign keys `(org_id, id)`. Five tables already point at the two
candidates that way:

```
jobs          (org_id, repo_id)     → git_repos (org_id, id)
schedules     (org_id, template_id) → job_templates (org_id, id)
job_triggers  both
git_repo_vault_credentials, job_template_vault_credentials  (v0.2e)
```

A job in organization A carries `org_id = A`. Pointing it at an
installation-owned repository with `org_id = NULL` would require `(A, id)`
to match `(NULL, id)`. It cannot. A reserved sentinel organization fails
identically, for the same reason.

So the alternative would be dropping those composite keys and leaving
tenancy to RLS alone — trading two independent mechanisms for one, which is
the same trade the architecture decision of 2026-10-19 rejected when it
chose one installation per provider over a provider level above the
organization.

Instead: the installation owns a **definition**, and each organization holds
an ordinary row that is a **projection** of it, carrying its own `org_id`,
its own `id`, its own RLS and its own composite keys. Nothing in the
existing schema changes meaning. The cost is one row per organization and a
propagation path, which is the cheaper half of this trade by a wide margin.

### 2. The definition carries what is the provider's; the projection carries the bindings

Every column belongs to exactly one side, and the split is the same idea
each time: what is the same for every customer is shared, what names that
customer's own world is theirs.

| | definition (read-only inside an organization) | projection (the customer's) |
|---|---|---|
| repository | name, url, branch, subpath | credential |
| job template | playbook path, `limit`, `extra_vars`, schema | scope, ssh credential |
| check definition | key, plugin, params, interval | binding (org / group / host), `enabled` |

This refines backlog 2.90's own wording, which says a shared resource is
"visible and usable but not editable". Part of it **must** be editable: the
bindings are exactly what the installation cannot know and what the
resource does not work without. The read-only part is the shared part.

`name` belongs to the definition for every resource type, and the table
above said so only for check definitions until an implementer pointed out
the gap. A projection's name has nowhere else to come from, and it is what
makes decision 7's collision check mean anything.

`check_definitions.key` belongs to the definition because it *is* the
check's identity, and it participates in that table's uniqueness together
with the binding. `enabled` belongs to the projection: a customer must be
able to switch a check off for their own fleet without the provider
losing it everywhere, and a definition the provider wants gone is deleted
rather than disabled.

A job template's `playbook_id` resolves per organization — each one syncs
its own clone of the repository and gets its own `playbooks` row — so the
definition stores the playbook's path and the projection stores the
resolved id.

### 3. A shared repository authenticates with the organization's own credential

The provider's playbook repository is usually private, so something must
open it.

A credential on the definition would be delivered to every organization's
worker, because the claim ships the git credential to the worker and
workers belong to zones that belong to organizations. That does not expose
customer A to customer B — it exposes the **provider's own deploy key to
every customer**, on hosts a customer may control.

So the definition carries url, branch and subpath, and each organization
supplies its own read-only deploy key. One key per customer on the
provider's repository, set once.

### 4. A new definition appears in every organization, including later ones

Creating a definition projects it into every organization immediately, and
creating an organization projects every existing definition into it — the
same seam `rules.SeedForOrg` already uses.

A projection whose bindings are not yet filled in shows as incomplete
rather than hiding. "Configure it once" is the point of the feature, and a
catalogue a customer must know to go looking in is not that.

Rejected: a per-definition list of organizations (one more step per new
customer, for control the provider rarely wants), and an opt-in catalogue
(furthest from the goal).

### 5. Deleting a definition in use is refused, not cascaded

A projection may be named by a schedule, a trigger or a job — a customer's
configuration. Deleting a definition therefore fails with `ErrInUse` while
any projection is referenced, naming where, exactly as `credentials`
already behaves.

The provider's housekeeping must not silently remove a customer's
automation.

### 6. An organization cannot delete its own projection

Deleting is how a row disappears, and a projection the installation owns
must not disappear from one organization while the definition still
exists — the next propagation would recreate it, so the delete would
either be undone or need a tombstone, and a tombstone is the opt-out
catalogue decision 4 rejected wearing a different hat.

An organization that does not want a shared resource leaves its bindings
empty, which is already how an unconfigured projection looks. If a
customer genuinely should not have a definition at all, that is the
provider's call and it belongs on the definition — which is the shape
decision 4 deliberately did not build, and the first thing to revisit if
this proves wrong in use.

### 7. A name collision fails loudly and names the organizations

`git_repos` carries `UNIQUE (org_id, name)`, and the other two have their
own uniqueness. A definition named `ansible-base` cannot be projected into
an organization that already has a repository of that name.

Creating or renaming a definition therefore fails with a message listing
the organizations that already use the name, rather than quietly appending
a suffix. A silently renamed resource is one the provider cannot refer to
in writing, which defeats configuring it once.

### 8. Definitions sit at the installation level, like `instance_settings`

No `org_id`, no row-level security, no policy pair — the posture
`instance_settings` has had since migration 00009. Access is a service-layer
decision on `Principal.InstanceAdmin`, which already exists and already
carries through `internal/auth`.

Only an instance admin writes a definition. Inside an organization the
shared part is read-only for everyone, while the bindings follow the
existing write permission for that resource (`repos.write` and so on).

## Data

Three definition tables, no `org_id`:

```sql
CREATE TABLE shared_repos (
  id         uuid PRIMARY KEY,
  name       text NOT NULL UNIQUE,
  url        text NOT NULL,
  branch     text NOT NULL,
  subpath    text NOT NULL DEFAULT '',
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);
```

and the same shape for `shared_job_templates` and
`shared_check_definitions`, each holding only its own half of decision 2's
table.

Each projected table gains one nullable column, additive:

```sql
ALTER TABLE git_repos        ADD COLUMN shared_repo_id uuid REFERENCES shared_repos (id);
ALTER TABLE job_templates    ADD COLUMN shared_template_id uuid REFERENCES shared_job_templates (id);
ALTER TABLE check_definitions ADD COLUMN shared_definition_id uuid REFERENCES shared_check_definitions (id);
```

Non-null means the row is a projection. The reference is deliberately *not*
composite: the parent has no `org_id` to compose with, which is the whole
point of decision 1 — the tenancy-bearing keys stay between org-scoped
tables, and this one crosses to the installation level, where nothing is
tenant data.

`check_definitions.origin` is `CHECK (origin IN ('seed','custom'))` today and
gains `'shared'`. That is a constraint replacement rather than a column
drop, so it stays within the additive-only rule.

## The GUI

A projected row is marked as installation-managed wherever it is listed and
wherever it is opened, and its shared fields are shown disabled rather than
hidden — the same call v0.2e made for a superseded field, and for the same
reason: a value that still describes the resource should stay visible even
when this is not the place to change it.

An instance admin gets one place to manage definitions, outside any
organization, beside the existing instance settings.

## Risks

- **A projection drifting from its definition.** Propagation writes the
  shared columns of every projection; if one write fails, that organization
  silently runs an older playbook path or interval. Propagation must be
  atomic per definition, and a projection must be able to report that it is
  stale rather than merely look current.
- **A customer discovering the provider's other customers.** An error
  naming organizations (decision 7) is shown to an instance admin only,
  never inside an organization. Worth a test, because the natural way to
  write that message is to let it escape.
- **The projection count.** One row per organization per definition is
  cheap, but the propagation path is O(organizations) per edit. Fine at the
  scale this product targets; worth measuring once rather than assuming.
- **`origin = 'shared'` meeting code that only knows `seed` and `custom`.**
  Every switch over origin needs finding, not just the ones tests cover.

## Acceptance

- An instance admin creates a shared repository; it appears in every
  organization, marked as installation-managed, its url read-only.
- An organization adds its own credential to that repository and runs a
  playbook from it.
- A second organization's credential is not visible to the first, and
  neither organization can edit the url.
- Editing the definition's branch changes it in every organization; the
  credentials are untouched.
- A new organization created afterwards has the repository already.
- Deleting a definition a schedule depends on is refused, naming the
  dependency.
- Creating a definition whose name an organization already uses is refused,
  naming that organization — to an instance admin, never inside an
  organization.
- `make test`, `golangci-lint run`, the SPA suite, the coverage gates and
  `npm run e2e` all pass.
