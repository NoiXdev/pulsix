# Pulsix v0.3b-2 — Rules and states design

**Status:** approved 2026-09-29. Supersedes nothing; refines the architecture
spec's §9 (points 6 and 7, rules and states) for the second of the three
sub-projects that together deliver v0.3b. It builds directly on v0.3b-1
(`2026-09-27-v0.3b-checks-design.md`), which delivered measurement and
deliberately evaluated nothing.

**Goal:** every value the check pipeline already collects gets a meaning. An
operator writes rules — in a form editor or as an expression — decides what
counts as `warn` and what as `crit`, sees the resulting state per metric, per
host and across the whole fleet, and can see for any host which rule decided
its state and where that rule came from.

## Why this is the second of three

v0.3b-1 measures and stores. This sub-project judges. Discovery and per-item
overrides (v0.3b-3) come after, and alerting — alerts as rows, routes,
escalation, acknowledge, snooze, silence and every form of notification —
is v0.4 and is **not** in this document. A state turning `crit` here changes
a colour and a row; it wakes nobody.

That cut is deliberate. Rules are the part of the monitoring stack that is
hardest to get right and easiest to get subtly wrong, and a rule engine whose
mistakes only show up as a wrong colour is far cheaper to correct than one
whose mistakes page an on-call engineer. v0.4 inherits a state machine that
has already run against a real fleet.

## Division of labour

**The agent still knows nothing.** It measures and ships observations, exactly
as v0.3b-1 defined. No threshold, no severity, no state ever reaches it. This
document adds no agent-side behaviour at all and no change to the wire
contract.

**The manager decides what a value means.** Evaluation runs in the manager,
over the values `check_current` already holds and, for windowed expressions,
over `check_samples`. It is triggered by a ticker rather than by the ingest
path (see "Evaluation"), so a burst of samples cannot slow the stream that
carries them.

**The database holds the state machine's memory.** Candidate states, the
moment a state began and the history of changes are rows, not process memory:
a manager restart in the middle of a five-minute `for_duration` window must
not restart the clock, and two managers must not reach different conclusions.

## Decisions

| Decision | Choice | Why |
|---|---|---|
| Scope of this sub-project | Rules and states only; no alerts, routes or notifications | The architecture spec's own decomposition. Milestone gate 3.4a's notification half stays open until v0.4 |
| Expression mode | Ships in full, including window functions (`avg`, `min`, `max`, `rate`) | The rule editor of mockup 0.8 promises both modes; a form-only first cut would have to be rebuilt rather than extended |
| Window source | Raw `check_samples` through `check_samples_lookup_idx`, window length capped at 24 h | Continuous aggregates are deferred (v0.3b-1, "Retention"); the existing index serves a bounded window from one or two daily chunks |
| Evaluation trigger | A ticker every 15 s over a per-host cursor, not evaluation inside the ingest transaction | Keeps the ~7 000 samples/s hot path free of SQL aggregates, and one code path covers thresholds, duration, missing data and windows alike. `for_duration` and `unknown` need a timed path regardless — this way there is one engine, not two |
| Ingest's contribution | One single-row upsert per **batch** marking the host dirty | ~170 upserts/s at the fleet target, against 7 000 samples/s. The cheapest possible watermark, and it makes an idle host cost nothing |
| Rule granularity | One severity per rule row | The architecture spec's "first matching rule per severity wins" — `disk` warn and `disk` crit are two rows, and precedence resolves per severity |
| Both editor modes | Compile into one AST, stored as `jsonb` | The evaluator never sees the difference, so the form mode cannot drift from the expression mode's semantics |
| Item binding | Full item scope now: a rule may bind to `(host, check_key, item)` | Chosen over an item filter inside the rule body. It is the architecture spec's fourth precedence level, and v0.3b-3 will attach real item rows to bindings that already exist |
| Orphaned item rules | The row survives an item that stops being reported | Mirrors `check_current`, which never deletes a row for a vanished mount: nothing observes a disappearance. The effective view labels it "no longer observed" |
| First thresholds | A seeded, editable rule set per organization; no plugin defaults in code | Mirrors `checks.SeedForOrg`. A code-level default is a number an operator cannot see, cannot edit and would silently re-inherit after deleting the visible row |
| `service.state` seed rule | None | Backlog 4.3's standing ruling: the seeded `sshd` check must not alert by default, or a host that legitimately lacks the unit becomes a 3 a.m. page |
| `for_duration` direction | Applies to deterioration only; recovery takes effect at once | A host that is healthy again should not stay red for ten more minutes |
| `unknown` vs. no data | `unknown` means "we had data and lost it"; a host that never reported shows "no data" | A state is a statement about something observed. A host with no tuples has nothing to be unknown about |
| Roll-up order | `crit` > `warn` > `unknown` > `ok` | A known problem is more urgent than an unknown one; one expired mount must not mask a real `crit` |
| Group state | Derived on read from member hosts, never stored | Group membership is a selector: it changes when a host's tags change, with no write to the group |
| Precedence ties | Decided by a strict total order, and the loser is shown | An evaluation that depended on map iteration order would make states flap. The architecture spec's "report the ambiguity" is served by the effective view naming the shadowed rule, not by leaving evaluation undecided |

## Data model

Three migrations, additive, each org-owned table carrying the RLS policy pair
in the exact shape migration 00037 uses and the composite `(org_id, id)`
foreign keys the schema convention requires.

### `check_rules` (migration 00045)

One rule judges one metric with one severity.

```
id            uuid primary key
org_id        uuid not null → organizations
name          text not null
enabled       boolean not null default true
origin        text not null check (origin in ('seed','user'))
scope         text not null check (scope in ('org','group','host','item'))
group_id      uuid null      -- scope='group';  FK (org_id, group_id) → monitoring_groups
host_id       uuid null      -- scope in ('host','item'); FK (org_id, host_id) → hosts
item          text not null default ''   -- scope='item'
check_key     text not null
metric        text not null              -- 'disk.used_pct', 'service.state', …
severity      text not null check (severity in ('warn','crit'))
mode          text not null check (mode in ('form','expression'))
ast           jsonb not null
clear_ast     jsonb null
source        text not null
for_duration  interval not null default '0'
created_at, updated_at
```

A `CHECK` constraint ties `scope` to the column it requires: `group_id` set
exactly for `group`, `host_id` for `host` and `item`, `item` non-empty exactly
for `item`. The rule references `check_key` as **text**, never a
`check_definitions` row — for the same reason samples do: a definition may be
edited or deleted without orphaning the rules written against its key.

`mode` exists for the editor alone. Both modes compile into `ast`; `source` is
what the operator typed (the expression) or a rendered summary (the form).

### `check_states` (migration 00046)

The current state of one `(host, check_key, item, metric)` tuple.

```
primary key (host_id, check_key, item, metric)
org_id, host_id, check_key, item, metric
state            text not null check (state in ('ok','warn','crit','unknown'))
since            timestamptz not null
rule_id          uuid null → check_rules on delete set null
last_value       double precision null
last_label       text null
candidate_state  text null
candidate_since  timestamptz null
flapping         boolean not null default false
evaluated_at     timestamptz not null
```

`rule_id` is `ON DELETE SET NULL` rather than `CASCADE`: deleting the rule
that currently holds a `crit` must not delete the state row — the next tick
re-evaluates the tuple and moves it, which is the behaviour review focus 7
pins.

### `check_state_changes` (migration 00046)

Append-only, a TimescaleDB hypertable on `at` with one-day chunks and a
90-day retention policy — the same shape as `check_samples`.

```
at, org_id, host_id, check_key, item, metric,
from_state, to_state, rule_id, value, label
```

It feeds flapping detection (changes within 30 minutes) and becomes v0.4's
alert history, so that milestone adds routing rather than a second journal.

### `check_host_states` (migration 00046)

```
primary key (host_id)
org_id, host_id
state         text not null
crit_count, warn_count, unknown_count  integer not null default 0
since         timestamptz not null
evaluated_at  timestamptz not null
```

The fleet overview reads one row per host instead of aggregating every tuple
of every host on each page view.

### `check_eval_cursor` (migration 00047)

```
primary key (host_id)
org_id, host_id
dirty_at      timestamptz not null
evaluated_at  timestamptz not null default 'epoch'
next_due_at   timestamptz not null default 'epoch'
```

with an index on `(next_due_at)` for the ticker's claim. This is the whole
scheduling substrate: no queue table, no lease column, no retry counter.

## The rule language

Both editor modes produce the same tree. The node set is deliberately small:

| Node | Meaning |
|---|---|
| `metric(name)` | the current value of `name` for the tuple being evaluated |
| `window(agg, name, duration)` | `avg`, `min`, `max` or `rate` of `name` over the last `duration`; `duration` ≤ 24 h |
| `fact(name)` | a host fact collected by v0.3a, e.g. `cpu_count` |
| `number`, `string` | literals |
| `arith(op, l, r)` | `+`, `-`, `*`, `/` over numbers |
| `compare(op, l, r)` | `>`, `>=`, `<`, `<=`, `==`, `!=` over numbers |
| `label(op, metric, values)` | `==`, `!=`, `in` over a discrete metric such as `service.state` |
| `and`, `or`, `not` | boolean composition |

`rate` is `(last − first) / seconds` over the window. Together with `arith`
it is what makes the architecture spec's own examples writable without further
node types: `avg(cpu.used_pct, 10m) > fact("cpu_count") * 0.8`, or a
days-until-full estimate from `disk.free_bytes` and its rate.

**Facts are strings.** `internal/agent/facts` reports every fact as text by
contract (`map[string]string`), so `fact(name)` yields a number only when its
stored value parses as one. Whether it does cannot be known when the rule is
saved — facts differ per host — so a fact that does not parse, or that the host
does not report at all, makes the rule **not match** on that host, exactly like
a missing metric. Division by zero does the same: it is a non-match, never an
error and never a severity.

**Typing is checked at save time, not at evaluation time.** A rule that
compares a discrete metric with a number, names a metric no plugin reports, or
uses a window longer than the cap is refused by `POST /rules` and
`POST /rules/validate` with the position in the source. The evaluator
therefore never meets a malformed tree — but it still treats a tree it cannot
evaluate as "does not match", never as `crit`, because a rule engine that
fails loudly into the worst severity is a rule engine that pages on its own
bugs.

**A missing value is not a false comparison.** If the metric a rule names has
no current value, or its window contains no sample, the rule does not match.
The tuple's state in that situation comes from the `unknown` path below, not
from a threshold silently reading as satisfied.

**The form subset** is one `compare` or one `label` node against a literal,
optionally with a clear condition. A form rule stays editable in the form
editor as long as its AST stays in that subset; switching to expression mode
is one-way and the GUI says so before doing it.

## Precedence and the effective view

For each `(check_key, item, metric, severity)`, the winning rule is chosen by
scope: **item > host > group > org**. Among group-scoped rules, the winner is
decided by the same strict total order `checks.Group.beats` already
implements — higher `priority`, then the older `created_at`, then the smaller
id, byte for byte. Being a strict total order, it never depends on the order
the candidates are visited in, which is what keeps a resolution stable across
ticks and across managers.

A group-scoped rule reaches a host through the very same membership the check
definitions use: `internal/checks`'s selector matching over the host's tags.
There is no second notion of membership in this sub-project, so a host cannot
receive a group's checks without also receiving that group's rules.

Disabled rules take part in nothing: they are filtered before precedence, so
disabling the host-scoped rule lets the group's rule win rather than leaving
the metric unjudged.

`GET /hosts/{id}/effective-rules` returns, per tuple and severity, the winning
rule with its source and **the rules it shadowed**. That is where the
architecture spec's requirement to surface ambiguity is met: the resolution is
always decided, and never silent about what it decided against.

## Evaluation

### Trigger

`checks.RecordObservations` gains one statement per batch:

```sql
INSERT INTO check_eval_cursor (org_id, host_id, dirty_at) VALUES (…)
ON CONFLICT (host_id) DO UPDATE SET dirty_at = excluded.dirty_at
```

The ticker runs every 15 s and claims work in bounded batches:

```sql
SELECT … FROM check_eval_cursor
WHERE dirty_at > evaluated_at OR next_due_at <= now()
ORDER BY next_due_at LIMIT :batch
FOR UPDATE SKIP LOCKED
```

`SKIP LOCKED` distributes hosts across managers without a claim protocol, the
same way `internal/schedules/due_sql.go` already works. Each host is evaluated
in its own transaction, so one host whose data is broken cannot roll back the
others.

If a tick overruns its deadline the overrun is counted and logged, and the
next tick simply takes the oldest `next_due_at` first: delay, not backlog. It
does not re-enter immediately — backlog 2.60 records what that costs. Lease
and staleness comparisons use the database's clock, not each manager's wall
clock (backlog 2.80).

### The evaluation itself is a pure function

`evaluate.go` takes the host's resolved checks (from the v0.3b-1 resolver, for
the intervals), its current values, its effective rules, the window aggregates
those rules asked for, the previous states and `now`. It returns the new
states, the state changes to append, the host roll-up and the next
`next_due_at`. No IO, so every rule below is a table-driven test without a
database.

The shell around it loads, calls, and writes states, changes, roll-up and
cursor in one transaction. Window aggregates are fetched in a single statement
per host: a `VALUES` list of the needed `(check_key, item, metric, agg, from)`
tuples, joined laterally against `check_samples`, every row served by
`check_samples_lookup_idx`.

### Order of decision, per tuple

1. **`unknown` first.** The last value is older than 3 × the check's interval,
   or `check_current` carries a collection error → `unknown`. This outranks
   every threshold: a rule cannot say anything true about data that is not
   there.
2. Otherwise every effective rule is evaluated and the highest matching
   severity wins (`crit` over `warn`); no match is `ok`.
3. **Hysteresis.** If the tuple stands at `warn` or `crit` and the deciding
   rule has a `clear_ast`, the state holds until the *clear* predicate becomes
   true — not merely until the trigger predicate becomes false. Without a
   `clear_ast`, it clears as soon as the trigger predicate is false.
4. **`for_duration` applies downward only.** A deterioration is recorded as
   `candidate_state`/`candidate_since` and becomes the state once it has held
   continuously for the duration; an improvement takes effect immediately. A
   candidate that flips back before it ripens is discarded, and the change is
   not written to `check_state_changes` — the history records states, not
   candidates.
5. **`next_due_at`** is the minimum of "the candidate ripens" and "the last
   value goes stale". This is what lets a tuple reach `unknown` when nothing
   arrives at all: the ticker comes back for a host that has gone silent.
6. **Flapping** counts this tuple's changes in `check_state_changes` over the
   last 30 minutes: set at 5, cleared below 3 — its own hysteresis, so the
   flag does not flap. In this sub-project it is a label only; v0.4 hangs
   notification suppression on it.
7. **Roll-up** into `check_host_states`: the worst tuple state, ordered
   `crit` > `warn` > `unknown` > `ok`, with a count per severity. A host with
   no tuples at all gets no row and renders as "no data".

## API and permissions

All routes are org-scoped under `/api/v1/orgs/{org}/`, and carry the same
permissions as the check definitions of v0.3b-1.

| Route | Purpose |
|---|---|
| `GET/POST /rules`, `GET/PUT/DELETE /rules/{id}` | CRUD, filterable by scope, `check_key` and host |
| `POST /rules/validate` | parse and type-check an expression without saving; returns the error position and whether the AST still fits the form subset |
| `GET /hosts/{id}/effective-rules` | per tuple and severity: the winning rule, its source, and the rules it shadowed |
| `GET /hosts/{id}/checks` | **existing** route, extended additively with `state`, `since` and `flapping` per tuple |
| `GET /fleet` | hosts ordered worst-state-first with per-severity counts; filters by zone, monitoring group and tag |

`/fleet` is a route of its own rather than a sort parameter on `/hosts`: it
reads `check_host_states`, one row per host, and has nothing in common with
host administration's query shape.

Mutating routes are audited; `TestEveryMutatingRouteIsAuditedOrAllowlisted`
stays green with no new allowlist entries.

## GUI

The existing `ChecksTabs` gains a third tab, **Rules**, beside Checks and
Monitoring groups — a rule is a sibling of a check definition, not a separate
region of the product.

- **Rule editor, two modes.** Form: scope picker (org / group / host / item),
  metric, operator, value, clear value, duration, severity. Expression: a text
  field validated against `POST /rules/validate`, errors marked at their
  position. The switch from form to expression names its one-way nature before
  making it.
- **Host page, monitoring card:** a colour per tuple, with `unknown` and
  `flapping` as their own markers beside the stale hint v0.3b-1 already
  renders. Opening a tuple shows the **effective rules**: the deciding rule
  with a provenance chip (Org / Group *X* / Host / Item) and the shadowed
  rules folded underneath.
- **Fleet overview** as a new navigation entry: every host ordered by its
  worst state, counts per severity, filters by zone, group and tag.

No new charts — v0.3b-1's graphs stand unchanged. No new frontend dependency,
and no i18n scaffolding (backlog 3.22 stays open).

## Testing

- **Unit, table-driven:** every AST node including type errors and absent
  values; the parser including error positions; form ↔ AST as a round trip;
  precedence, mirroring `resolver_test.go`'s shape; the pure evaluation
  function with an injected clock over `for_duration`, hysteresis, `unknown`,
  flapping and roll-up.
- **Integration against Postgres:** the window-aggregate statement; the
  `SKIP LOCKED` claim exercised by two concurrent tickers; the RLS policy pair
  of each new table.
- **API** through `internal/api/apitest`, including cross-org access.
- **SPA:** Vitest ≥ 70 % for the editor and the fleet page, **and Playwright
  specs shipped with the feature**. Backlog 2.68 and 2.78 already record this
  debt for two earlier milestones; this one does not add to it.
- **E2E scenario in Go:** an agent reports a value above the threshold →
  after `for_duration` the API shows `crit` → the value recovers → `ok`; the
  agent then goes silent → `unknown` after 3 × the interval. The scenario uses
  a short-interval definition of its own so that the staleness deadline is
  seconds rather than minutes. This is as much of gate 3.4a as is reachable
  without notifications.
- `internal/rules` joins `scripts/coverage-gate.sh`'s 90 % list, beside
  `internal/checks` and `internal/agentapi`. Everything else keeps the 80 %
  floor.
- **Performance:** a benchmark over one host with many mounts and windowed
  rules, plus the tick's own overrun counter, establish the measurement. If a
  large fleet outgrows the ticker, the documented way out is to move the
  trigger to a dirty-queue with a worker pool — the evaluation function and
  every table above stay as they are.

## Review focus

The input classes the design implies but that no single task's own tests would
otherwise exercise. Each gets its pinning test in the task that owns the code.

1. **Two rules of equal precedence and equal severity.** The same winner on
   every evaluation, whatever order the candidates are visited in.
2. **An item-scoped rule whose item stops being reported.** The rule survives,
   the tuple runs into `unknown`, and the effective view says "no longer
   observed" rather than hiding the rule.
3. **A window containing no sample, or exactly one.** A defined result: no
   value means the rule does not match — never `crit`. `rate` over one sample
   is not a division by zero.
4. **A `for_duration` window spanning a manager restart.** `candidate_since`
   is a row, so the clock survives; the state must not restart its wait.
5. **An agent going silent mid-window.** `unknown` outranks the ripening
   candidate, and the candidate is discarded rather than ripening in the dark.
6. **Two managers seeing the same host due.** Exactly one evaluation, one set
   of state changes, no duplicate history rows.
7. **A rule deleted while it holds a `crit`.** `ON DELETE SET NULL` keeps the
   state row; the next tick re-evaluates the tuple and moves it.

## Explicitly not in this sub-project

Alerts as rows, routes, escalation, acknowledge, snooze, silence, the alert
timeline, and every form of notification — all v0.4. Discovery and per-item
overrides, and items as first-class rows — v0.3b-3. Synthetic checks, probes
and web assertions. The `script` plugin, `agent.yaml` and secret references.
Windows and macOS collectors. Continuous aggregates and per-organization
retention. Plugin-level default thresholds in code. SPA i18n.

## As built

Where the implementation deviated from what is approved above — every one a
deliberate decision made during Tasks 1–14, not a drift nobody noticed.

- **The metric catalogue has eleven entries, not eight.** Task 1's first
  commit (`1e1c769`) built `Catalogue()` (`internal/rules/catalog.go`) against
  exactly the eight metrics v0.3b-1's plugins were assumed to report:
  `cpu.used_pct`, `mem.used_pct`, `mem.available_bytes`, `swap.used_pct`,
  `disk.used_pct`, `disk.free_bytes`, `disk.inodes_used_pct` and
  `service.state`. `cpu.load1`, `cpu.load5` and `cpu.load15` — which the cpu
  plugin has reported since v0.3b-1 (`internal/agent/checks/cpu.go`) — were
  missing, even though the architecture spec's own plugin list names
  `cpu` "load 1/5/15" outright (`2026-09-10-pulsix-architecture-design.md`,
  line 422) and its flagship rule example — `avg(cpu.load5, 10m) >
  cores * 0.8` — is unwritable without `cpu.load5` in the catalogue. Fixed
  the same day, in a commit of its own (`8d61b66`) before Task 2 started, so
  nothing built on top of the gap.
- **A route the table above omitted: `GET /orgs/{org}/rules/metrics`.**
  Task 10's own pre-flight scan added it: the rule editor's metric picker
  (`RuleDialog.tsx`) has no other honest source for which metrics exist and
  what kind each is, and a list hand-copied into the SPA would silently drift
  from `Catalogue()` the moment a plugin gained a metric — exactly the
  failure mode the previous bullet just described. Same permission as every
  other read here (`checks.read`).
- **A tuple with no state row reports `state: null`, not `"ok"`.**
  `hostCheckValueDTO.State` (`internal/api/host_check_handlers.go`) and
  `fleetHostDTO.State` are both nullable rather than defaulting healthy: a
  state is a statement about something the evaluator actually judged, and
  reporting `ok` before that first evaluation has run would assert a health
  nobody established. The SPA's own `stateLabel`/`fleetStateLabel` render the
  two nulls differently on purpose — "not yet evaluated" for one tuple,
  "no data" for a whole host with no roll-up row at all — because they are
  different facts even though both begin life as the same JSON `null`.
- **`Snapshot` gained a field the original data model did not have:
  `PreviousHost`.** The design's own "`since` carries over" contract for the
  host roll-up cannot be implemented from the tuple states alone once one
  alerting tuple recovers while another holds the host at the same overall
  state — the tuple-only derivation would drift `Since` forward onto the
  surviving tuple. `Snapshot.PreviousHost` (`internal/rules/evaluate.go`) is
  the last roll-up the previous evaluation wrote, threaded through so `Since`
  carries over exactly when the host's own state has not changed; `nil` is a
  supported input with a documented, bounded degradation for a caller that
  does not have it on hand.
- **A tuple whose check resolves no interval is excluded from evaluation and
  the roll-up entirely, and a host with no measured tuples has its roll-up
  row deleted.** Neither is explicit in the sections above. The first mirrors
  backlog 3.28's read-side-filter ruling one layer up: judging a frozen value
  from a deleted or disabled check would hold a stale verdict forever, and
  inventing `unknown` for it would paint a deleted check grey on the fleet
  page with nothing an operator could do about it. The second is what makes
  "no data" reachable at all (`rules.Evaluate`'s zero `Result.Host` when no
  tuple survives the first filter; `EvalSQLStore`'s `Apply` deletes rather
  than leaves a stale colour behind).
- **The flapping count includes the change the current evaluation is about
  to write**, not only the changes already on the books when the tick began.
  A tuple whose fifth change in the rolling window is the one this very
  evaluation produces is flagged flapping on that same tick — the flag exists
  for an operator watching a tuple move, and it should not lag a tick behind
  the move that earned it.
- **`POST /rules/validate` is a read:** `PermChecksRead`, not
  `PermChecksWrite`, and allowlisted in `audit_coverage_test.go` rather than
  audited — following `POST /monitoring-groups/preview`'s own precedent
  exactly (same shape: a POST only because the payload is a request body,
  persists nothing, and here the editor calls it on every debounce, which
  would otherwise bury the three real mutations — create, update, delete —
  under keystroke noise).
- **The fleet response's totals describe the filtered set, not the whole
  organization.** `fleetTotalsDTO` (`internal/api/fleet_handlers.go`) counts
  exactly the hosts `GET /fleet`'s own zone/group/tag filter matched, with a
  doc comment saying so explicitly: a total that disagrees with the list
  beside it on the same page is worse than no total, and an operator who
  wants the organization's own figures clears the filter.

### Changed by the whole-branch review

Three of the above acquired a bound or a guard the sections further up do not
describe. They are listed here rather than edited into those sections because
each is a refusal the approved design did not call for.

- **An expression is bounded in length and in nesting depth.**
  `Service.buildRule` refuses an expression over 4 KiB, and both the parser
  (`parser.enter`) and `TypeCheck` refuse a tree nesting deeper than
  `maxRuleDepth` = 64 levels. Every walker over `Node` is a plain recursion,
  so depth is stack depth, and a stack overflow in Go is a runtime fatal no
  recover can catch — `POST /rules/validate` is reachable with `checks.read`
  and carries a 1 MiB body limit. Both guards exist because neither covers
  the other: a parenthesis costs stack frames without costing tree depth, and
  `1+1+1+…` costs tree depth at a constant frame depth.
- **A rule may only read the metrics of its own check.** `buildRule` walks
  both compiled trees and refuses any metric, window or label node whose
  catalogue entry names a different `check_key` than the rule's own, pointing
  at the offending node's position. The evaluator builds one `Input` per
  `(check_key, item)` from that item's tuples alone, so a rule bound to
  `disk` whose expression reads `mem.used_pct` would compile, store, and then
  never match — the silent-never-match failure the catalogue exists to
  prevent, reached through a known metric rather than an unknown one.
- **A `for_duration` candidate must have been watched continuously.**
  `decide` carries `candidate_since` forward only when the previous
  evaluation of that tuple is at most three check intervals old, and
  otherwise restarts the wait at `now`. A tuple whose check stops resolving
  an interval is skipped before step 1, so its row — candidate included —
  freezes rather than ageing into `unknown`; without the continuity test, a
  check disabled mid-ripening and re-enabled days later promoted instantly,
  on a deterioration nothing had observed to hold.
