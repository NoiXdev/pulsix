## Decisions taken in this plan

- **2.40 (bastion key pins):** a bastion pin mirrors the host model of 00021: `bastions` gains `ssh_host_key text` (the full OpenSSH public key line, `SHA256:<fingerprint>` fingerprint stored alongside) — the probe (Task 10's sshprobe) already dials every hop and sees each hop's host key; a connection test triggered for a host records its hops' keys (TOFU per hop, one row per bastion in a new `bastion_host_keys` snapshot column on the test result? NO — simpler: the probe result gains `hop_keys []{bastion_id, fingerprint, key}`; the pin write targets the bastion; enforcement: the runner's ssh_config generator (Task 9) demands the pinned key per bastion alias the same way it does for hosts (`StrictHostKeyChecking=yes` + `HostKeyAlias=pulsix-bastion-<id>`); a changed bastion key fails every connection through it (fail closed, same as hosts).
- **2.41 (git server key pins):** `git_repos` gains `ssh_host_key text` pinned at first successful sync (TOFU), enforced with `StrictHostKeyChecking=yes` afterwards; a changed key fails the sync job with an error naming the repo and the new fingerprint (never proceeds). Token-based (https) repos have no host key; the column stays NULL.
- **2.43 (pin not enforceable):** pins made before migration 00021 hold only a fingerprint. The hosts/bastions read APIs gain `pin_state: "full" | "fingerprint_only"`; claims for fingerprint-only hosts fail with the documented "run a connection test to complete the pin" message (already the behavior); the SPA shows the state on the SSH card and ConnectionTestCard. The daily re-test completes such pins automatically (already does — the state makes it visible).
- **2.44 (refuse unpinned):** an org-level boolean setting `jobs_require_pinned_hosts` (default false, spec §5's TOFU-for-one-job stays the default), exposed as `PUT /orgs/{org}/settings/jobs` — the enqueue paths (template run, adhoc, bootstrap, rotation) refuse unpinned hosts when set (422 naming the hosts). The setting rides the existing org-settings table (check how SMTP settings are stored; additive).
- **2.45 (per-zone limit):** `EnqueueRun`'s scope resolution applies the template `limit` per zone job at enqueue: a limit that matches no host of a zone produces a normal job whose scope is empty → that zone's job is NOT created (a run that would cover zero hosts overall fails with `ErrEmptyScope` as today); the limit remains on the job payload for ansible (defense in depth).
- **2.46 (revocation targets snapshot):** `EnqueueRotation` snapshots the referencing host/bastion ids into the rotation group (a `rotation_targets` jsonb on the group's first job or a dedicated column on `jobs.rotation_credential_id` rows — choose: store the snapshot sealed in the group's first rotate_key job payload? NO: the revocation phase needs the list without secrets. Resolution: `job_groups`-style: add `rotation_targets jsonb` to the first job row? Cleanest: a small `rotation_groups (id, org_id, credential_id, targets jsonb, created_at)` table, migration 00033; `FinishRotation`/`revoke_key` reads targets from there, so a target that stopped referencing the credential mid-rotation is still revoked (as decided in sign-off 3).
- **2.47+2.52 (legacy plaintext template secrets):** `sealSecrets` treats a stored PLAINTEXT value under a secret-typed field as keepable: the masked/keep marker resolves to the stored plaintext and seals it (the stored value stays until a save re-seals it — no background job). Keep-marker + plaintext stored = OK; mask marker = OK; only a missing stored value is the problem.
- **2.49–2.51 (event internals):** the stream's attempt is carried from the binding into every append (an old attempt's still-open stream appends under its own attempt and keeps its binding alive until its stream closes — the reaper must not requeue a job whose ANY attempt's stream is alive); `max(seq)` lookup gains a `created_at >= job.created_at` bound (the hypertable partition column) so it scans only the job's own chunks; UTF-8 truncation switches to `strings.ToValidUTF8` (single pass).
- **2.53 (reaper staleness):** the exhaustion transition re-checks staleness inside the transaction (predicate in the UPDATE), so a job that got a fresh binding in between is not failed.
- **2.59 (gofmt gate):** CI gains a `gofmt -l` (or gofumpt) check; the five known-deviant files are fixed in the same task.
- **2.83 (race flake):** CI and README split `go test -race ./...` into per-package-group invocations; the plan's task briefs already do this.
- **2.84 (digest cap):** `schedules.Service.Digest` caps the schedule list at 100 entries (most relevant first: schedules with runs in the period, then by name), appends `"schedule_count_total"` so the webhook can say "+N more"; the e-mail body renders the same cap. `maxBodyBytes` stays the backstop; a capped digest renders, never fails permanently.
- **2.85 (SPA error surfaces):** `ChannelsPage`, `DigestCard`, `ScheduleNotifications` get the same query-guard treatment the calendar received (error state instead of vanishing/permanent skeleton).
- **2.66 (gRPC addr validation):** `PULSIX_GRPC_PUBLIC_ADDR` validation names the right variable in errors and rejects a bare `:443` (no host).

### Task 4: Template legacy secret sealing (2.47, 2.52)

- `internal/templates/service.go` `sealSecrets`: a keep/mask marker whose stored value is a PLAINTEXT string under a secret-typed field is keepable — the stored plaintext is sealed into the outgoing result (fresh seal with the row's AAD), so a legacy template saves cleanly and the value is sealed from that save on. A marker with NO stored value stays the validation problem. `schema.StraySealed`-style edge: a stored value that is neither string nor sealed envelope under a secret field (e.g. number after a string→secret change) is NOT keepable (same problem message) — document.
- The no-save re-seal part of 2.47: claims read plaintext under a secret field as the value (current behavior) — after this task a save migrates it; the claim path already accepts it; confirm no separate job needed (the backlog row asks "without a save" — resolve: a one-time SQL pass would encrypt with the AAD requiring the box at migration time (impossible) — so the resolution IS on-save sealing; update the backlog row to say so).
- Tests: keep marker over legacy plaintext saves and re-reads masked; marker over missing value still problems; claim of a legacy plaintext still works.
- Backlog rows 2.47, 2.52 → done.

### Task 5: Event internals (2.49, 2.50, 2.51)
