## Owner decisions (2026-11-25, binding)
- **3.13g:** yes, like rules. A decision on a plugin key applies to every check of that plugin. A decision on the exact check key takes precedence. The Items page shows such items as decided "via the plugin decision".
- **4.39:** adopt within 1 hour. When the same alert subject opens again within one hour after its previous episode closed `stale` (not resolved), the new episode takes over the previous episode's acknowledgement and snooze. If the new severity is higher than the acknowledged severity, nothing is adopted.

## Rulings (controller's calls)
- **3.13g matching.** `items.Target` gains `Plugin string`. A decision applies to a target when its `CheckKey` equals the target's `CheckKey` (exact key) **or** equals the target's `Plugin` (plugin key); scope applicability as today. Precedence (`beats`), a strict total order: scope (host > org) first, then key (exact check key > plugin key), then match kind (exact > glob), then older `CreatedAt`, then smaller ID. For a check whose key *is* its plugin name the two coincide and count as the exact key. Every caller fills `Plugin` from the check it already has (find the plugin in each call site's data; if one lacks it, load it the cheapest way the call site's existing reads allow — say which in the report). A target with an unknown plugin (`Plugin == ""`) matches exact keys only. Update `Decide`'s and `applies`' doc comments. Tests (`decide_test.go`, table-driven): a plugin-key decision reaches a copied check (`disk` → `disk-data`); an exact-key decision beats a plugin-key one in the same scope; a host plugin-key decision beats an org exact-key one; a plugin-key decision does not reach a check of another plugin; an empty Plugin matches exact only. Plus one integration test through the evaluation (`internal/rules` load) that an org-wide ignore on `disk` silences an item of a `disk-data` check.
- **3.13g UI/API.** The API already returns the deciding decision with an item (check `item_handlers.go` / `host_check_handlers.go` DTOs); if the DTO carries the decision's `check_key`, the SPA can tell "via plugin decision" by comparing it with the item's own check key — prefer that over a new field. The Items views (find them under `web/src/features`) show a short marker on such items: EN `via the plugin's decision`, DE in the file's existing register. When creating a decision from an item of a copied check, the form keeps offering the item's own check key as today (no new choice); the decision list shows plugin-key decisions as they are. Vitest for the marker.
- **4.39 decision is pure.** Reconcile stays a pure function: the evaluator's input gains, per host, the recently closed episodes the opening needs (`rules.AlertInput` or a parameter beside `open` — choose the shape that keeps `rules` free of `alerts` types as today; read where `open` comes from in the store and add one query: for the host, per subject, the latest alert closed with reason `stale` whose `closed_at` is within one hour before the evaluation's `At`). When Reconcile emits `ActionOpen` for a subject that has such an episode, it carries what to adopt: the acknowledgement (`AckAt`, `AckBy`, `AckSeverity`, `AckNote`) when the old episode was acknowledged **and** `StateRank(new severity) <= StateRank(AckSeverity)`; the snooze when `SnoozedUntil` is still after `At` (a timed snooze), or when `SnoozeUntilChange` is set and the new severity equals the old episode's severity at close; when the new severity is above the acknowledged severity, nothing at all is adopted (owner decision). The window is a named constant `reopenAdoptWindow = time.Hour`. An episode closed `resolved`, `forgotten` or any other reason is never adopted from. Only tuple-scope alerts adopt (the host-scope unknown alert does not). Peak is not adopted.
- **4.39 store and history.** The store executes the adoption inside the same insert (the opening row starts acknowledged/snoozed), records which episode it continued in a nullable column `continues_alert_id uuid REFERENCES alerts(id)` (additive migration, next number; check the backup tests), and the alert's timeline shows an entry at the opening: EN `Acknowledgement carried over from the previous episode` / `Snooze carried over from the previous episode` (whichever applied), linking the earlier alert if the timeline UI has links (find `timeline.go` and the SPA's alert detail). Notifications: an opening that adopted a snooze is muted exactly as any snoozed alert is today; an opening that adopted only an acknowledgement still sends its firing notification (the problem is back — that is information), and escalation/reminders treat it as acknowledged exactly as an alert acknowledged by hand. Verify both against the existing mute and escalation code and say in the report which code paths do it. Tests: reconcile unit tests for every adopt/no-adopt case above (inside/outside the window at exactly 1 h, resolved close, severity above ack, timed snooze expired, until-change snooze with same/different severity, host-scope); one store/integration test through the evaluator: an acknowledged crit alert closes stale when its check is disabled, the check comes back within the hour still crit, the new alert is acknowledged and `continues_alert_id` points at the old one; and a notification-level test that an adopted ack does not restart an escalation chain's acknowledged-stop behaviour (find the existing escalation tests for acknowledged alerts and add the adopted case).
- **Docs.** `docs/upgrades.md` "Behaviour changes to check after an upgrade": item decisions on a plugin key now reach copied checks (an existing org-wide ignore on `disk` starts silencing `disk-*` checks); a check switched off and on within an hour keeps the acknowledgement. User docs in the docs clone: items/decisions page and alerts page; changelog.
