# Pulsix v0.3b-1 Check Pipeline Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every monitored host with an agent reports processor, memory and disk usage and the state of selected services; an operator sees current values and 1 h / 24 h / 7 d graphs per host and configures the checks — interval, parameters, enable/disable, and which hosts they apply to.

**Architecture:** The manager resolves check definitions bound to the organization, to monitoring groups (named host-tag selectors) and to hosts into one set per host, hashes it into a configuration version and pushes it over the existing agent stream; the agent runs a timer per check, measures, and ships observations with its own timestamps, buffering them across a disconnect. Nothing is evaluated: samples land in a TimescaleDB hypertable and a current-value table, and the GUI reads both. Rules, states and alerts are sub-project 2 and are deliberately absent here.

**Tech Stack:** as v0.3a (Go 1.27, chi v5, huma v2, pgx v5, sqlc, goose, buf, testcontainers-go, React 19, TanStack, Vitest, Playwright) plus uPlot (newest stable; verify the pin at write time) as the only new frontend dependency. `gopsutil/v4` is already a direct dependency and covers cpu, memory and disk; systemd unit state is read over D-Bus (`github.com/coreos/go-systemd/v22/dbus`, newest stable).

**Spec:** `docs/superpowers/specs/2026-09-27-v0.3b-checks-design.md` (binding for every decision below).

## Review Focus

The input classes the spec implies but that no task's own tests would otherwise exercise. Each already has its pinning test assigned to the task that owns the code; a reviewer checks them deliberately.

1. **Two groups match one host with equal priority and equal age.** The resolved set must be the same on every resolution — an order that depends on map iteration would make the configuration version flap and push endlessly (Task 3).
2. **A group's selector stops matching a host** (a tag was removed). The checks it contributed disappear from that host; the effective view must show the host falling back to the organization's set rather than silently losing the check (Task 3).
3. **An agent reconnects carrying a version for definitions that were deleted meanwhile.** The manager must converge on one push, not loop because the version never matches (Task 6).
4. **A sample batch arrives for a `check_key` whose definition was just deleted.** One unknown key must not fail the whole batch; the spec keys history by `check_key` precisely so history survives the definition (Task 4).
5. **A disk mount disappears** (unmounted, or the host shrank). Its `check_current` rows would otherwise sit there forever, looking current. The behaviour must be decided and documented, as the stale fact tag was in v0.3a (Task 4).

### Task 2: Check definitions and the seed set

**Files:** create `internal/db/migrations/00043_check_definitions.sql`, `internal/checks/definitions.go`, `internal/checks/seed.go`, tests alongside; modify `internal/db/queries/checks.sql`, `internal/checks/store_sql.go`.

**Interfaces — Produces:**
```go
type BindingKind string // "org" | "group" | "host"
type Definition struct {
    ID, OrgID uuid.UUID
    Key, Plugin string
    Params map[string]any
    Interval time.Duration
    Enabled bool
    Origin string // "seed" | "custom"
    BindingKind BindingKind
    GroupID, HostID *uuid.UUID
    CreatedAt, UpdatedAt time.Time
}
type DefinitionInput struct {
    Key, Plugin string
    Params map[string]any
    Interval time.Duration
    Enabled bool
    BindingKind BindingKind

}
func (s *Service) CreateDefinition(ctx context.Context, orgID uuid.UUID, in DefinitionInput) (Definition, error)
```

Table per the spec: the two nullable binding columns with a `CHECK` that exactly the one matching `binding_kind` is set, and
`UNIQUE NULLS NOT DISTINCT (org_id, binding_kind, group_id, host_id, key)` — without `NULLS NOT DISTINCT` two organization-bound rows with the same key would not collide at all, which is the case the constraint exists for. Composite FKs `(org_id, group_id) → monitoring_groups (org_id, id)` and `(org_id, host_id) → hosts (org_id, id)`, both ON DELETE CASCADE: deleting a group or host takes its bindings with it.

Validation in the service: key matches `^[a-z0-9][a-z0-9-]{0,62}$` and defaults to the plugin name; plugin is one of the four this milestone ships (a table in code, so an unknown plugin is refused at write time rather than silently never running); interval between 10 s and 24 h; params validated against a per-plugin schema (`disk` takes an optional mount allow-list, `service` a required non-empty unit list, `cpu`/`memory` take none).

The seed set is written when an organization is created — extend the existing organization creation path — and backfilled for existing organizations by the migration. Seeded rows carry `origin = 'seed'`; the service refuses to update a seeded row's key or plugin (copy it instead) but allows disabling it and changing its interval and parameters.

Tests: the validation table; the binding CHECK and the NULLS NOT DISTINCT constraint against the real database (two org-bound rows with the same key must conflict); seeding on organization creation; the backfill; cascade behaviour when a group is deleted.

Commit: `feat(checks): check definitions with bindings and the seeded Linux base`.

### Task 3: The resolver and the configuration version

**Files:** create `internal/checks/resolver.go`, `internal/checks/resolver_test.go`; modify `internal/checks/service.go`.

**Interfaces — Produces:**
```go
type Resolved struct {
    Key, Plugin string
    Params map[string]any
    Interval time.Duration
    Source BindingKind       // where the winning definition was bound
    SourceID *uuid.UUID      // the group or host it came from, nil for org
}
type ResolvedSet struct {
    HostID uuid.UUID
    Checks []Resolved // sorted by Key
    Version string    // sha256 over the canonical encoding, hex
}
func (s *Service) ResolveHost(ctx context.Context, orgID, hostID uuid.UUID) (ResolvedSet, error)
func (s *Service) ResolveOrg(ctx context.Context, orgID uuid.UUID) (map[uuid.UUID]ResolvedSet, error)
```

Rules, all from the spec: organization first, then every matching group, then the host; overriding matches on `Key`; among groups higher `Priority` wins and a tie goes to the older group by `created_at`, then by `id` — `ResolveOrg` must return the identical `Version` for identical inputs, so no step may depend on map iteration order. `Enabled = false` at any scope removes the check from the resolved set but is still reported by the effective view with its source, so the GUI can show where it was turned off. Only hosts with `monitored = true` resolve to a non-empty set.

`Version` is the hex SHA-256 of a canonical encoding: checks sorted by key, each rendered as `key\x00plugin\x00interval_seconds\x00canonical-json(params)\x00`, joined. Canonical JSON means sorted object keys — `encoding/json` sorts map keys, so marshalling `map[string]any` is enough, and the test pins it.

Tests (table-driven, fake store): org only; group overrides org; host overrides group; two groups, higher priority wins; two groups, equal priority, older wins; **two groups, equal priority and equal `created_at`, resolved by id and identical across 100 runs** (Review Focus 1); a group whose selector no longer matches falls back to the organization's definition and the effective view names the new source (Review Focus 2); `enabled=false` at host scope removes a check the organization enabled; an unmonitored host resolves to nothing; the same inputs produce the same version, and any change of key, plugin, interval or params changes it.

Commit: `feat(checks): resolve bindings into a per-host set with a version`.

### Task 4: Samples, current values, retention

**Files:** create `internal/db/migrations/00044_check_samples.sql`, `internal/checks/samples.go`, `internal/checks/samples_test.go`; modify `internal/db/queries/checks.sql`, `internal/checks/store_sql.go`.

**Interfaces — Produces:**
```go
type Observation struct {
    HostID uuid.UUID
    CheckKey, Item, Metric string
    At time.Time
    Value *float64
    Label *string
    Err string // collection failure; no sample row is written
}
type Current struct {
    CheckKey, Item, Metric string
    At time.Time
    Value *float64
    Label *string
    Err string
}
type Series struct {
    Metric string
    Points []Point // Point{At time.Time; Value float64}

func (s *Service) SeriesForHost(ctx context.Context, orgID, hostID uuid.UUID, checkKey, item, metric string, from, to time.Time, buckets int) (Series, error)
```

Schema per the spec: `check_samples` as a hypertable on `at` with one-day chunks and a 90-day retention policy; `check_current` with primary key `(host_id, check_key, item, metric)`; both with the RLS pair. A `CHECK` that exactly one of `value`/`label` is set on samples; `check_current` additionally allows both null when `error` is set.

`RecordObservations` writes one batch in one transaction: samples inserted, current values upserted. Rejection rules, counted and returned rather than erroring the batch: a timestamp more than 2 minutes in the future or more than 1 hour old, and an observation whose `check_key` is not in the host's current definitions is **still stored** (Review Focus 4 — history is keyed by `check_key` so it survives a deleted definition), but one whose host does not exist in the organization is rejected.

**A disappearing item keeps its current row** (Review Focus 5): nothing deletes `check_current` rows when a mount vanishes, exactly as a fact tag survives a fact in v0.3a. The row's `at` is what makes it visibly stale, and the host page must render an entry older than three intervals as stale rather than current. Documented on the type and pinned by a test.

Tests: round trip and bucketed series against the real database; the plausibility window at both boundaries (2 min − 1 s accepted, 2 min + 1 s rejected; 1 h − 1 s accepted, 1 h + 1 s rejected) with an injected clock; an unknown `check_key` stored and counted as accepted; an unknown host rejected without failing its batch; two-organization isolation; the retention policy present in the catalog after migration.

Commit: `feat(checks): sample storage, current values and retention`.

### Task 6: Configuration delivery and sample ingest

**Files:** modify `internal/agentapi/service.go`, `internal/agentapi/stream.go`, `internal/app/app.go`; create `internal/agentapi/checks_test.go`.

**Consumes:** Task 3's `ResolveHost`/`ResolveOrg`, Task 4's `RecordObservations`.

**Interfaces — Produces:** `agentapi.Deps` gains `Checks ChecksPort`:
```go
type ChecksPort interface {
    ResolveHost(ctx context.Context, orgID, hostID uuid.UUID) (checks.ResolvedSet, error)
    RecordObservations(ctx context.Context, orgID uuid.UUID, obs []checks.Observation) (int, int, error)

```

Behaviour: on every heartbeat, compare the agent's `config_version` against the resolved set's version and send `CheckConfig` when they differ — including the first heartbeat after connect, which is what repairs a push missed while the agent was away. A `CheckResults` message maps to `RecordObservations`; `checks.ErrInvalidInput` becomes `InvalidArgument`, anything else `Internal`, matching the facts path.

**Convergence (Review Focus 3):** the manager answers a version it does not recognise exactly as it answers any mismatch — by sending the current set once. Nothing remembers what was sent, so a stale or invented version cannot produce a loop; the test drives a heartbeat carrying a random version and asserts exactly one push, then no further push for the version that push established.

A definition, group, tag or capability change pushes to connected agents: `agentapi` exposes `PushHost(ctx, orgID, hostID)` and `internal/api`'s write paths call it after a successful write; a host that is not connected is a no-op, because the agent's own re-assert heals it within the configuration interval.

Tests in the bufconn harness: a heartbeat with an empty version receives the full set; the same version receives nothing; a changed definition pushes once; results are recorded and rejected counts surface in the log; a results message for an unknown host id is refused.

Commit: `feat(agentapi): deliver check configuration and ingest results`.

### Task 8: Scheduler and buffer

**Files:** create `internal/agent/checks/scheduler.go`, `internal/agent/checks/buffer.go`, tests alongside; modify `internal/agent/loop.go`, `internal/agent/session.go`, `internal/agent/config.go`.

**Interfaces — Produces:**
```go
type Scheduler struct{ /* ... */ }
func NewScheduler(reg map[string]Plugin, now func() time.Time, ticker func(time.Duration) Ticker) *Scheduler
func (s *Scheduler) Apply(cfg Config)                    // Config{Version string; Checks []Spec}
func (s *Scheduler) Version() string
func (s *Scheduler) Run(ctx context.Context, sink func([]Result)) error
type Buffer struct{ /* ring */ }
func NewBuffer(window time.Duration, now func() time.Time) *Buffer
func (b *Buffer) Add(r []Result) (dropped int)
func (b *Buffer) Drain() []Result
```

The scheduler holds one timer per check and applies a new configuration without restarting timers whose key, plugin, params and interval are unchanged — a configuration push must not reset the phase of every check on a fleet at once. Results go to the session's sender; when no stream is up they go to the buffer, which keeps 15 minutes and drops oldest first, counting drops. On reconnect the buffer drains before new results, preserving timestamps.

The loop reports `Scheduler.Version()` in every heartbeat and calls `Apply` when a `CheckConfig` arrives. `PULSIX_CONFIG_INTERVAL` (default 60 s, clamped 30–600 s) drives the re-assert; the agent sends a heartbeat at that cadence even when the heartbeat interval is longer, since the version rides it.

Tests with injected clock and tickers: a check fires at its interval; applying an unchanged configuration does not reset phase; applying a changed interval does; a disconnect buffers and a reconnect drains in order with original timestamps; the buffer overflows and counts; the version reported matches what was applied.

Commit: `feat(agent): check scheduler with a disconnect buffer`.
