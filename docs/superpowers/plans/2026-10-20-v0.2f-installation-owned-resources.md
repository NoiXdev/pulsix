# Installation-owned resources — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A service provider configures a playbook repository, a job template or a check definition once, at the installation, and every customer organization gets it — without any secret crossing a customer boundary.

**Architecture:** The installation owns a *definition* with no `org_id`. Each organization holds an ordinary row that is a *projection* of it, carrying its own `org_id`, RLS and composite foreign keys, so nothing in the existing schema changes meaning. The definition holds what is the same for every customer; the projection holds the bindings that name that customer's own world. The mechanism is built once against repositories, then applied to job templates and check definitions.

**Tech Stack:** Go 1.27, pgx v5, sqlc, goose, PostgreSQL 18, huma v2, React 19, TanStack Query, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-20-v0.2f-installation-owned-resources-design.md`

## Global Constraints

- Migrations are additive only. A `CHECK` constraint replacement counts as additive; a dropped column does not.
- Tenancy rests on two independent mechanisms and both must survive: RLS policy pairs (`org_isolation` / `org_isolation_bypass`, `ENABLE` **and** `FORCE`) and composite foreign keys `(org_id, id)` between org-scoped tables. A reference from an org-scoped table to an installation-level table is single-column by necessity and must say so in a comment.
- Definition tables carry no `org_id`, no RLS and no policy pair — the posture `instance_settings` has had since migration 00009. Access is a service decision on `Principal.InstanceAdmin`.
- Layers are strict: `internal/api` decodes, calls a service and encodes; services hold rules and depend on interfaces declared beside them; stores are sqlc behind those interfaces. Handlers never touch `gen.Queries`.
- No feature without tests; the failing test comes first. Run the race suite as `make test`, never a bare `go test ./...`. `internal/api` needs `-timeout 3600s`, everything else 900 s. The 600 s default panics the whole invocation rather than failing one test.
- `golangci-lint run` and `gofmt -s -l .` clean before every commit.
- Conventional Commits, footer `Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`.
- End-user documentation lives in `/Users/noidee/_dev/noix-docs` on branch `pulsix`, and never names the technology stack.

## Review Focus

Five things the spec implies that no task's own tests would otherwise reach:

1. **An organization deleted while definitions exist.** Its projections cascade away with it through `org_id`'s own foreign key. The next propagation must not fail, count it, or recreate it. *Pinned in Task 2.*
2. **Propagation failing partway.** The spec's own risk: one organization silently left on an older branch or interval while every list says current. Propagation is atomic per definition, and a test must prove a failed propagation leaves every projection on the previous value rather than some on each. *Pinned in Task 2.*
3. **An error naming organizations escaping into an organization-scoped response.** Decision 7's collision message lists other customers by name. It is for an instance admin only; the natural way to write it is to let it leak. *Pinned in Task 4.*
4. **A projection's binding pointing at a credential that is later deleted.** `credentials` refuses deletion while in use; a projection's credential must count as in use exactly like a normal row's. *Pinned in Task 3.*
5. **A new organization created while a definition is being edited.** It must receive either the old value or the new, never a projection written from a half-applied edit. *Pinned in Task 3.*

## Task 1: Migration 00060 and the repository definition table

**Files:**
- Create: `internal/db/migrations/00060_shared_repos.sql`
- Test: `internal/db/schema_test.go`, `internal/db/rls_test.go`

**Interfaces:**
- Produces: tables `shared_repos (id, name, url, branch, subpath, created_at, updated_at)` and column `git_repos.shared_repo_id uuid NULL REFERENCES shared_repos (id)`.

- [ ] **Step 1: Write the migration**

```sql
-- +goose Up
-- shared_repos is a playbook repository the INSTALLATION owns, projected
-- into every organization as an ordinary git_repos row (spec decision 1).
-- No org_id, no RLS and no policy pair: this is installation-level data,
-- the posture instance_settings has had since 00009, and access is a
-- service decision on Principal.InstanceAdmin rather than a database one.
-- It deliberately carries no credential — the projection supplies the
-- organization's own (spec decision 3), so a definition holds no secret
-- by construction rather than by policy.
CREATE TABLE shared_repos (
  id         uuid PRIMARY KEY,
  name       text NOT NULL UNIQUE,
  url        text NOT NULL,
  branch     text NOT NULL,
  subpath    text NOT NULL DEFAULT '',
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);

-- shared_repo_id non-null means this git_repos row is a projection of the
-- definition above: its url, branch and subpath are the definition's and
-- read-only inside the organization, while credential_id and the vault
-- identity set remain the organization's own.
--
-- Single-column on purpose, and this is the one place in the schema where
-- that is right: every other foreign key out of an org-scoped table is
-- composite (org_id, id) because both ends are tenant data. shared_repos
-- has no org_id to compose with — it is not tenant data — so composing is
-- not available, and nothing is weakened by its absence because the
-- parent is visible to every organization by design.
--
-- ON DELETE RESTRICT, not CASCADE: deleting a definition out from under a
-- customer's schedules is what spec decision 5 refuses. The service
-- reports that as ErrInUse before the database ever has to.
ALTER TABLE git_repos
  ADD COLUMN shared_repo_id uuid REFERENCES shared_repos (id) ON DELETE RESTRICT;

-- +goose Down
ALTER TABLE git_repos DROP COLUMN shared_repo_id;
DROP TABLE shared_repos;
```

- [ ] **Step 2: Write the failing schema test**

In `internal/db/schema_test.go`, in the style of its neighbours:

```go
func TestSharedReposSchema(t *testing.T) {

	// must NOT carry RLS. Both are asserted, because a later migration

}
```

Assert: `shared_repos` has no `org_id` column; `relrowsecurity` is false for it; `git_repos.shared_repo_id` exists, is nullable, and its foreign key's delete action is `r` (restrict).

## Task 2: The projection mechanism

This is the heart of the sub-project. Tasks 6 and 7 re-apply it; get it right here.

**Files:**
- Create: `internal/shared/definition.go`, `internal/shared/definition_test.go`, `internal/shared/service.go`, `internal/shared/service_test.go`, `internal/shared/store_sql.go`, `internal/db/queries/shared.sql`
- Test: as above

**Interfaces:**
- Produces, consumed by Tasks 3, 4, 6 and 7:
  - `type RepoDefinition struct { ID uuid.UUID; Name, URL, Branch, Subpath string }`
  - `Service.CreateRepo(ctx, in RepoDefinitionInput) (RepoDefinition, error)` — creates and projects into every organization
  - `Service.UpdateRepo(ctx, id uuid.UUID, in RepoDefinitionInput) (RepoDefinition, error)` — updates and propagates
  - `Service.DeleteRepo(ctx, id uuid.UUID) error` — `ErrInUse` when any projection is referenced
  - `Service.ProjectAllInto(ctx, orgID uuid.UUID) error` — for a newly created organization
  - sentinel errors `ErrNameTaken`, `ErrInUse`, `ErrNotFound`

- [ ] **Step 1: Write the pure rules and their failing tests first**

`definition.go` holds no SQL and no `context`. Table-driven tests for:
- which organizations collide on a name, given a definition name and a set of `(orgID, name)` pairs — returns the colliding organizations, so decision 7's message can name them;
- what a projection's shared columns should be, given a definition — the single place Tasks 6 and 7 will copy.

- [ ] **Step 2: Propagation is atomic per definition — Review Focus 2**

Write this test before the implementation:

```go
func TestUpdatePropagatesToEveryProjectionOrNone(t *testing.T) {
	// Three organizations hold projections of one definition. The second
	// organization's update fails. Every projection must still carry the
	// PREVIOUS branch — not two new and one old, which is the state that
	// looks current in every list while one customer quietly runs the
	// wrong playbook.
}
```

Make it fail first by implementing propagation as a loop of separate
statements, see the mixed state, then wrap it in one transaction the way
`repos.SQLStore.ReplaceRepoVaultIdentities` does (`s.d.Begin(ctx)`,
`gen.New(tx)`, explicit `Commit`, `defer tx.Rollback(context.WithoutCancel(ctx))`).

- [ ] **Step 3: A deleted organization does not break propagation — Review Focus 1**

An organization is deleted; its projection cascades away with it through
`git_repos.org_id`'s own foreign key. The next `UpdateRepo` must succeed
and must not recreate a row for the dead organization. Assert the surviving
projections' values and the total count.

- [ ] **Step 4: Delete refuses while a projection is in use**

A projection named by a schedule blocks `DeleteRepo` with `ErrInUse`, and
the error names where. A definition whose projections are referenced by
nothing deletes, taking the projections with it.

- [ ] **Step 5: The store and its queries**

Every statement in `internal/db/queries/shared.sql` carries a comment
saying **why**, in the style of `internal/db/queries/vault_identities.sql`.
Replacing a set is delete-then-insert as two statements inside one
transaction — never one data-modifying `WITH`, whose statement order
Postgres leaves undefined.

git add internal/shared internal/db
